# 赛后复盘模板

每次比赛或项目结束后，都应该做复盘。复盘不是写“这次学到了很多”，而是把能复用的判断、流程、模板、坑点沉淀下来。

## 1. 基本信息

```markdown
# 项目复盘：[项目名]

时间：
比赛/课程/展示场景：
团队成员：
最终提交物：
最终结果：
仓库地址：
Demo 地址：
```

## 2. 最终项目一句话

```text
当 [目标用户] 在 [具体场景] 遇到 [痛点] 时，
这个 Agent 通过 [核心 AI 能力]，
帮助用户完成 [现实结果]。
```

## 4. 正确决策

每条都要写原因：

```markdown
| 决策 | 为什么正确 | 下次是否复用 |
|---|---|---|
| 先做开发检验台 | 快速定位模型和状态问题 | 是 |
| 语音降级为实验功能 | 避免现场权限和 ASR 风险 | 是 |
```

## 5. 主要问题

不要只写“时间不够”，要具体：

```markdown
| 问题 | 表现 | 根因 | 下次预防 |
|---|---|---|---|
| 目标菜被旧图片影响 | 用户改文字后仍按旧菜规划 | 状态优先级不清 | 用户确认文本必须高于模型猜测 |
```

## 12. 下次项目默认规范

复盘最后，要沉淀成规则：

```markdown
以后 Agent 项目默认：

- 先写一句话价值。
- 先做一个具体场景闭环。
- 每个 Agent 输出 JSON schema。
- 第一天就做开发检验台。
- 模型结果进入下一步前要有确认或归一化。
- 用户端隐藏后台字段。
- 模型失败要有缓存兜底。
- 最后一天不加不稳定主功能。
```

## 13. 本次「厨房小助手」可直接复盘结论

这次项目已经可以先沉淀以下结论：

```markdown
## 正确决策

- 从“冰箱里有什么”升级为“今晚吃什么”，让视觉识别结果驱动行动。
- 选择“刷到想吃的菜 -> 拍冰箱判断够不够做”作为抖音场景，连接内容种草和现实库存。
- 保留用户确认库存，解决多模态识别不确定性。
- 增加目标菜识别后文本确认，避免模型误判直接进入规划。
- 做开发检验台，能快速定位每个 Agent 的输入输出。
- 做模型缓存和 source 标注，兼顾现场稳定和技术诚实。
- 展示端隐藏模型细节，开发台展示原始 JSON，面向不同观众分层。

## 暴露问题

- 模型可能把菜名当作食材，需要补常见菜品知识和 schema 约束。
- 等待状态如果没有阶段和超时提示，会让用户觉得卡死。
- 用户端话术容易技术化，需要持续替换成生活化表达。
- 图片识别结果和用户手动文字的优先级必须明确。
- 语音输入等功能现场风险高，不适合放进主演示流程。

## 下次默认复用

- 三层展示：情景视频、用户端 Demo、开发检验台。
- 四层兜底：固定样例、缓存 JSON、手动修正、备用录屏。
- Agent 合约：输入输出结构化，source 可追踪。
- 讲解顺序：先讲人和场景，再讲产品操作，最后讲技术可信度。
```
