# 开发检验台与调试闭环

开发检验台是这次比赛最值得复用的工程习惯之一。它不是“开发者自用页面”那么简单，而是调试工具、验收工具、路演可信证明三合一。

## 1. 为什么 Agent 项目需要开发检验台

AI Agent 和普通前端不同，问题经常出现在中间链路：

```text
图片是否真的传过去？
模型返回了什么？
JSON 是否符合 schema？
前端状态有没有被旧图片污染？
用户确认后的输入是否真的进入规划？
缓存是不是误用了？
```

如果只有用户端页面，很多问题看不见，只能猜。

开发检验台的目标：

```text
把每一步输入、输出、状态变化摊开。
```

## 2. 最小开发检验台结构

建议每个 Agent 项目都准备一个 `/dev.html` 或 `/debug` 页面。

最小模块：

| 模块 | 作用 |
|---|---|
| 服务健康状态 | provider、model、key 是否存在 |
| 原始输入区 | 上传文件、文本、参数 |
| 调用按钮 | 单独触发每个 Agent |
| 原始返回 JSON | 看模型到底说了什么 |
| 归一化结果 | 看业务状态如何整理 |
| 人工确认区 | 看哪些事实进入下一步 |
| 规划输入 JSON | 看最终传给规划 Agent 的内容 |
| 规划输出 JSON | 看最终可渲染结构 |
| 错误和 source | 区分 model、cache、manual |

## 3. 本次项目中开发台解决的问题

### 3.1 目标菜识别跑偏

用户端看到：

```text
待确认目标菜：模型结果
```

开发台能看到：

```text
targetVision.dishName 是否真的返回了具体菜名
source 是 model 还是 cache
前端是否拿错字段
```

### 3.2 用户文字没有优先

用户把回锅肉改成鱼香肉丝后，结果仍按回锅肉判断。

开发台检查：

```text
planningInput.targetDishText 到底是什么
targetVision 是否仍覆盖用户输入
服务端 prompt 是否强调用户文字优先
```

### 3.3 模型把菜名当食材

结果出现：

```text
做鱼香肉丝少不了鱼香肉丝
```

开发台能帮助确认：

```text
planningInput 里缺少常识拆解
模型没有把菜名映射到常见主料
fallback knowledge 是否命中
```

### 3.4 等待状态卡住

用户端只看到：

```text
正在判断这顿能不能做
```

开发台和服务端日志应该能区分：

```text
请求是否发出
模型是否超时
缓存是否命中
前端是否等待错误 promise
```

## 4. 开发检验台设计原则

### 4.1 开发台可以丑，但必须清楚

用户端追求美观，开发台追求真实。

开发台应该优先：

```text
字段完整
复制方便
错误清楚
状态分段
按钮可单独触发
```

### 4.2 每个 Agent 可以单独调用

不要只有“一键跑全链路”。

需要支持：

```text
只调用视觉识别
只调用目标菜识别
只调用晚餐规划
加载上次识别
复制当前 JSON
手动改输入后重跑
```

这能快速定位是哪一步坏了。

### 4.3 用户端隐藏，开发台展开

同一个字段，在不同页面处理不同：

| 字段 | 用户端 | 开发台 |
|---|---|---|
| model | 不展示 | 展示 |
| provider | 不展示 | 展示 |
| confidence | 少展示或不展示 | 展示 |
| raw JSON | 不展示 | 展示 |
| source | 不展示 | 展示 |
| modelError | 用户化提示 | 原始错误 |
| cache path | 不展示 | 展示或摘要 |

### 4.4 开发台也是演示素材

技术评委问“这是不是写死的”时，不要口头辩解，直接打开开发台。

讲法：

```text
刚才是用户端。这里是开发检验台，可以看到每一步 Agent 的结构化输入输出。
识别结果先变成候选项，用户确认后才进入规划。
如果模型超时，这里会显示 source，不会把缓存伪装成实时模型。
```

## 5. 开发台字段模板

### 5.1 服务健康

```json
{
  "ok": true,
  "provider": "xxx",
  "model": "xxx",
  "hasApiKey": true,
  "cacheEnabled": true
}
```

### 5.2 Agent 返回包装

```json
{
  "provider": "xxx",
  "model": "xxx",
  "agent": "xxx",
  "source": "model",
  "modelError": null,
  "result": {}
}
```

### 5.3 调试事件

```json
{
  "stage": "target-dish-planning",
  "startedAt": "2026-05-24T10:00:00.000Z",
  "elapsedMs": 5230,
  "inputSummary": {},
  "outputSummary": {},
  "error": null
}
```

## 6. 调试方法

遇到 Agent 结果异常，按这个顺序排查：

```text
1. 原始输入是否正确？
2. 图片 / 文本是否传到服务端？
3. 模型原始返回是否合理？
4. JSON schema 是否解析成功？
5. 归一化是否改坏字段？
6. 用户确认后的状态是否正确？
7. 规划输入是否使用确认状态？
8. Prompt 是否给了错误优先级？
9. fallback 是否误命中？
10. 前端渲染是否拿错字段？
```

这比直接改 prompt 更稳。

## 7. 新项目开发台清单

每个新 Agent 项目都建议在第一天创建：

```text
/dev.html 或 /debug
健康检查按钮
每个 Agent 单独调用按钮
原始输入预览
原始 JSON 展示
复制 JSON 按钮
加载上次成功结果
source / error 展示
```

开发台完成标准：

> 不看服务端代码，只看开发台，也能解释这条 Agent 链路怎么跑。
