# 路演提交与现场作战清单

这份文档用于比赛最后一天和现场展示。它把“要交什么、要怎么讲、要怎么防止翻车”集中在一起。

## 1. 最后一天优先级

最后一天不要再追求功能完整，而要追求：

```text
主路径稳定
讲解顺畅
材料齐全
兜底可靠
```

优先级排序：

1. 用户端主路径能跑通。
2. 开发检验台能证明链路。
3. 备用录屏能播放。
4. 作品说明和讲稿能对齐评分点。
5. GitHub 没有密钥和本地隐私数据。
6. UI 小问题只修影响理解的部分。
7. 实验功能不稳定就降级。

## 2. 提交材料清单

通用比赛材料：

```text
作品名称
一句话介绍
作品说明文档
项目代码仓库
可运行 Demo 或录屏
海报 / 封面图
路演讲稿
团队信息
```

每项要检查：

| 材料 | 检查点 |
|---|---|
| 作品说明 | 用户价值、AI 能力、技术实现、风险兜底 |
| GitHub | README、启动命令、无密钥、无隐私数据 |
| 录屏 | 主路径完整、无等待过长、无错误栈 |
| 海报 | 一句话能看懂、二维码可扫 |
| 讲稿 | 先讲场景，再讲 Demo，再讲技术 |
| Demo | 网络差时也能展示 |

## 3. 现场启动清单

到现场先做：

```text
1. 接电源。
2. 连网络。
3. 打开终端。
4. 启动后端服务。
5. 启动展示端。
6. 打开用户端 URL。
7. 打开开发检验台 URL。
8. 测一次主路径。
9. 打开备用录屏。
10. 关闭可能弹通知的软件。
```

本项目启动例子：

```bash
PORT=4174 npm run dev
npm run showcase
```

然后打开：

```text
http://localhost:5173/
http://localhost:4174/dev.html
```

## 4. 端口占用处理

常见问题：

```text
Error: listen EADDRINUSE
```

处理：

```bash
pgrep -af "node demo/server.mjs"
kill <PID>
```

或换端口：

```bash
PORT=4175 npm run dev
```

注意同步前端代理地址或环境变量。

## 5. 路演讲解顺序

推荐 3 分钟结构：

```text
0:00-0:20 场景痛点
0:20-1:20 用户端 Demo
1:20-2:00 AI 链路和关键设计
2:00-2:30 开发检验台证明
2:30-2:50 生态闭环和商业可能
2:50-3:00 总结一句话
```

不要上来讲：

```text
我们用了什么模型、什么框架、什么接口。
```

要先讲：

```text
谁在什么情况下卡住了。
```

## 6. 现场问答准备

### 6.1 这和 ChatGPT 有什么不同？

回答模板：

```text
ChatGPT 通常从用户文字问题开始。
我们这个项目从真实场景输入开始，比如冰箱照片，再经过用户确认、结构化规划和行动入口。
重点不是聊天，而是把视觉输入变成可执行决策。
```

### 6.2 怎么证明不是写死？

```text
可以看开发检验台。
这里展示每一步 Agent 的原始输入输出、用户确认后的中间状态、规划请求和 source 字段。
模型成功、模型超时缓存、模型错误缓存都会区分。
```

### 6.3 模型识别错怎么办？

```text
识别结果不会直接作为事实进入规划，而是先给用户确认。
用户可以取消错误项，也可以手动修改目标菜文本。
这是我们有意保留的人机协作环节。
```

### 6.4 为什么不上完整 Agent 框架？

```text
当前 MVP 的关键是稳定闭环和清楚的数据合约。
我们用轻量 Agent 函数和结构化 JSON，把视觉识别、用户确认和规划分开。
后续如果需要多轮工具调用、状态回滚或复杂任务编排，可以迁移到 LangGraph 或 Agents SDK。
```

### 6.5 商业化在哪里？

```text
商业入口不硬推，而是在用户缺材料或需要下一步行动时出现。
比如想做黄焖鸡但缺鸡腿肉和土豆，就可以顺手加入模拟购物车。
做完后再接生活记录和内容发布，形成内容种草到现实行动再回到内容的闭环。
```

## 7. 现场演示风险预案

| 风险 | 预案 |
|---|---|
| 网络差 | 用缓存样例和备用录屏 |
| 模型慢 | 展示等待状态，必要时加载缓存 |
| 图片识别错 | 演示用户确认和手动修改 |
| 页面报错 | 切备用录屏，同时打开开发台解释 |
| 端口冲突 | 查 PID 或换端口 |
| 时间不够 | 只讲用户端主路径，不展开技术细节 |
| 评委追问技术 | 打开开发检验台 |

## 8. GitHub 上传前检查

```text
1. git status 看清楚改动。
2. 确认 `.env.local` 没被提交。
3. 确认 data/local-users、data/local-cache 不提交。
4. npm run check 通过。
5. README 或文档有启动命令。
6. 提交信息清楚。
7. push 到正确分支。
```

推荐命令：

```bash
npm run check
npm run push -- "提交信息"
```

## 9. 现场心态

比赛现场讲解不要追求把所有功能讲完。

目标是让对方记住三件事：

```text
这个问题真实。
这个 Agent 能帮上忙。
这个系统不是写死的。
```

如果时间只剩 30 秒，就讲：

```text
用户痛点
主路径结果
一句价值闭环
```

如果时间多，再讲技术。
