# AI Agent 情景化 Demo 展示工作流

这份文档是一套可长期复用的 AI Agent 项目展示方法论。

它的目标不是只服务某一个比赛 Demo，而是帮助后续任何 Agent 项目从“功能能跑”升级成“别人看得懂、记得住、愿意相信”的完整展示。

核心观点：

> 功能 Demo 说明“能用”，情景 Demo 说明“为什么值得用”，开发检验台说明“不是写死的”。

很多 AI 项目失败不在能力本身，而在展示方式：开发者从接口、模型、参数和按钮开始讲，观众却还不知道这个产品解决了谁的什么问题。情景化 Demo 的任务，就是先把观众带进一个真实场景，再让产品自然出现，最后用用户的行动和情绪证明价值。

## 0. 快速复用方式

以后做任何 Agent 项目，如果时间很紧，可以先按这一节执行。后面的章节是展开解释。

### 0.1 最小可用流程

15 分钟内先写清楚五件事：

```text
1. 目标用户是谁？
2. 他在什么具体场景里卡住？
3. Agent 让他少做了什么？
4. Agent 背后多判断了什么？
5. 用户最后在现实里完成了什么？
```

再把答案压成一句话：

```text
当 [用户] 在 [场景] 遇到 [痛点] 时，
这个 Agent 通过 [AI 能力]，
帮助用户完成 [现实结果]。
```

如果这句话写不顺，说明项目还没有进入可展示状态，应该先收窄场景，而不是先做视频。

### 0.2 一小时准备法

如果只有 1 小时准备展示材料，按这个顺序：

| 时间 | 动作 | 产物 |
|---:|---|---|
| 10 分钟 | 写一句话价值和用户困境 | 项目开场 |
| 10 分钟 | 填六段式用户故事 | 演示主线 |
| 15 分钟 | 录一遍用户端主流程 | 真实操作素材 |
| 10 分钟 | 截开发检验台关键状态 | 可信证明素材 |
| 10 分钟 | 写 30 秒旁白 | 路演讲稿 |
| 5 分钟 | 检查风险和兜底 | 现场预案 |

不要一上来改 UI、换配色、堆技术架构图。先把“为什么值得看”讲顺。

### 0.3 半天打磨法

如果有半天时间，推荐准备四个版本：

| 产物 | 用途 | 内容 |
|---|---|---|
| 30 秒情景视频 | 开场吸引注意 | 痛点、产品出现、结果 |
| 60 秒用户端录屏 | 证明能真实操作 | 主路径完整跑通 |
| 90 秒技术讲解 | 回答技术评委 | Agent 分工、数据流、兜底 |
| 1 页叙事卡 | 队友统一口径 | 用户、场景、能力、结果、风险 |

这四个产物不是互相替代，而是面向不同观众。

### 0.4 标准材料目录

以后新项目可以直接复制这个目录结构：

```text
docs/demo/
  Demo叙事卡.md
  用户端演示讲稿.md
  开发检验台讲稿.md
  情景视频脚本.md
  现场风险预案.md

assets/demo/
  screenshots/
  screen-recordings/
  generated-video/
  poster/
  sample-inputs/
  sample-outputs/

data/demo-cache/
  README.md
  sample-success.json
  sample-timeout-fallback.json
```

每个项目不一定都要完整建立这些文件，但这个结构能提醒团队：展示不是只有代码，还需要故事、素材、兜底和统一口径。

### 0.5 展示顺序铁律

推荐顺序：

```text
先讲人
再讲事
再讲产品
再讲 AI
最后讲工程可信度
```

常见错误顺序：

```text
先讲模型
再讲接口
再讲页面
最后才说用户
```

第二种顺序会让观众觉得这是“技术作业”；第一种顺序更像“真实产品”。

## 1. 适用场景

这套方法适用于：

- AI Agent 比赛路演
- 课程项目汇报
- 产品原型评审
- 作品集展示
- 创业项目 Demo Day
- GitHub / README 项目介绍
- 短视频平台上的产品概念展示
- 面试或实习作品讲解

尤其适合具有以下特征的项目：

- 有一个明确用户场景
- 有多个 Agent 或多个处理阶段
- 有上传、识别、规划、生成、工具调用等链路
- 有用户画像、长期记忆、缓存兜底、结构化 JSON 等后台能力
- 用户端很简洁，但背后逻辑相对复杂
- 需要让非技术观众也能快速理解价值

不适合只用这套方法的情况：

- 纯算法 Benchmark
- 只展示底层模型性能
- 没有明确用户场景的底层 SDK
- 完全内部工具且观众只关心接口吞吐或成本

即便如此，也可以借用其中的“痛点 -> 操作 -> 结果 -> 可信证明”结构。

## 2. 展示的三个层次

一个成熟的 AI Agent Demo 通常应该准备三层展示材料。

| 层次 | 面向谁 | 解决什么问题 | 展示内容 | 不适合展示 |
|---|---|---|---|---|
| 情景视频 | 所有人，尤其是非技术观众 | 为什么需要这个产品 | 用户痛点、产品介入、情绪变化、现实结果 | JSON、模型名、接口细节 |
| 用户端 Demo | 评委、老师、用户、产品同学 | 这个产品能不能真实操作 | 上传、确认、输入、点击、结果页、行动 CTA | 太多调试信息、错误栈、内部字段 |
| 开发检验台 | 技术评委、开发者、需要可信证明的人 | 这是不是写死的、工程上是否可靠 | Agent 分工、结构化输入输出、用户画像、缓存、日志、安全边界 | 一上来就展示给所有人 |

推荐顺序：

```text
情景视频或一句话开场
-> 用户端 Demo
-> 开发检验台 / 后台解释
-> 总结价值闭环
```

不要反过来。

如果先展示后台 JSON，非技术观众会失去产品感；如果只展示用户端，技术评委可能怀疑是写死页面；如果只有视频，观众会怀疑没有真实系统。三层展示互相补足。

## 3. 一句话价值模板

所有展示都应该从一句话价值开始。

模板：

```text
当 [目标用户] 在 [具体场景] 遇到 [痛点] 时，
这个 Agent 通过 [核心 AI 能力]，
帮助用户完成 [现实结果]。
```

例子：厨房小助手

```text
当学生晚上打开冰箱却不知道吃什么时，
厨房小助手通过冰箱视觉识别、库存确认和晚餐规划，
帮助他做出一顿现实可执行的饭。
```

例子：简历 Agent

```text
当求职学生不知道如何包装项目经历时，
简历 Agent 通过经历提取、岗位匹配和亮点改写，
帮助他生成一份更适合投递的简历。
```

例子：论文阅读 Agent

```text
当研究生面对一篇陌生论文不知道从哪里读起时，
论文阅读 Agent 通过结构解析、概念解释和相关工作梳理，
帮助他快速建立论文理解框架。
```

例子：财务报销 Agent

```text
当员工面对一堆票据和繁琐报销规则时，
报销 Agent 通过票据识别、规则校验和表单自动填写，
帮助他一次性提交合规报销材料。
```

写这句话时要避免：

- 只写技术，不写用户
- 只写“提升效率”，不写具体动作
- 场景太泛，例如“帮助用户更好生活”
- 结果太虚，例如“获得智能体验”

更好的表达要有真实动作：

```text
拍冰箱
上传简历
读论文
整理票据
生成邮件
规划路线
提交申请
```

## 4. 六段式用户故事结构

情景化 Demo 的核心是六段式用户故事。

```text
用户困境
-> 产品出现
-> 核心操作
-> AI 判断
-> 现实行动
-> 情绪回报
```

### 4.1 用户困境

目的：让观众在 5 到 10 秒内共情。

要回答：

- 用户是谁？
- 他在哪个具体场景里？
- 他卡在什么地方？
- 这个问题是不是日常、真实、有画面？

不要直接说：

```text
用户需要一个多模态智能助手。
```

要展示：

```text
一个人打开冰箱，看着零散食材发愁。
```

常见困境类型：

| 类型 | 示例 |
|---|---|
| 选择困难 | 冰箱里有东西但不知道吃什么 |
| 信息过载 | 搜到一堆资料但不知道重点 |
| 表达困难 | 有经历但不会写简历 |
| 流程繁琐 | 报销、申请、填表、整理材料 |
| 不确定风险 | 不知道某个方案是否可行 |
| 时间压力 | 只剩 20 分钟但要做决定 |
| 能力不足 | 新手不会做复杂任务 |

### 4.2 产品出现

目的：让解决方案自然登场。

产品不要像广告硬插入，而要像用户在困境中找到一个可用工具。

例子：

```text
用户打开手机，进入“厨房小助手”，看到“上传冰箱照片”。
```

讲解句式：

```text
这时候，他不需要先想好菜名，也不用手动列清单，只需要让 AI 先看一眼当前场景。
```

### 4.3 核心操作

目的：说明用户成本低。

只展示最关键的 1 到 3 个动作，不要把所有配置项都演一遍。

厨房小助手：

```text
上传冰箱
确认食材
输入或上传想吃的菜
```

简历 Agent：

```text
上传简历
选择目标岗位
点击生成优化建议
```

论文 Agent：

```text
上传论文
选择阅读目标
查看结构化解读
```

核心原则：

> 用户操作越少，AI 判断越多，Agent 感越强。

但也要保留必要的用户确认，尤其是多模态识别、健康、法律、金融、个人偏好等高风险或高不确定场景。

### 4.4 AI 判断

目的：展示这个系统不是普通表单，也不是简单 Chatbot。

要回答：

- AI 看到了什么？
- AI 结合了哪些约束？
- AI 做了什么判断？
- AI 有没有承认不确定性？
- AI 有没有把结果变成下一步行动？

厨房小助手：

```text
识别冰箱食材
确认用户时间和厨艺
判断目标菜家里够不够做
给出今晚现实路线
```

AI 判断不要只展示 loading。

可以用卡片或动效表达：

```text
可用食材：番茄、鸡蛋、面条
时间约束：25 分钟
用户状态：新手、少洗锅
目标菜：黄焖鸡
判断：缺鸡腿肉和土豆，今晚不适合硬做完整版
```

### 4.5 现实行动

目的：证明 AI 输出能落地。

很多 AI Demo 停在“生成文本”，但真正有说服力的是用户按结果做了什么。

厨房小助手：

```text
用户按步骤下锅做饭。
```

简历 Agent：

```text
用户复制优化后的项目经历，生成投递版本。
```

论文 Agent：

```text
用户按导读顺序阅读方法、实验和贡献点。
```

报销 Agent：

```text
用户检查自动填好的表单并提交。
```

### 4.6 情绪回报

目的：留下记忆点。

用户最终应该从一种情绪变成另一种情绪。

| 开始 | 结束 |
|---|---|
| 困惑 | 清楚 |
| 焦虑 | 放松 |
| 犹豫 | 确定 |
| 繁琐 | 省事 |
| 没思路 | 有方向 |
| 不敢做 | 敢开始 |

厨房小助手：

```text
用户端着热饭笑了。
字幕：从刷到想吃，到真的吃上。
```

情绪回报是视频最容易被记住的部分，不要省略。

## 5. 视频制作标准流程

建议每个 Agent 项目都按以下步骤制作情景化视频。

### Step 1：确定一句话价值

先写出：

```text
当 [用户] 在 [场景] 遇到 [痛点] 时，
这个 Agent 通过 [AI 能力]，
帮助用户完成 [现实结果]。
```

这句话没写清楚，不要急着做视频。

### Step 2：填写六段式故事

使用这个表：

| 段落 | 画面 | 用户动作 | AI 动作 | 字幕 |
|---|---|---|---|---|
| 用户困境 |  |  |  |  |
| 产品出现 |  |  |  |  |
| 核心操作 |  |  |  |  |
| AI 判断 |  |  |  |  |
| 现实行动 |  |  |  |  |
| 情绪回报 |  |  |  |  |

### Step 3：区分素材类型

不要把所有画面都交给文生视频。

推荐分工：

| 素材类型 | 适合内容 | 不适合内容 |
|---|---|---|
| 文生视频 | 生活场景、人物情绪、现实行动 | 精确 UI、复杂文字、真实按钮 |
| 真实录屏 | 产品界面、操作流程、结果页 | 生活场景、人物情绪 |
| 截图动效 | AI 判断过程、关键词高亮、流程箭头 | 长时间真实操作 |
| 实拍 | 最终成果、人物使用、环境真实感 | 没有条件时可被文生视频替代 |

最佳组合：

```text
生活镜头：文生视频或实拍
产品界面：真实录屏
AI 思考：截图 + 卡片动效
最终结果：文生视频或实拍
```

### Step 4：生成生活场景镜头

文生视频提示词结构：

```text
[人物] 在 [具体场景] 中遇到 [问题]，
正在 [动作]，
情绪是 [情绪]，
画面风格是 [真实 / 温暖 / 电影感 / 产品广告]，
镜头是 [近景 / 中景 / 手持 / 俯拍]，
时长 [秒数]。
```

英文模板：

```text
A [target user] in [specific environment], struggling with [problem], performing [action], showing [emotion], realistic cinematic product demo style, warm lighting, [shot type], [duration] seconds.
```

中文模板：

```text
[具体时间和地点]，[目标用户] 正在 [动作]，因为 [痛点] 感到 [情绪]，真实生活感，暖色灯光，电影感，[镜头类型]，[秒数] 秒。
```

### Step 5：录制真实产品界面

录屏建议：

- 使用固定窗口尺寸，例如手机比例 390 x 844 或桌面 1440 x 900
- 鼠标动作慢一点
- 不要让 loading 占满太久，剪辑时保留 0.5 到 1 秒即可
- 不展示真实 API Key
- 不展示用户隐私数据
- 不展示内部错误栈
- 只录用户看得懂的关键路径

厨房小助手的录屏片段：

```text
上传冰箱
食材识别出现
确认库存
上传目标菜图
识别菜名并填入文本框
用户补充“只有 25 分钟”
结果页出现“还差哪些材料”
购物车 CTA
饭后记录 CTA
```

### Step 6：剪辑合成

推荐时长：

| 用途 | 时长 |
|---|---:|
| 比赛现场开场 | 30 到 45 秒 |
| 课程汇报 | 45 到 60 秒 |
| 项目作品集 | 60 到 90 秒 |
| 产品路演详细版 | 90 到 120 秒 |

推荐节奏：

```text
痛点：5-8 秒
产品出现：4-6 秒
核心操作：10-18 秒
AI 判断：8-15 秒
现实行动：6-12 秒
情绪回报：4-8 秒
```

### Step 7：加字幕和旁白

字幕原则：

> 字幕说人话，不说模块名。

替换表：

| 不推荐 | 推荐 |
|---|---|
| 多模态视觉识别模块 | 先看看图里有什么 |
| 目标菜复刻路径规划 | 想吃这道菜，家里够不够做 |
| 用户画像驱动个性化推荐 | 按你的时间和习惯来推荐 |
| 结构化 JSON 输出 | 每一步都有清楚的中间结果 |
| 缺失关键依赖项 | 家里还差几样材料 |
| Agent 工具调用链路 | AI 分步骤帮你判断 |
| RAG 知识库增强 | 先查可靠资料，再给答案 |
| Workflow Orchestration | 把复杂流程拆成几步自动完成 |

旁白原则：

- 少讲“模型很强”
- 多讲“用户少做了什么”
- 少讲“我们用了什么技术”
- 多讲“它为什么更稳”
- 少讲“智能化赋能”
- 多讲“现在知道下一步怎么做”

### Step 8：导出多个版本

建议每个项目准备三个版本：

| 版本 | 用途 | 特点 |
|---|---|---|
| 30 秒版 | 开场、短视频、朋友圈 | 强痛点、强结果、少细节 |
| 60 秒版 | 比赛、课程汇报 | 完整流程、一个核心案例 |
| 120 秒版 | 路演、作品集 | 加后台解释、技术可信证明 |

## 6. 用户端 Demo 讲解流程

用户端 Demo 的目标是证明产品可以真实操作。

讲解顺序：

```text
先讲场景
-> 再操作
-> 再解释 AI 判断
-> 最后回扣用户收益
```

不要一边点一边念按钮名。

不推荐：

```text
这里点击上传，这里点击下一步，这里点击生成。
```

推荐：

```text
真实用户不会愿意手动列一堆条件，所以第一步只让他拍照。
视觉识别可能不准，所以第二步让用户确认库存。
确认后的库存才进入规划，这样既保留 AI 的方便，也保留人的判断。
```

用户端讲解模板：

```text
这个页面是给普通用户看的，所以我们刻意隐藏了模型名、JSON、内部画像和错误栈。
用户只需要完成几个动作：[动作 1]、[动作 2]、[动作 3]。
系统背后会完成：[AI 判断 1]、[AI 判断 2]、[AI 判断 3]。
最后给用户的不是一段泛泛建议，而是 [可执行结果]。
```

## 7. 开发检验台讲解流程

开发检验台不是给普通用户看的，而是给评委、老师和技术同学证明系统可信。

它应该展示：

- 每个 Agent 的输入
- 每个 Agent 的输出
- 用户确认后的中间状态
- 缓存和模型来源
- 用户画像或长期记忆
- 错误和兜底路径
- 安全边界

讲解时不要逐字段解释，只讲系统设计考虑。

推荐话术：

```text
刚才看到的是用户端。为了证明这不是写死页面，我们准备了开发检验台。
这里可以看到每一步 Agent 的结构化输入输出。
视觉识别只负责候选食材，用户确认后的库存才进入规划。
目标菜图片识别只负责猜菜名和关键材料，用户确认后的文字优先级最高。
如果模型超时，我们会用演示缓存兜底，但开发台会明确标注 source，用户端不会伪装成模型实时结果。
```

开发检验台常见展示点：

| 展示点 | 说明什么 |
|---|---|
| 服务健康状态 | 当前模型、provider、API Key 是否可用 |
| 原始图片预览 | 输入确实来自用户上传 |
| 视觉识别 JSON | 模型输出是结构化的 |
| 归一化库存 | 模型结果进入业务状态前被整理 |
| 人工确认库存 | 多模态不确定性由用户校正 |
| 规划请求 JSON | 后续 Agent 使用的是确认后的输入 |
| 规划结果 JSON | 输出可解析、可渲染、可兜底 |
| 用户画像 traits | 个性化依据可解释 |
| cache source | 稳定性策略透明 |

## 15. 常见错误

### 错误 1：从技术开始讲

不推荐：

```text
我们用了多模态模型、结构化 JSON、用户画像和缓存机制。
```

推荐：

```text
用户打开冰箱不知道吃什么，我们先让 AI 看一眼冰箱，再帮他判断今晚怎么吃最现实。
```

技术要放在用户理解产品之后。

### 错误 2：视频里只有 UI，没有人

只有 UI 录屏容易变成操作说明，不容易产生记忆点。

至少要补一个用户困境镜头和一个结果情绪镜头。

### 错误 3：视频里 UI 全靠文生视频生成

文生视频容易生成错误文字、错误按钮和不真实布局。

真实产品界面尽量用截图或录屏。

### 错误 4：后台讲太久

后台是可信证明，不是主角。

讲三个点就够：

```text
Agent 分工
结构化中间结果
稳定性和兜底
```

### 错误 5：没有兜底

现场 Demo 最怕模型慢、网络坏、图片识别错。

必须准备：

```text
演示样例
缓存结果
备用录屏
开发检验台
清晰错误提示
```

## 16. 不同观众的讲解重心

同一个 Agent 项目，面对不同观众要换讲法。不是改事实，而是改变信息顺序。

| 观众 | 最关心 | 应该先讲 | 少讲或后讲 |
|---|---|---|---|
| 普通用户 | 这和我有什么关系 | 场景、痛点、结果 | 模型名、接口、JSON |
| 产品同学 | 这个需求是否真实 | 用户路径、转化节点、复用场景 | 底层调用细节 |
| 技术评委 | 是否真实可运行 | Agent 分工、数据流、失败兜底 | 纯宣传视频 |
| 比赛评委 | 是否对齐评分点 | AI 不可替代性、完成度、创新点、稳定性 | 无关扩展规划 |
| 投资或创业观众 | 是否有商业闭环 | 用户频次、入口、交易或留存闭环 | 过细工程实现 |
| 队友或开发者 | 下一步怎么做 | 模块边界、接口契约、风险列表 | 情绪化宣传语 |

推荐讲解顺序：

```text
普通用户：痛点 -> 产品操作 -> 结果
技术评委：痛点 -> 产品操作 -> 开发检验台 -> 架构边界
产品评审：痛点 -> 用户路径 -> 关键指标 -> 后续路线
路演比赛：痛点 -> Demo -> AI 能力 -> 商业/生态闭环 -> 兜底稳定性
```

一个实用判断：

> 如果对方不是工程师，前三十秒不要出现模型名。

如果对方是工程师，前三十秒也不要只讲模型名。先让他知道系统解决的真实问题，再展示工程可信度。

## 17. 当前项目讲解安排：厨房小助手

本节专门记录当前“厨房小助手”的现场讲解方式，后续可迁移到其他 Agent 项目。

### 17.1 两个页面的分工

当前有两个主要入口：

```text
用户端展示页：http://localhost:5173/
开发检验台：http://localhost:4174/dev.html
```

讲解定位：

| 页面 | 给谁看 | 讲什么 | 不讲什么 |
|---|---|---|---|
| 用户端展示页 | 评委、游客、非技术观众 | 普通用户怎么完成一顿饭决策 | provider、模型名、JSON、缓存路径 |
| 开发检验台 | 技术评委、老师、队友 | 链路不是写死的，每步有输入输出 | 不当作第一屏主体验 |

推荐说法：

```text
主页面是给普通用户看的，所以它只保留三步：拍冰箱、确认食材、得到今晚方案。
但我们也准备了开发检验台，用来展示背后的 Agent 链路：视觉识别、用户确认、目标菜识别、规划输入、规划输出和缓存来源。
```

### 17.2 2 分钟现场讲解脚本

```text
我们做的是一个厨房小助手。
它解决的不是“给我一份菜谱”，而是晚上打开冰箱时那个更真实的问题：家里有一些东西，但不知道今晚到底吃什么，或者刷到一道菜以后不知道家里够不够做。

用户端只有三步。
第一步拍一下冰箱，让 AI 先识别可用食材。
第二步用户自己确认库存，因为图片识别可能有遮挡，也不能替用户判断食材新不新鲜。
第三步可以选择“帮我决定吃什么”，也可以上传一道想吃的菜，比如黄焖鸡，系统会先识别菜名，再允许用户修改文字，最后判断家里还差什么、今晚怎么做最现实。

结果页不是简单菜谱，而是行动路线：已有食材、还差哪些材料、先做什么、难点是什么。
如果缺关键材料，我们展示一个“加入购物车，去抖音商城”的模拟入口；做完饭后，也有“拍成品，发抖音”的生活记录入口。

为了证明这不是写死页面，我们还有开发检验台。
这里能看到每一步 Agent 的原始输入输出，以及用户确认后的库存如何进入规划。
如果模型超时，系统会使用演示缓存兜底，但开发台会明确标注 source，不会把缓存伪装成实时模型结果。
```

### 17.3 30 秒游园版讲法

```text
这是厨房小助手：拍一下冰箱，它先识别家里有什么，再让你确认哪些能用。
如果你刷到一道想吃的菜，也能上传菜图，它会判断家里够不够做，还差什么，今晚怎么吃最现实。
缺材料可以接到抖音商城，做完还能生成生活记录。
我们重点做的是“内容种草 -> 冰箱判断 -> 补齐材料 -> 做完记录”的闭环。
```

### 17.4 技术评委追问时的答法

如果被问“怎么证明不是写死的”：

```text
可以打开开发检验台看每一步输入输出。
上传图片后，视觉 Agent 返回结构化 JSON；用户勾选后的库存会重新组成规划请求；目标菜图只负责识别候选菜名，最终以用户确认的文字为准；规划 Agent 再根据库存、目标菜和用户画像生成方案。
```

如果被问“模型慢怎么办”：

```text
等待状态会显示阶段和已用秒数。
超过阈值后可以走演示缓存兜底。开发台会标 source，区分 model、model-timeout-cache 和 model-error-cache，现场稳定性和真实性都保留。
```

如果被问“为什么要用户确认库存”：

```text
因为冰箱照片天然有遮挡、反光、包装、变质和剩菜安全问题。
AI 可以降低录入成本，但不能替用户确认食材是否真的可用。
所以我们把多模态识别结果变成候选项，再让用户确认，这样更接近真实产品。
```

如果被问“和普通菜谱生成有什么不同”：

```text
普通菜谱是假设食材齐全。
我们的链路是从现实库存出发，先判断条件够不够，再决定照着做、简化做、补买后做，还是换成更现实的一餐。
```

### 17.5 当前项目的三条演示路线

| 路线 | 适合场合 | 操作 | 强调点 |
|---|---|---|---|
| 不知道吃啥 | 普通观众 | 上传冰箱 -> 确认库存 -> 帮我决定 | 从库存到晚餐方案 |
| 刷到想吃的 | 抖音场景 | 上传冰箱 -> 上传目标菜 -> 修改文字 -> 生成方案 | 内容种草和现实库存连接 |
| 技术可信证明 | 技术评委 | 打开开发检验台 -> 看原始 JSON 和 source | 不是写死，有兜底和边界 |

推荐现场顺序：

```text
先讲“刷到想吃的”路线，因为它最贴近抖音。
再补一句“不知道吃啥”也能做。
最后打开开发检验台证明链路。
```

## 18. AI Agent 可信证明四件套

AI Agent Demo 最容易被质疑两件事：

```text
是不是写死的？
是不是只是 ChatGPT 套壳？
```

为了回答这两个问题，每个 Agent 项目最好准备四件套。

### 18.1 真实输入

展示用户上传、输入或选择的原始材料。

例子：

```text
冰箱照片
目标菜图片
简历 PDF
课程大纲
发票照片
合同原文
```

要避免：

```text
页面一打开就直接出现完美结果，但看不到输入从哪里来。
```

### 18.2 中间状态

Agent 不要像黑箱一样直接吐最终答案。要能展示中间状态：

```text
识别到了什么
哪些不确定
用户确认了什么
下一步用了哪些输入
```

中间状态越清楚，观众越相信系统不是硬编。

### 18.3 结构化契约

后台应该有稳定的数据结构，而不是靠大段自然语言拼接页面。

可展示内容：

```text
JSON schema
Agent 输入字段
Agent 输出字段
错误字段
source 字段
cache 字段
```

讲解时不需要把 schema 念完，只需要说明：

```text
每一步输出都是结构化的，所以前端可以稳定渲染，也方便失败时兜底。
```

### 18.4 失败兜底

成熟 Demo 不是永远成功，而是失败时有边界。

至少准备：

```text
模型超时提示
缓存兜底
用户手动修改入口
错误类型提示
备用录屏
```

讲解重点：

```text
我们不把 AI 的不确定性藏起来，而是把它变成用户可确认、系统可兜底的流程。
```

## 19. 通用讲稿模板

### 19.1 30 秒版

适合游园、海报前、短视频简介。

```text
我们做的是 [项目名]。
它解决的是 [目标用户] 在 [具体场景] 里的 [痛点]。
用户只需要 [1-2 个动作]，Agent 会自动完成 [核心 AI 判断]。
最后给到的不是一段泛泛建议，而是 [现实可执行结果]。
这个项目的关键闭环是：[输入] -> [判断] -> [行动] -> [回流/复用]。
```

厨房小助手填充版：

```text
我们做的是厨房小助手。
它解决的是学生晚上打开冰箱，不知道今晚吃什么，或者刷到一道菜不知道家里够不够做的问题。
用户只需要拍冰箱、确认食材，也可以上传想吃的菜图，Agent 会判断已有食材、缺失材料和今晚最现实的做法。
最后给到的不是泛泛菜谱，而是一条能照着做的晚餐路线。
这个项目的关键闭环是：内容种草 -> 冰箱判断 -> 补齐材料 -> 做完记录。
```

### 19.2 60 秒版

适合比赛主讲。

```text
我们观察到 [场景痛点]。
传统做法是 [低效方式]，问题在于 [为什么低效]。

所以我们做了 [项目名]。
它的用户端刻意保持简单：[用户动作 1]、[用户动作 2]、[用户动作 3]。
背后 Agent 会完成 [AI 判断 1]、[AI 判断 2]、[AI 判断 3]。

这里最关键的设计是 [关键设计]。
因为 [现实原因]，所以我们没有让 AI 直接替用户决定，而是 [人机协作方式]。

最后结果会变成 [可执行结果]。
如果遇到 [常见失败情况]，系统会 [兜底方式]。
```

### 19.3 3 分钟版

适合评委答辩和项目汇报。

```text
第一段：场景
我们选择 [目标场景]，因为它高频、具体，而且 AI 能在关键判断中产生价值。

第二段：用户流程
普通用户只看到 [页面主流程]。我们隐藏了模型名、JSON 和内部画像，让用户专注在自己的任务上。

第三段：Agent 链路
背后分成 [Agent 1]、[Agent 2]、[Agent 3]。每一步都有结构化输入输出，中间状态可检查。

第四段：产品设计
我们保留 [用户确认/编辑/反馈]，因为 [不确定性或风险]。这让系统更适合真实使用。

第五段：稳定性
模型慢或失败时，我们有 [缓存/错误提示/备用录屏/手动输入]，现场不会空白。

第六段：未来扩展
后续可以扩展到 [更大场景]，但 MVP 先把 [当前闭环] 做稳。
```

## 20. 情景视频制作细化流程

### 20.1 先定“人设”，再定镜头

文生视频最怕生成漂亮但空泛的画面。提示词里应该包含明确人物：

```text
大学生
刚下班的白领
准备面试的应届生
实验室里的研究生
财务报销的员工
第一次租房的年轻人
```

不要只写：

```text
一个用户使用 AI 工具。
```

要写：

```text
一个刚下课回到宿舍的大学生，晚上九点打开冰箱，看着零散食材不知道吃什么。
```

### 20.2 产品 UI 用录屏，不交给文生视频

文生视频适合生成：

```text
用户困境
人物情绪
现实行动
最终成果
```

真实录屏适合展示：

```text
上传
点击
等待
结果页
按钮 CTA
```

不要让文生视频生成复杂 UI，因为它容易把文字、按钮、布局生成错。

### 20.3 画面转场模板

推荐转场：

```text
困境镜头 -> 手机界面
手机界面 -> AI 判断卡片
AI 判断卡片 -> 现实行动
现实行动 -> 最终成果
最终成果 -> 产品 logo 或 slogan
```

每个转场都要回答一个问题：

| 转场 | 观众心理 |
|---|---|
| 困境到产品 | 这个工具为什么出现 |
| 产品到 AI 判断 | 它不只是普通表单 |
| AI 判断到行动 | 输出真的能落地 |
| 行动到成果 | 用户状态发生改变 |

### 20.4 视频不要塞太多功能

一个 45 秒视频只讲一个主路径。

不推荐：

```text
同时讲冰箱识别、目标菜、用户画像、商城、视频发布、语音输入、后台 JSON。
```

推荐：

```text
只讲“刷到黄焖鸡 -> 拍冰箱 -> 判断够不够做 -> 缺材料可补 -> 做完记录”。
```

其他能力放在开发检验台或答辩追问中。

### 20.5 结尾要有可复述句

视频最后一定留一句观众能复述的话。

厨房小助手：

```text
从刷到想吃，到真的吃上。
```

简历 Agent：

```text
从不知道怎么写，到敢投出去。
```

论文 Agent：

```text
从看不懂论文，到知道先读哪里。
```

报销 Agent：

```text
从怕填错，到放心提交。
```

## 21. 新 Agent 项目复用决策树

做新项目时，可以按这个决策树判断该怎么展示。

```text
这个项目有没有具体用户？
  没有 -> 先定义用户，不急着做 Demo
  有 -> 继续

用户有没有一个具体卡住的时刻？
  没有 -> 场景太泛，继续收窄
  有 -> 继续

AI 是否参与关键判断？
  没有 -> 可能只是普通工具，重新找 AI 价值点
  有 -> 继续

最终结果是否能变成现实动作？
  没有 -> 展示会像生成文本，补行动闭环
  有 -> 继续

链路是否有可展示中间状态？
  没有 -> 增加开发检验台或日志
  有 -> 继续

失败时是否有兜底？
  没有 -> 准备缓存、录屏或手动输入
  有 -> 可以进入情景化 Demo 打磨
```

这个决策树的本质：

> 先确认项目有真实任务，再确认 AI 有关键价值，最后确认现场可以稳定证明。

## 22. 素材命名与版本管理

展示材料越到最后越容易混乱，所以建议从第一天就规范命名。

### 22.1 文件命名

```text
YYYYMMDD_项目名_素材类型_版本
```

例子：

```text
20260524_kitchen_user-demo_v1.mov
20260524_kitchen_devbench_screenshot_v1.png
20260524_kitchen_45s_script_v2.md
20260524_kitchen_fallback_recording_final.mov
```

### 22.2 版本含义

| 后缀 | 含义 |
|---|---|
| v1 | 初版，能表达主线 |
| v2 | 修改话术或顺序 |
| final | 比赛/汇报当天使用 |
| backup | 备用录屏或兜底素材 |
| raw | 未剪辑原始素材 |

### 22.3 演示素材清单

每次正式展示前，最好准备：

```text
用户端 URL
开发检验台 URL
3 张稳定输入样例
1 条完整备用录屏
1 份 30 秒讲稿
1 份 3 分钟讲稿
1 张架构图或链路图
1 份风险预案
```

## 23. 完成定义

一个 Agent Demo 可以认为“准备好了”，不是因为功能都做完，而是满足这些条件：

```text
1. 30 秒内能讲清楚用户是谁、痛点是什么。
2. 用户端能在 1 分钟内跑完主路径。
3. 结果页给的是行动路线，不只是大段建议。
4. 至少一个 AI 判断是不可替代的核心环节。
5. 开发检验台能展示关键中间状态。
6. 模型失败时页面不空白。
7. 有备用录屏或缓存样例。
8. 讲稿里有一句观众能记住的结尾。
9. 队友对“先讲什么、后讲什么”口径一致。
10. 敏感信息、API Key、隐私数据不会出现在展示里。
```

如果只满足前 4 条，可以做课程小作业演示。
如果满足前 7 条，可以参加一般比赛。
如果 10 条都满足，才比较适合现场路演和公开展示。

## 24. 最终原则

情景化 Demo 的最终目标不是让观众看到你写了多少功能，而是让观众记住：

```text
谁遇到了什么问题
这个 Agent 如何介入
用户少做了什么
AI 多判断了什么
最后现实中发生了什么变化
```

一句话记忆：

> 先让观众相信问题真实，再让他们看到产品好用，最后证明系统可信。

对于 AI Agent 项目，最理想的展示不是：

```text
这是一个智能系统。
```

而是：

```text
这个人刚才还卡住，现在知道下一步怎么做了。
```
