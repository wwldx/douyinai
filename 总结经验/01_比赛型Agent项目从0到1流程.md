# 比赛型 Agent 项目从 0 到 1 流程

这份文档总结本次比赛从选题、开发、调试、展示到提交的流程。它适合用于黑客松、课程项目、Demo Day、作品集项目等有明确展示期限的 Agent 项目。

## 1. 总原则

比赛型 Agent 项目和长期产品不一样。

长期产品追求完整、稳定、可扩展；比赛项目首先追求：

```text
观众能快速理解
评委能看到 AI 价值
现场能稳定跑通
技术可信但不过度复杂
```

所以优先级应该是：

```text
具体场景 > 大而全功能
完整闭环 > 单点炫技
稳定展示 > 架构漂亮
结构化输出 > 自由发挥
人机协作 > AI 全自动幻觉
```

## 2. 阶段一：选题收敛

### 2.1 从“真实卡点”开始

不要从“我想用多模态 / RAG / Agent / 语音”开始。

先问：

```text
谁？
在什么时候？
面对什么材料？
卡在哪里？
现在怎么解决？
为什么现在的方法麻烦？
AI 能不能做一个关键判断？
```

本次项目的卡点是：

```text
学生晚上打开冰箱，家里有一些东西，但不知道今晚吃什么；
或者刷到一道想吃的菜，不知道家里够不够做。
```

这个卡点好，是因为它：

- 高频。
- 有画面。
- 可现场演示。
- 需要视觉输入。
- 输出能变成现实行动。
- 和抖音内容种草、商城、本地生活、生活记录都有连接。

### 2.2 砍掉泛化冲动

比赛里最危险的想法是：

```text
做一个万能生活助手。
做一个能管理所有饮食健康的 Agent。
做一个完整家庭厨房平台。
```

更好的版本：

```text
今晚这顿饭怎么解决。
这张冰箱图里的东西能不能做这道菜。
这个人只有 25 分钟，做什么最现实。
```

判断是否该砍：

| 问题 | 如果答案是否，就砍 |
|---|---|
| 30 秒内能讲清楚吗 | 不能就收窄 |
| 现场能用一张图片演示吗 | 不能就换路径 |
| AI 是否参与核心判断 | 没有就弱 |
| 输出是否能变成行动 | 不能就像聊天 |
| 失败时是否能兜底 | 不能就别放主流程 |

## 3. 阶段二：定义 MVP 主路径

MVP 主路径不是功能列表，而是一条用户故事。

模板：

```text
用户进入页面
-> 提供一个现实输入
-> AI 做第一步理解
-> 用户确认关键事实
-> AI 做第二步规划
-> 页面给出可执行行动
```

本次项目主路径：

```text
上传冰箱
-> 识别食材
-> 用户确认库存
-> 选择帮我决定 / 我有想吃的
-> 生成今晚方案
-> 缺材料可模拟加入购物车
-> 做完可生成抖音生活记录
```

值得复用的点：

- 用户确认库存是多模态不确定性的缓冲层。
- 目标菜图片识别后先写入文本框，允许用户修改，避免图片误识别直接污染规划。
- 第三步重新规划回到第二步，而不是清空回第一步，符合用户心理。
- 结果页给“已有 / 还差 / 怎么做 / 难点”，而不是只给菜谱。

## 4. 阶段三：设计 Agent 分工

比赛项目不一定要上复杂 Agent 框架。

更重要的是把职责拆清楚：

```text
输入理解 Agent
-> 中间状态归一化
-> 用户确认
-> 规划 Agent
-> 前端渲染
```

本次项目拆法：

| Agent | 职责 | 不做什么 |
|---|---|---|
| 冰箱视觉识别 | 看图识别候选食材和不确定项 | 不直接决定今晚吃什么 |
| 目标菜视觉识别 | 猜目标菜名、关键材料、难度 | 不覆盖用户手动文字 |
| 晚餐规划 | 根据确认库存和用户状态生成方案 | 不假装能判断食材新鲜度 |
| 目标菜规划 | 判断家里够不够照着做、还差什么 | 不给可做指数，不硬凑 |

可复用原则：

```text
让每个 Agent 只做一类判断。
跨 Agent 的状态要结构化。
模型结果进入下一步前，尽量有归一化或用户确认。
```

## 5. 阶段四：同步做开发检验台

不要等出 bug 以后才想调试页。

开发检验台应该从第一天就有，因为它同时服务三件事：

```text
调试
验收
路演可信证明
```

最小开发检验台包括：

- 服务健康状态。
- 当前 provider / model / key 是否存在。
- 原始输入预览。
- Agent 原始返回 JSON。
- 归一化后的业务状态。
- 用户确认后的最终输入。
- 规划 Agent 请求和响应。
- 错误信息和 cache source。

本次比赛里，开发检验台帮助定位过：

- 目标菜被识别成“模型结果”。
- 上传图片后直接跳结果页，用户没机会改菜名。
- 用户把回锅肉改成鱼香肉丝后，图片仍影响规划。
- 鱼香肉丝被当成一个整体食材。
- 模型超时后缓存来源是否正确。

经验：

> 开发检验台不是额外工作，它是让问题可见的基础设施。

## 6. 阶段五：准备兜底

比赛现场不要假设模型、网络、浏览器权限、端口、演示机都会正常。

至少准备四层兜底：

```text
缓存 JSON
固定演示样例
手动输入修正
备用录屏
```

本次可复用做法：

- 模型优先，超时或失败后再缓存兜底。
- 开发台展示 `source`，用户端不暴露内部字段。
- 等待状态显示阶段和秒数，避免用户以为卡死。
- 语音识别不稳定时降级为实验链路，不进主演示。
- 购物车和发抖音入口先做演示 CTA，不做真实跳转。

## 7. 阶段六：展示与提交

最终展示不是“把功能跑一遍”，而是：

```text
先让观众相信问题真实
再让观众看到产品好用
最后证明系统可信
```

推荐顺序：

```text
一句话场景
-> 用户端主流程
-> 结果页价值
-> 开发检验台证明
-> 评分点回扣
```

比赛提交材料要提前反向整理：

| 材料 | 重点 |
|---|---|
| 作品说明 | 用户价值、AI 能力、完整闭环 |
| 路演讲稿 | 先讲场景，再讲能力 |
| 海报 | 一句话 + 一张结果图 + 二维码 |
| 录屏 | 主路径稳定跑通 |
| GitHub | README、启动方式、无密钥 |

## 8. 推荐时间分配

### 一天冲刺版

| 时间 | 任务 |
|---:|---|
| 1 小时 | 选题收敛和一句话价值 |
| 2 小时 | 用户端最小页面 |
| 2 小时 | Agent API 和缓存样例 |
| 1 小时 | 开发检验台 |
| 1 小时 | 结果页打磨和兜底 |
| 1 小时 | 文档、讲稿、录屏 |

### 两天比赛版

第一天：

```text
上午：选题和主流程
下午：MVP 页面和 API
晚上：模型接入和缓存
```

第二天：

```text
上午：调试台、兜底、样例
下午：视觉打磨、讲稿、提交材料
晚上：录屏和演示彩排
```

## 9. 最重要的复用句

下次比赛可以把这句话贴在任务列表最上面：

> 先做一个观众能记住的真实闭环，再用开发检验台证明它不是假的。
