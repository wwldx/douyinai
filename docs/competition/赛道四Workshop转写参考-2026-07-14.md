## 2. 对当前项目有直接影响的口径

### 2.1 大区赛必须端到端可体验

转写中工作人员明确区分了交流赛和大区赛：交流赛允许只做关键模块；大区赛更关注一个部署后可体验的端到端产物。网页或 H5 可以使用，但需要部署到评委和赛后评委能访问的地址。

对本项目的影响：

- CloudBase 公网版本、真实输入、完整流程和失败兜底优先于继续增加支线功能。
- 不能只依赖固定示例或本地中间结果；评委可能使用自己拍摄或上传的输入。

### 2.2 “AI 链路可落地”是可验证工作流

转写对“可落地”的解释不是要求复杂训练或重 Agent 框架，而是：想法需要具备可行性，数据流、模型/API 调用和结果生成应封装在项目中，最终能让评委从输入到输出实际跑通。

对本项目的影响：

- 当前“视觉理解 -> 用户确认 -> 确定性工具 -> 规划 -> 满足反馈”的结构符合该口径。
- 开发检验台、严格 Schema、来源标记、延迟和失败分类是有效证据。
- OneReason 式训练、额外 Agent 框架或仅为技术感增加的模块不构成更高优先级。

### 2.3 评委会随机试几次，不只看 showcase

转写答疑称不会用大量 case 做正式准确率测试，但评委可能用手边任意内容试几次；明显错误、图片异常、流程 bug 和等待数分钟都会影响评价。

对本项目的影响：

- 固定示例用于保证讲解，随机输入稳定性用于保证得分，两者都要有。
- 下一阶段优先验证真实手机相机、非示例菜图/冰箱图、超时、未知菜名和上游失败。
- 30 例评测和失败案例分析比新增一个未经验证的 U20 支线更重要。

### 2.4 不要求仿做完整抖音界面

转写答疑明确表示无需 mock 完整抖音页面；只要讲清入口从哪里来、如何与抖音或真实世界结合，并把视觉搜索业务闭环做好即可。抖音内的未来应用可以在项目文档中说明。

对本项目的影响：

- UI 需要清楚、可信、移动端可用，但不再投入时间还原抖音 Feed 外壳。
- 功能冻结前只修阻塞理解、操作或响应式的问题；统一视觉 polish 放在闭环和公网稳定后集中完成。

### 2.5 数据、模型和 Skill

- 允许按能力需要选择 VLM/provider，关键是能完成闭环。
- 无法获得抖音后台数据时，可以构造 demo 数据；公开内容可用于演示，后台批量数据不会提供。
- 转写中将 Skill/Agent 称为 bonus，但官方截图写明需将核心流程打包并至少包含 `SKILL.md`。当前仍按更严格的书面要求交付，不因口头表述降低优先级。

## 3. 当前优先级结论

1. 固化并提交当前本地功能，形成可追溯发布基线。
2. 部署 CloudBase 003，使公网与本地功能一致。
3. 真机和随机输入稳定性验收，包括相机、语音、移动网络、无痕窗口和非示例输入。
4. 运行 Case V0/正例/正反例消融及必要的真实模型回归，记录延迟、token 和失败案例。
5. 功能冻结后集中做一次 UI polish，再录制 showcase、生成二维码和完成提交材料。
6. U20“翻车菜品视觉救援”降为时间有余才做，不进入当前关键路径。
