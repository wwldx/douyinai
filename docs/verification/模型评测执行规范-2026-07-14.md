# 模型评测执行规范

日期：2026-07-18  
状态：U12 完成；`gpt-5.6-terra` 固定 30 例真实模型回归与完整 19 例 Case A/B/C 消融已完成  
目标：用同一套可重复数据记录 Schema、动作、安全、来源、模型、延迟、token、结构化输出和失败类型，禁止把演示缓存结果混入真实模型指标。

## 1. 为什么不能直接使用主演示服务

主演示服务默认启用 4.5 秒视觉缓存兜底。模型响应较慢时，固定示例可能先返回 `model-timeout-cache`。这适合现场稳定性，但不适合真实模型评测。

真实视觉评测必须使用独立本地进程并关闭演示缓存；Case 消融还必须允许请求级模式覆盖：

```bash
DEMO_VISION_CACHE_ENABLED=false \
CASE_RETRIEVAL_MODE=off \
ALLOW_RETRIEVAL_MODE_OVERRIDE=true \
AGENT_RUNS_ENABLED=false \
VISION_MODEL=gpt-5.6-terra \
PLANNING_MODEL=gpt-5.6-terra \
PORT=4181 \
npm run dev
```

不要修改或提交 `.env.local`。评测脚本不读取或输出 API Key，只访问已启动的本地服务。消融不得直接对公网生产服务运行；生产环境默认禁止请求级模式覆盖，否则命令写了 `positive` 或 `contrast`，服务端仍可能实际执行 `off`。

## 2. 当前评测器的硬门禁

### 2.1 展示端等效视觉输入

`scripts/run-evals.mjs` 不再把仓库中的原始大图直接发送给模型。每张评测图片都会先通过 `ffmpeg` 转为 JPEG，并按保持宽高比的方式把最长边限制在 1400 像素，再交给视觉接口。这与 React 展示端上传前的压缩尺度等效，避免“评测原图超大而真实产品已压缩”造成无意义的超时差异。

报告中的：

```json
"visionInput": "jpeg-max1400-showcase-equivalent"
```

用于确认本轮采用了这一输入口径。运行真实视觉评测的机器必须安装 `ffmpeg`；压缩失败应直接判失败，不能退回原图或缓存。

### 2.2 真实来源、模型与输出

使用 `--require-model-source` 时，视觉和规划每一例都必须实际返回 `source=model`；`model-timeout-cache`、`model-error-cache`、未知来源和错误响应都不得进入真实模型通过数。

每例报告必须保存：

- `source`、`provider`、`model`；
- request ID、`Server-Timing` 和端到端耗时；
- provider 返回的 token usage；
- 用于复核的结构化 `output`；
- Schema、动作、关键语义、缺料、安全和视觉覆盖指标；
- 失败原因与失败分类。

汇总报告同时保存 `sourceCounts`、`providerCounts` 和 `modelCounts`。因此“使用了 terra”必须由报告中的 `modelCounts` 证明，不能只根据 `.env.local` 或口头配置推断。

### 2.3 实际检索模式与角色

规划消融请求 `off`、`positive` 或 `contrast` 后，评测器必须校验服务端实际返回的检索结果：

- `off`：实际模式必须为 `off`，且 Case 数量必须为 0；
- `positive`：实际模式必须为 `positive`，必须返回 Case，且角色全部为 `positive`；
- `contrast`：实际模式必须为 `contrast`，必须同时包含 `positive` 与 `negative`。

请求模式、实际模式或角色不一致时，该例直接失败。这一门禁用于防止把“命令请求了 contrast、服务端实际仍是 off”的假实验写入消融结论。

### 2.4 `uncertainItems` 覆盖指标

冰箱图片经常存在塑料袋反光、遮挡、标签不清等情况。把保守的不确定表达一律当成漏识别，会反向鼓励模型硬猜，因此冰箱视觉同时记录两层指标：

- `confirmedItemRecall`：预期食材在明确 `items` 中被识别的比例；
- `acknowledgedItemRecall`：预期食材在 `items` 或 `uncertainItems.description` 中被明确覆盖的比例；
- `itemRecall`：当前质量门禁使用 `acknowledgedItemRecall`，阈值为 `>= 0.5`。

只有不确定描述确实覆盖对应食材或类别时才计入，泛泛写“有遮挡物”不能算命中。该指标表示模型看到了相关区域并把不确定性交给后续用户确认，不代表已经确认食材种类、新鲜度或安全性；报告仍应同时保留 `confirmedItemRecall`，不能只展示较高的覆盖率。

目标菜视觉也允许保守处理菜名歧义：菜名不完全匹配时，只有输出明确使用“疑似/可能/或”、置信度不高于 0.85、提供 warning，且关键材料召回不低于 0.5，才可记为 `dishNameUncertaintyAcknowledged=true` 并通过。产品中的菜名人工确认仍是硬步骤。

## 3. 数据校验与准确命令

先检查固定数据集，不调用模型：

```bash
npm run eval:validate
```

当前固定集为 30 例：9 例冰箱视觉、2 例目标菜视觉、10 例目标菜规划、9 例自由晚餐规划。

运行完整 30 例无检索真实模型基线：

```bash
npm run eval:model-full -- \
  --base-url http://localhost:4181 \
  --retrieval-mode off \
  --timeout-ms 70000 \
  --output docs/verification/reports/gpt56-terra-full-30-off-frontend-compressed-final-20260718.json
```

运行完整 19 例规划消融：

```bash
node scripts/run-evals.mjs \
  --base-url http://localhost:4181 \
  --suite planning \
  --require-model-source \
  --retrieval-mode off \
  --timeout-ms 70000 \
  --output docs/verification/reports/case-ablation-terra-off-full19-20260718.json
```

```bash
node scripts/run-evals.mjs \
  --base-url http://localhost:4181 \
  --suite planning \
  --require-model-source \
  --retrieval-mode positive \
  --timeout-ms 70000 \
  --output docs/verification/reports/case-ablation-terra-positive-full19-20260718.json
```

```bash
node scripts/run-evals.mjs \
  --base-url http://localhost:4181 \
  --suite planning \
  --require-model-source \
  --retrieval-mode contrast \
  --timeout-ms 70000 \
  --output docs/verification/reports/case-ablation-terra-contrast-full19-20260718.json
```

`--timeout-ms 70000` 是评测器等待本地 HTTP 响应的外层门限，不会扩大 Agent 当前的 50 秒模型请求门限。账单金额仍以 Right Code 控制台为准；没有明确单价版本和账单记录时，不自行把 token 换算成对外成本。

## 6. 失败处理与报告保留

- `source`：接口未返回真实 `model` 来源，不能进入真实模型指标。
- `schema`：结构化输出缺字段、类型错误或多余字段。
- `quality`：动作、召回、关键语义、缺料、检索角色或禁用语义不符合标注。
- `upstream`：HTTP 5xx、50 秒模型超时、TLS/SSL、网关或模型服务连接失败。
- `http`：4xx 输入或限流问题。
- `fixture`：图片、标签或期望值本身错误；必须先人工纠正素材，再创建新的定向复验和最终报告。

出现连续上游错误时停止扩大样本，不自动循环重试。先保存失败报告和 request ID；网络恢复后只对明确失败的 ID 做定向复验。

所有原始失败、超时、错误端口、旧素材、未压缩输入和中间复验报告都是审计轨迹，必须原样保留：

- 不得删除失败报告；
- 不得覆盖原文件名；
- 不得修改旧报告中的结果使其看起来通过；
- 修复后必须生成带新文件名的新报告，并在结论中区分原始失败、定向复验和最终固定基线。

## 7. 对外表述边界

- 30/30 只能称为“当前模型、提示词、Schema 和固定 30 例上的真实模型回归通过”，不能称 100% 视觉准确率、线上满意度或真实用户成功率。
- 30 例由 11 例固定视觉素材和 19 例人工规划 holdout 构成，不代表真实抖音用户分布；视觉期望来自经人工复核的固定演示参考，不是大规模盲标数据。
- `acknowledgedItemRecall` 把明确写入 `uncertainItems` 的相关食材计为覆盖，体现“识别或保守交给用户确认”，不代表模型已经确认该食材。
- 本轮是单轮固定回归，没有重复采样置信区间；模型延迟和输出仍可能波动。
- 视觉缓存、人工规则回归、真实模型评测和素材纠正后的重新评估必须分开报告。
- Case 消融的当前结论是“没有测得质量增益，且成本/动作结果更差或不优”，因此继续 `off`；不得挑选 positive 的 19/19 来声称检索有效。
- 原始失败报告与最终成功报告必须同时保留，路演只讲清楚最终口径，但技术问答可以展示完整失败分析和纠正过程。
