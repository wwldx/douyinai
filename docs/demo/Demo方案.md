# Demo 方案：冰箱晚餐 Agent

方案定位：现场可试玩的视觉搜索 AI Agent  
推荐赛道：大区赛赛道四，视觉搜索：视觉 + 语音，所见即所想
当前实现：`frontend/` 评委展示端 + `demo/server.mjs` 轻量 Agent API；`demo/index.html` 保留为旧展示页/本地兜底页。展示端首屏提供 Feed 和冰箱双入口，两条路线共享视觉识别、库存确认和规划接口，结果页支持做饭过程救援；CloudBase 011 是当前公网基线并已通过定向门禁，历史 005 iPhone 主链路证据保留，011 真机复验待完成。

## 1. 一句话

刷到想吃的菜时，先放入菜图或说出要求，再拍冰箱判断今晚能不能照着做；没有目标菜时，也可以直接拍冰箱，让 AI 推荐一顿现实可执行的晚餐。

## 2. 核心洞察

用户打开冰箱时，真正的问题通常不是“里面有什么”，而是“今晚到底吃什么”。普通识别工具停在图片描述，普通菜谱工具又需要用户先想好食材和菜名。冰箱晚餐 Agent 把两者连起来：先从真实视觉场景读出可用库存，再结合用户状态做晚餐决策。

## 3. 30 秒演示路径

1. 首屏选择「刷到想吃的」进入 Feed 路线；主演示默认走这条路线。
2. 直接拍下暂停画面、从相册选目标菜图或载入示例黄焖鸡，系统识别菜名并写入可编辑文本框；用户可补充“只有 25 分钟 / 不想洗锅”等要求。
3. 用户确认目标菜后进入冰箱步骤，直接拍冰箱、从相册选择或载入示例冰箱。
4. 有 API Key 时调用视觉识别 Agent；无 Key 或失败时，演示图片回退到明确标记的缓存样例。
5. 用户勾选确认可用食材；如有想优先处理的食材，可主动选择已开封、确认标签日期临近或状态不确定，再点击「看看家里够不够做」。
6. 页面展示能否照着做、简化步骤、已有材料、先吃清单、关键缺口、安全提醒和克制商业延展。
7. 首屏选择「打开冰箱没想法」时，先识别冰箱，再选择「帮我决定」或「我有想吃的」；后者复用相同目标菜确认流程。
8. 结果页可反馈「正合适 / 太麻烦 / 缺料太多 / 不想洗锅 / 换清淡点」；负反馈写入事件并回到库存确认，下一轮显式带上对应约束。
9. 结果页「重新规划」回到库存确认并保留当前数据；「换一种开始方式」返回双入口。
10. 家里还差材料时展示模拟抖音商城按钮；饭后可拍摄/上传成品图，生成可编辑标题、封面、旁白、补拍建议和标签。商城和生活记录均不执行真实下单或发布。
11. 做到一半卡住时，可拍当前画面并选择状态、味道、调料或下一步问题；系统结合原步骤，只给当前动作和观察点。

## 4. 当前 Demo 内容

已实现 3 个缓存视觉样例：

| 样例 | 场景 | 推荐结果 |
|---|---|---|
| 新手赶时间 | 番茄、鸡蛋、面条、黄瓜、速冻饺子 | 番茄鸡蛋面 |
| 想练一道菜 | 豆腐、鸡胸、胡萝卜、生菜、米饭 | 豆腐胡萝卜盖饭 |
| 太晚太累 | 速冻饺子、鸡蛋、生菜、面包、饮料 | 速冻饺子 + 生菜汤 |

上传冰箱图片时，Demo 会展示上传预览，并调用 `/api/analyze-fridge` 获取视觉识别 JSON；用户确认库存后，可调用 `/api/plan-dinner` 生成晚餐规划 JSON。上传目标菜图时，Demo 会调用 `/api/analyze-target-dish` 猜测菜名、关键材料和难点，用户可手动修改菜名后再调用 `/api/plan-target-dish` 生成复刻路线。没有 `OPENAI_API_KEY` 或接口失败时，页面保留缓存 JSON 兜底，现场不会空白。

## 5. 页面结构

| 区域 | 功能 |
|---|---|
| 视觉输入区 | 上传冰箱图、选择预置样例 |
| 目标菜输入区 | 上传想复刻的菜图、识别目标菜、手动确认菜名 |
| 语音输入 | 浏览器 Web Speech 实时识别优先，服务端录音转写兜底，把目标菜或约束写入可编辑文本框 |
| 已授权上下文 | 展示厨艺、时间、精力、偏好、避开项、近期饮食 |
| 识别库存 | 展示食材、类别、数量、置信度和状态，可勾选确认 |
| 冰箱救援 | 用户可选填开封/标签状态，确定性规则输出本餐优先、近两餐和待确认，并影响规划 |
| AI 决策区 | 输出晚餐方案、路线标签和核心判断 |
| 保底方案 | 输出菜名、理由、耗时、难度和步骤 |
| 进阶一点 | 给出可选升级菜，不作为主推荐 |
| 缺料补买 | 只推荐 0 到 3 个关键补买项 |
| 外卖/速食兜底 | 时间不足或材料缺失时给现实兜底 |
| 安全提醒 | 明确图片不能判断过期、新鲜度和肉类安全 |
| 目标菜复刻 | 输出已有材料、关键缺口、替代路线、难点提醒和模拟补齐卡 |
| 商业延展 | 以补货、外卖兜底、厨具升级表达，避免硬推消费 |
| 满足反馈 | 五类显式反馈写入用户事件；负反馈形成下一轮可解释约束 |
| Case 检索证据 | 开发台可切换 V0/仅正例/正反例并查看 Top-K、分项分数和来源 |
| 饭后内容回流 | 成品图生成可编辑生活记录草稿；开发台展示模型/缓存来源，用户端不自动发布 |
| 做饭过程救援 | 当前画面 + 用户描述 + 原步骤，返回一到三个可验证动作，不从图片猜味道或熟度 |

## 6. AI 能力表达

Demo 要强调 AI 不是“识别冰箱里有什么”，而是完成一个决策链：

```text
视觉识别
  -> 不确定项标注
  -> 用户确认库存
  -> 结合用户状态
  -> 判断今晚是否适合做饭
  -> 生成保底菜 / 进阶菜 / 补买项 / 兜底方案
```

这比单纯 OCR 或菜谱搜索更符合赛道四视觉搜索，因为图片理解结果直接驱动后续行动；对外表达时要强调“刷到想吃的菜 -> 视觉/语音表达需求 -> 拍冰箱判断能否照着做 -> 补齐和发布”的抖音生态闭环。

## 7. 技术实现

当前阶段：

- HTML/CSS/JavaScript 单页 Demo。
- 零依赖 Node 服务：`demo/server.mjs`。
- 轻量 Agent 端点按目标菜视觉、冰箱视觉、两类规划、过程救援和饭后草稿拆分职责。
- OpenAI Responses API + JSON schema 结构化输出。
- Right Code 中转站使用 `rightcode_responses_stream` provider，发送 `stream:true` 并解析 SSE 中的 `response.output_text.delta`。
- 静态样例作为模型失败兜底。
- React H5 与 API 使用单个 Node 服务同源生产部署，避免公网跨域和双服务运维。
- 30 例固定评测集覆盖视觉 Schema/召回、规划动作、关键缺料、安全语义和延迟。
- Feed 菜图识别后可从关键食材候选中选择一个关注对象；系统只用人工确认库存运行确定性替代规则，结果明确区分“已有、改做、补买”，并有 12 例独立规则回归。当前不是像素级 ROI，不在演示中声称精确圈选定位。
- 用户主动确认食材状态后，`/api/eat-first` 用确定性规则生成本餐优先、近两餐和待确认清单，并把优先食材加入 Planner 约束；10 例规则回归已通过。它不读取图片日期，也不判断过期、新鲜度或可安全食用。
- 24 条独立人工参考 Case 与 8 条检索标签支持结构化正反例检索；公网默认关闭，真实规划消融通过后再决定是否启用。
- 生产服务已加入请求上限、模型/普通接口分组限流、错误脱敏、安全头、request ID 和阶段 trace。
- 官方 Skill 位于 `submission/skill/fridge-dinner-visual-search/`。
- 勾选库存后实时调整缺料补买和兜底文案；目标菜复刻不展示分数，避免现场解释评分算法。

Agent 分层：

```text
/api/analyze-fridge
  -> 返回 items / uncertainItems / warnings

/api/analyze-target-dish
  -> 返回 dishName / likelyIngredients / requiredTools / estimatedTime / difficulty

/api/plan-dinner
  -> 返回 decision / baseMeal / stretchMeal / shoppingUpgrade / fallback / safetyTips

/api/plan-target-dish
  -> 返回 targetDish / inventoryMatch / executionPlan / userFit / commerceCards

/api/case-retrieval/preview
  -> 返回 Top-K / scoreBreakdown / sharedEvidence / positive-negative role

/api/eat-first
  -> 返回 confirmed-status 本餐优先 / 近两餐 / 待确认 / plannerPriorities

/api/generate-life-log
  -> 返回 dishName / visualSummary / titleOptions / coverText / voiceoverDraft / suggestedShots / tags / warnings

/api/rescue-dish
  -> 返回 visible evidence / issue assessment / immediate actions / observation checks / boundary reminder
```

默认模型通过 `OPENAI_MODEL` 配置。当前 CloudBase 011 的视觉、规划和生活记录均使用 `gpt-5.6-terra`，`OPENAI_MODEL` 也设为 terra 以避免任务变量缺失时回退到 sol；后续切换模型只需修改服务端环境变量，前端 JSON 合约不变。

## 8. 现场讲解要点

- 推荐采用 `docs/strategy/AI_Agent情景化Demo展示工作流.md` 里的三层讲法：先用情景说明“晚上不知道吃什么 / 刷到想吃的但不知道家里够不够做”，再演示公网用户端，最后按需打开开发检验台证明 Agent 链路、结构化输入输出和缓存兜底。
- 这不是菜谱搜索，而是从“所见食材”出发的晚餐决策 Agent。
- 用户只需拍照和确认库存，不需要手动输入一堆条件。
- AI 会考虑厨艺、时间、精力和近期饮食，所以不会给新手推荐高风险复杂菜。
- 不确定食材不会硬编；会进入不确定项，并要求用户确认。
- 刷到复杂暂停帧时，可以手动框选菜品区域后再识别；AI 先猜菜名和关键材料，最终仍由用户确认。
- 不想打字时，可以用语音说出目标菜或约束；语音只作为快捷输入，录音临时转写后删除。
- 商业化自然发生在补货、外卖兜底、厨具升级，不喧宾夺主。

## 9. 评分对齐

| 评分关注 | 对齐方式 |
|---|---|
| 真实场景成立 20% | 解决高频、具体、即时的“刷到想吃的/打开冰箱后今晚吃什么”问题 |

| AI 链路可落地 25% | 视觉识别、目标菜识别、偏好理解、时间约束和安全规划共同决策，并可在开发检验台展示 |
| 增长与 ROI 15% | 可从美食视频和厨房场景冷启动，用搜索渗透、满足率、补买转化和复访衡量 |

## 10. 运行方式

生产模式需要先构建 React H5，并在服务端环境变量中设置真实 `OPENAI_API_KEY`：

```bash
npm run build
OPENAI_API_KEY=你的_key npm start
```

然后访问 `http://localhost:4173/`。

无 Key 时也可以运行：

```bash
npm run dev
```

页面会提示回退缓存，仍可完整演示前端流程。
