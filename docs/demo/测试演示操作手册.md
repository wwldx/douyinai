## 1. 当前 Demo 是什么

当前项目是「冰箱晚餐 Agent」本地 Demo。

核心链路：

```text
上传冰箱图片
  -> 视觉识别 Agent 识别可见食材
  -> 用户人工确认库存
  -> 晚餐规划 Agent 生成今晚方案
  -> 页面展示保底方案、进阶方案、缺料补买和安全提醒
```

当前不是 Python 项目，也不是 C++ 项目。主要代码是原生 JavaScript / Node.js：

- 后端 Agent：`demo/server.mjs`
- 主展示端：`frontend/`，Vite + React
- 旧展示/兜底页：`demo/index.html` + `demo/app.js`
- 开发检验台：`demo/dev.html` + `demo/dev.js`
- 样式：`demo/styles.css` + `demo/dev.css`

## 5. 健康检查

服务启动后，可以打开：

```text
http://localhost:4174/api/health
```

正常应该看到类似：

```json
{
  "ok": true,
  "provider": "rightcode_responses_stream",
  "model": "gpt-5.5",
  "hasApiKey": true,
  "disableResponseStorage": true
}
```

重点看：

- `ok` 应该是 `true`
- `provider` 应该是 `rightcode_responses_stream`
- `model` 应该是 `gpt-5.5`
- `hasApiKey` 应该是 `true`

如果 `hasApiKey:false`，说明 `.env.local` 没读到、仍是中文占位符或没有填真实 Key。填完后重启服务。生产健康检查不会暴露上游 API 地址。

## 6. 开发检验台测试流程

推荐先用开发检验台验链路：

```text
http://localhost:4174/dev.html
```

操作步骤：

1. 确认右上角显示：

```text
rightcode_responses_stream · gpt-5.5 · key:yes
```

2. 点击「选择冰箱图片」。

3. 推荐先选择项目里的样例图：

```text
assets/fridge-images/330d23dcca05ea8e54bbe6bace6677e7.png
```

或：

```text
assets/fridge-images/f63de1c0794c76a412b9f06f0d919044.png
```

如果上传手机拍摄的大图，前端会先在本地压缩到适合模型识别的尺寸，再发送给本地服务。这样可以降低中转站因为图片过大而返回 `fetch failed` 的概率。

现场稳定性说明：

- `assets/fridge-images`、`assets/imgs-ai` 和 `assets/菜` 里的演示图片已经有本地预分析缓存。
- 识别时仍然先走模型，不会因为文件名命中缓存就立刻返回。
- 如果模型超过约 4.5 秒还没返回，且这张图命中缓存，后端会切到本地缓存，保证演示不断。
- 开发检验台可以从接口返回里的 `source` 判断来源：`model` 表示真实模型，`model-timeout-cache` 表示超时后切到缓存，`model-error-cache` 表示模型失败后切到缓存。
- 比赛展示端不展示这些内部来源字段，避免干扰评委。

4. 点击「调用视觉识别」。

5. 查看「视觉识别原始返回」。

正常情况下会看到完整 JSON，例如包含：

```text
番茄酱、饮料罐、百事可乐、鸡蛋、圆白菜、花菜、蘑菇、绿叶菜
```

具体结果每次可能略有变化，以原始 JSON 为准。

6. 查看「归一化库存与人工确认」。

这里是给用户确认的可用食材列表。可以取消勾选明显识别错的食材。

视觉识别成功后，页面会自动把本次结构化识别结果保存到当前演示用户的本地文件夹。后续如果现场网络慢或中转站不稳定，可以点击「加载上次识别」继续演示库存确认和晚餐规划。

缓存位置：

```text
data/local-users/<userId>/vision-cache.json
```

浏览器 `localStorage` 只作为兜底，它不是项目目录里的长期文件。不同演示用户之间的画像和冰箱缓存互相隔离。

7. 点击「调用晚餐规划」。

8. 查看「晚餐规划输入与原始返回」。

重点检查：

- `request.inventory` 是否就是人工确认后的库存。
- `response.plan` 是否给出合理的保底方案。
- 安全提醒是否保守，不要直接判断食材一定新鲜。

## 7. 展示界面演示流程

比赛展示端打开：

```text
http://localhost:5173/
```

现场演示推荐流程：

1. 简单介绍一句：

```text
刷到想吃的，拍下冰箱，AI 判断这一餐能不能复刻；如果没有目标菜，它也能直接给一顿最现实的做饭方案。
```

2. 首屏选择「刷到想吃的」进入主演示，上传目标菜图或点击「用示例黄焖鸡」，确认系统写入的菜名和附加要求。

3. 点击「下一步，看冰箱」，上传冰箱照片；远程评委也可点击「没有照片？用示例冰箱体验」。同时确认这顿饭的基本上下文：

- 餐次：页面会根据当前时间预选早餐 / 午餐 / 晚餐 / 夜宵，但现场可以手动改。
- 可支配时间：15 分钟、25 分钟、40 分钟，由用户确认。
- 当前模式：时间忙、想尝试新菜、今天很累，由用户显式选择。

4. 点击「识别冰箱」。

5. 第二步确认可用食材。

这里可以取消勾选一两个明显不确定的食材，体现人工确认机制。食材新鲜度、剩菜安全、肉类是否解冻等不由 AI 独断。

6. Feed 路线直接点击「看看家里够不够做」。如果从首屏选择「打开冰箱没想法」，这里再选择路线：

路线 A：用户无所谓，点击「帮我决定」，再点击「生成这一餐」。

路线 B：用户已有目标菜，点击「我有想吃的」，输入菜名、上传目标菜图或点击「用示例菜图」，再点击「看看家里够不够做」。

文字方式：

```text
我今晚想吃番茄牛腩
```

图片方式：

```text
上传目标菜图 -> 必要时补一句想吃什么 -> 点击「判断复刻路线」
```

这一步用于展示抖音场景故事：

```text
刷到想吃的，拍下冰箱，AI 判断今晚能不能复刻。
```

目标菜结果不会展示可做指数或分数，避免现场解释评分算法。重点看：

- 尽量尊重用户想吃的方向，而不是简单劝退。
- 当前冰箱已有材料和关键缺口。
- 时间和难度带来的提醒。
- 可以今晚做的简化路线。
- 必要时才出现补齐材料建议。

7. 查看结果页。

展示端只保留最重要的信息：

- 这顿饭做什么。
- 为什么适合当前餐次和时间。
- 现在就做的步骤。
- 会用到哪些已有材料。
- 如果是复刻目标菜，展示已有 / 还缺 / 难点提醒。
- 缺关键食材时，可以展示「加入购物车，去抖音商城」模拟按钮，强调补齐材料的生态入口。
- 饭后可以展示「拍成品，发抖音」入口，强调做完后的生活记录和内容回流。
- 如果用户明确选择自己做饭，不突出外卖兜底。
- 点击底部「重新规划」会回到库存确认，保留这次冰箱识别和人工确认库存；点击「换一种开始方式」返回双入口。
- 点击「太麻烦 / 缺料太多 / 不想洗锅 / 换清淡点」会记录明确反馈并回到库存确认，下一轮会带上对应约束；「正合适」只记录接受反馈。

8. 强调产品价值：

```text
它不是只识别冰箱里有什么，而是把视觉库存、用户厨艺、时间和精力一起纳入决策，给出今晚最现实的一顿饭。
```

补充讲法：

```text
普通聊天机器人可以告诉你番茄牛腩怎么做，但这里会先看你家的冰箱、今晚时间和厨艺水平，判断现在能不能复刻；如果不能，就给你简化版本、明天补买路线、抖音商城模拟补齐卡，以及饭后生成生活记录的入口。
```

语音输入说明：

- React 展示端目标菜文本框旁已提供「语音输入」。
- 优先使用 Edge/Chrome 的浏览器实时语音识别；不可用时再录音调用 `/api/transcribe-audio`。
- 公网必须使用 HTTPS 才能稳定申请麦克风权限。
- 语音失败后立即改用文本，不在现场排查 ASR；文本始终是稳定兜底。

## 8. 如何判断是不是模型真实结果

比赛展示端为了减少信息干扰，不直接展示模型名、provider、confidence 或原始 JSON。需要确认链路真假时，打开开发检验台：

```text
http://localhost:4174/dev.html
```

旧展示页和开发检验台会标注来源。

开发检验台还可以切换 `V0 无检索 / V1 仅正例 / V1.1 正反例`，点击「只看 Top-K」时不会调用大模型，只展示 Case ID、分项相似度、共同证据和来源。

如果是模型结果，会显示类似：

```text
模型识别 · gpt-5.5 · 12/12 已确认
```

如果加载的是上次成功识别缓存，会显示类似：

```text
上次模型结果 · gpt-5.5 · 12/12 已确认
```

如果是缓存样例，会显示：

```text
缓存样例 · 6/6 已确认
```

如果识别失败，会显示：

```text
识别失败 · 0/0 已确认
```

识别失败时，展示页不会再把缓存食材伪装成模型结果。要看具体错误，请打开：

```text
http://localhost:4174/dev.html
```

## 9. 常见问题

### 9.1 npm run dev 提示找不到 package.json

错误类似：

```text
npm error enoent Could not read package.json
```

原因是当前终端不在项目目录。先执行：

```bash
cd "/Users/wwl_mac/Desktop/2026春季第四学期/2026抖音ai创变者计划"
npm run dev
```

### 9.2 EADDRINUSE: address already in use

说明端口已经有服务在运行。可以直接打开对应端口使用。

查看 4174 端口：

```bash
lsof -nP -iTCP:4174 -sTCP:LISTEN
```

如果确认要停止旧服务：

```bash
kill <PID>
```

然后重启：

```bash
PORT=4174 npm run dev
```

### 9.3 页面提示 failed to fetch

常见原因：

- 没有启动 `npm run dev`
- 服务终端被关闭
- 用 `file://` 打开了 HTML
- 打开的是 4174，但服务跑在 4173
- `.env.local` 改完后没有重启服务
- 上传图片过大，中转站连接被断开

建议先检查：

```text
http://localhost:4174/api/health
```

如果健康检查正常，但识别接口返回：

```json
{
  "error": "fetch failed"
}
```

优先处理方式：

1. 先用 `assets/fridge-images` 里的样例图测试。
2. 如果样例图正常，说明服务和模型链路没问题，问题多半是上传图片太大或图片格式特殊。
3. 更新到最新版代码后，前端会自动压缩大图。
4. 修改了 `demo/server.mjs`、`demo/app.js` 或 `demo/dev.js` 后，需要重启 `npm run dev`。

### 9.4 hasApiKey 是 false

说明服务没有读到 API Key。

检查 `.env.local` 是否存在，且包含：

```env
OPENAI_API_KEY=你的中转站 API Key
```

填好后重启：

```bash
PORT=4174 npm run dev
```

### 9.5 模型返回和图片不太相符

这是当前 Demo 特意保留人工确认步骤的原因。

处理方式：

1. 到开发检验台看原始 JSON。
2. 在库存列表取消勾选错误食材。
3. 再生成晚餐方案。
4. 记录明显误识别案例，后续优化提示词和样例图。
