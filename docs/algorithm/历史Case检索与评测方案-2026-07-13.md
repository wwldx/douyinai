# 历史 Case 检索与评测方案

更新日期：2026-07-16  
状态：V1 检索层与当前 `terra` 完整 19 例 A/B/C 消融已完成；未测得规划质量增益，主演示继续关闭检索  
来源参考：Codex 任务 `019f1725-8ecf-7fc2-b96e-af05c5c2d7cb` 中对 OneReason、FinFRE-RAG、ARG、LSVCR 的讨论

## 1. 为什么选择这个方向

本项目不具备大团队预训练、SFT、分域 RL、teacher 蒸馏所需的数据、算力和时间。强行加入 LoRA、GRPO 或多 Agent 框架只会增加叙事，不会产生可信算法证据。

适合当前 Solo 项目的路线是：

- 不训练底模。
- 把菜品、冰箱库存、时间和用户约束结构化。
- 从独立的历史案例库检索相似成功/失败 case。
- 用少量正反例约束规划 Agent，而不是让模型只靠通用常识生成。
- 用离线评测和消融判断是否真的减少错误。

这与 FinFRE-RAG 的方法论相似，但应用目标不同：FinFRE-RAG 面向金融欺诈风险，本项目面向视觉搜索后的晚餐行动规划。对外应称“参考历史 case 检索和对照 ICL”，不能声称复现论文。

## 2. 要验证的假设

| 编号 | 假设 | 可观测指标 |
|---|---|---|
| H1 | 结构化相似 case 能提高路线选择一致性 | action accuracy / consistency |
| H2 | 成功与失败对照例能减少“缺主料却声称可做” | critical-missing recall / contradiction rate |
| H3 | 历史 case 能让解释更具体、更贴近约束 | evidence coverage / 人工评分 |
| H4 | 检索增益能够覆盖额外延迟和 token 成本 | P50/P95 / token / cost |

H1-H4 未完成实验前均为假设，不得写成结论。

## 3. Case 数据结构

建议新增独立数据目录：

```text
data/case-memory/
  reference-cases.json
  retrieval-labels.json
  README.md
```

单条 case 至少包含：

```json
{
  "caseId": "case-001",
  "source": "curated",
  "scene": "feed_to_fridge",
  "targetDish": {
    "name": "黄焖鸡",
    "tags": ["鸡肉", "焖菜", "下饭"]
  },
  "inventory": ["土豆", "米饭", "鸡蛋"],
  "missingCritical": ["鸡腿肉", "香菇"],
  "constraints": {
    "timeMinutes": 25,
    "skill": "beginner",
    "energy": "low",
    "preferences": ["少洗锅"]
  },
  "decision": "shop_then_cook",
  "evidence": ["缺少鸡腿肉", "时间不足以从零完成"],
  "satisfaction": "accepted",
  "safetyNotes": [],
  "createdAt": "2026-07-18T00:00:00+08:00"
}
```

`source` 只能使用明确值：

- `curated`：人工构造并核验。
- `demo`：固定演示样例。
- `explicit-feedback`：用户明确反馈后产生。
- `synthetic`：模型生成但经过人工核验。

不得把 `synthetic` 写成真实用户数据。高风险健康信息、食材新鲜度和肉类安全不得自动进入记忆。

## 4. 数据隔离

当前 19 例规划评测不能同时作为检索库和测试集，否则会产生数据泄漏。

第一版建议：

- 单独建立 24-40 条 reference cases。
- 现有规划评测继续作为 holdout 基线。
- 按菜品家族、关键主料和约束组合检查近重复项。
- 检索时禁止返回与 query 相同的 `caseId`。
- 后续扩容时按菜品家族做 group split，避免同一道菜换一句话同时出现在检索库和测试集。

## 5. 检索版本

### V0：无检索基线

保持当前规划 Agent，只输入目标菜、确认库存和用户上下文。

### V1：结构化可解释检索

不依赖向量数据库，使用本地确定性特征：

```text
score =
  0.30 * target_dish_tag_similarity
  + 0.30 * inventory_jaccard
  + 0.15 * missing_pattern_similarity
  + 0.10 * time_bucket_similarity
  + 0.10 * skill_energy_similarity
  + 0.05 * preference_constraint_similarity
```

权重是初始假设，必须通过实验调整。不得把待预测的最终 `decision` 作为检索特征。

输出 Top-K 时同时返回：

- 总分。
- 各特征分项。
- 命中的共同食材、共同缺料和共同约束。
- case 来源。

这样开发检验台能够解释“为什么检索到它”。

### V1.1：正反例对照

从 Top-K 中选择：

- 1 条明确满意/成功的相似 case。
- 1 条失败、拒绝或关键缺料冲突的相似 case。

将其转换为短结构化上下文，限制模型只能参考证据，不得复制 case 中与当前库存冲突的结论。

### V2：混合语义检索

只有 V1 已证明有效且仍有时间时才实施：

- 对菜名、标签和用户约束生成 embedding。
- 语义相似度与 V1 结构化分数融合。
- 可选轻量 rerank Top-10 到 Top-3。

如果 provider 没有稳定 embedding API，V2 直接延期；不得为了混合检索再引入独立云服务。

## 6. Planner 接入

建议保持现有 JSON Schema 不变，只在服务端规划输入中新增：

```json
{
  "retrievedCases": [
    {
      "caseId": "case-001",
      "similarity": 0.82,
      "role": "positive",
      "sharedEvidence": ["同为新手", "25 分钟", "缺少核心肉类"],
      "decision": "shop_then_cook"
    }
  ]
}
```

提示词约束：

- 历史 case 是参考证据，不是当前事实。
- 当前确认库存优先级最高。
- 正例和反例都必须解释可迁移点与不可迁移点。
- 缺关键主料时不能因为正例成功就声称当前也能做。
- 检索失败时退回 V0，不阻断主流程。

## 7. 满意度闭环

结果页增加显式反馈：

- `accept_meal`：就做这个。
- `too_complex`：太麻烦，换简单点。
- `too_many_missing`：缺料太多。
- `low_cleanup`：不想洗锅。
- `lighter_taste`：换清淡点。

反馈先用于当前重新规划和本地事件记录。只有用户明确反馈、输入输出完整且没有安全争议时，才能进入 `explicit-feedback` case；不得根据点击停留时间自动推断满意度。

## 8. 评测与消融

### 8.1 三组最低实验

| 组别 | 配置 | 目的 |
|---|---|---|
| A | V0 无检索 | 当前模型基线 |
| B | V1 结构化检索，只给正例 | 检查相似成功经验是否有增益 |
| C | V1.1 结构化检索，正反例对照 | 检查反例能否减少错误承诺 |

V2 混合检索只作为第四组可选实验。

### 8.2 指标

检索指标：

- Recall@K。
- MRR 或 nDCG@K。
- Top-K case 来源和重复率。

规划指标：

- JSON Schema 通过率。
- action accuracy。
- 关键缺料召回率。
- 禁止语义/安全边界通过率。
- 当前证据覆盖率。
- 历史 case 与当前事实矛盾率。

工程指标：

- 端到端平均延迟、P50、P95。
- 检索阶段耗时。
- 输入/输出 token。
- 单次成本。
- 模型失败率和缓存降级率。

### 8.3 人工评分

对解释质量使用 1-5 分小量双盲打分：

- 是否引用当前证据。
- 是否说明为什么能/不能照做。
- 是否给出可行动下一步。
- 是否出现与库存冲突的幻觉。

样本较小时只表述“在本评测集上”，不得外推到真实抖音大盘。

## 9. 失败案例分类

至少保存以下失败：

| 类型 | 例子 | 修复方向 |
|---|---|---|
| 视觉误识别 | 把调料罐当主食材 | 用户确认、置信度和遮挡提醒 |
| 目标菜歧义 | 相似菜品名称混淆 | 菜名确认、标签和追问 |
| 检索错配 | 同食材但做法和时间完全不同 | 增加约束分项、降低纯 Jaccard 权重 |
| 反例污染 | 历史失败原因不适用于当前 | 明确可迁移/不可迁移证据 |
| 关键缺料冲突 | 缺主料却输出“可以完整做” | 规则后验检查和 negative case |
| 安全越界 | 根据照片判断新鲜度 | 禁止语义检测和用户确认 |

## 10. 验收条件

历史 case 检索只有同时满足以下条件才进入比赛主演示：

- 可以通过环境变量或开关关闭并回到 V0。
- 检索失败不影响生成主流程。
- 开发检验台显示 Top-K、分项分数和来源。
- A/B/C 三组使用同一测试集和同一模型配置。
- 至少一个核心规划指标改善，且安全指标不下降。
- 额外延迟和成本已经记录。
- 所有结论附带样本规模与数据边界。

如果没有测出稳定增益，检索保留为开发实验，不在路演中声称算法提升。

## 11. 当前实现与证据

截至 2026-07-13，本地已经实现：

- `data/case-memory/reference-cases.json`：24 条 `source=curated` 的独立参考 Case，同时包含 `accepted` 正例和 `rejected` 反例。
- `data/case-memory/retrieval-labels.json`：8 条结构化检索标签，不与 19 条规划 holdout 混用。
- `demo/agent/caseRetriever.mjs`：按本方案 V1 权重计算相似度，输出总分、分项、共同库存/缺料/约束和来源。
- 三档模式：`off`、`positive`、`contrast`。公网默认仍为 `off`，检索失败或关闭不阻断原规划链路。
- `/api/case-retrieval/preview`：不调用大模型即可查看 Top-K；开发检验台可选择路线和模式。
- Planner 可选接收 `retrievedCases`，提示词明确“当前确认事实优先、正例不可覆盖当前缺料、反例只用于避错”。
- `npm run eval:retrieval`：当前 8 条人工标签上 `Recall@4=100.0%`、`MRR@4=0.938`。

上述指标只说明确定性检索器能在当前小型人工标签集中找回预期 Case，不等于规划效果提升，也不代表真实用户分布。4 例先导消融与当前模型的完整 19 例规划消融均已完成，结果见下一节。重复运行和人工解释评分仍未开展；在当前比赛期限内不继续扩展这些实验。

## 12. 真实模型规划消融

`scripts/run-evals.mjs` 已增加 `--retrieval-mode off|positive|contrast`，规划请求会显式携带模式，报告同时保存服务端实际返回的模式、Case 数量、Case ID 和角色。该字段用于防止“命令写了 contrast，但服务端实际仍是 off”的假实验。

### 12.1 2026-07-15 无效尝试

首轮只选择 4 个高信息量规划用例：关键主料缺失、炖菜时间不足、目标菜名不确定、肉类状态不确定。实际情况如下：

- CloudBase 004 生产环境默认禁止请求级模式覆盖，最初的 positive/contrast 请求实际均返回 `mode=off`，因此全部作废，不作为检索增益证据。
- 本地开发模式的一例 contrast 请求确认实际命中 4 条 Case，包含正例和反例，规划用例通过；单例不足以形成消融结论。
- 随后的 positive 组统一收到 Right Code 上游 Cloudflare 502，属于 provider 网关故障，不是规划质量失败。
- 按外部请求最多重试两次的开发标准，本轮停止，不继续循环调用或为了实验临时部署多个云版本。

### 12.2 2026-07-16 有效 A/B/C

本轮改用本地开发服务，确保请求级 `retrievalMode` 可以生效；三组均使用相同的 4 个用例、`gpt-5.6-sol` 和 120 秒单例超时。评测报告保存服务端实际返回的模式、Case ID、正反例角色、延迟和 provider token usage。

| 组别 | 实际模式 | 通过 | Schema / 动作 / 安全 | 平均 / P95 延迟 | 总 token | 相对 V0 |
|---|---|---:|---|---:|---:|---:|
| A | `off`，0 条 Case | 4/4 | 100% / 100% / 100% | 48.6s / 84.9s | 12,908 | 基线 |
| B | `positive`，每例 4 条正例 | 4/4 | 100% / 100% / 100% | 37.3s / 44.2s | 14,652 | +13.5% |
| C | `contrast`，每例至少 1 条反例 | 4/4 | 100% / 100% / 100% | 32.7s / 42.2s | 14,539 | +12.6% |

三组的 Schema、动作、必需证据、关键缺料和安全门禁全部通过，未测得核心规划质量指标改善。目标菜名不确定用例在 C 组从 `cook_simplified` 变为 `prep_for_tomorrow`，但两者均属于预先允许动作，不能据此声称增益。B/C 延迟在单轮中低于 A，但没有重复运行，且模型延迟波动明显，不能解释为检索加速。

结论：当前结构化 Case 能被正确检索并进入 Planner，但在这 4 个高信息量样例上只增加了约 12.6%-13.5% 总 token，没有产生可证明的质量增益。公网继续使用 `CASE_RETRIEVAL_MODE=off`，U07 embedding 扩展延期；检索保留在开发检验台作为可解释实验，不进入主演示。

### 12.3 2026-07-18 当前 terra 完整 19 例 A/B/C

模型路由改为 `gpt-5.6-terra` 后，使用全部 19 条规划 holdout 重跑三组。评测器强制检查 `source=model`、服务端实际检索模式及角色组成，并保存结构化输出、provider、model、延迟与 token usage。

| 组别 | 实际模式 | 通过 | 平均 / P95 延迟 | 总 token | 相对 V0 |
|---|---|---:|---:|---:|---:|
| A | `off`，0 条 Case | 19/19 | 19.32s / 28.03s | 75,487 | 基线 |
| B | `positive`，仅正例 | 19/19 | 21.08s / 37.38s | 89,977 | token +19.2%，平均延迟 +9.1% |
| C | `contrast`，含正反例 | 18/19 | 22.43s / 31.67s | 93,641 | token +24.0%，平均延迟 +16.1% |

`contrast` 唯一失败是素食麻婆豆腐用例：动作从 V0 的 `cook_now` 改为 `shop_then_cook`，超出该用例允许动作；这不是 Schema 或上游失败。B 组没有产生门禁可测的质量提升，却增加成本和延迟。由此，4 例先导结论在完整 19 例上得到更强支持：当前检索没有收益证据，正反例上下文还会在一例上改变为更差动作。

当前决定保持 `CASE_RETRIEVAL_MODE=off`。后续只有引入新的独立评测集并证明质量增益、安全不下降且成本可接受时，才重新评估启用；不继续扩展 embedding。

路演口径：

- `[可讲]` 我们没有因为做出了检索模块就默认上线，而是用同模型、同用例做消融；小样本中质量指标持平但 token 增加，因此比赛版本主动关闭检索。
- `[可讲]` 检索层和正反例上下文仍保留为可审计实验，主链路优先采用更短、更稳的结构化规划。
- `[不要说]` 历史 Case 提升了规划准确率、降低了延迟，或已经证明适用于真实抖音用户分布。
