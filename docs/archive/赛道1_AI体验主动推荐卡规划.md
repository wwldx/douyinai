# 赛道 1：AI 体验主动推荐卡规划

更新日期：2026-05-23  
赛道：AI 体验：刷到懂你的瞬间  
默认模型策略：优先调用 GPT / Claude 高阶模型，接口层保留可切换能力  
当前定位：少输入、强上下文、主动弹出的校园即时推荐卡

## 1. 当前共识

赛道 1 不应该做成“用户填一堆信息，然后 AI 给建议”的表单工具。它更像抖音信息流里的智能推荐广告：系统已经根据用户授权上下文知道一些信息，在合适时刻主动弹出一张有用卡片。

因此 Demo 中可以使用模拟数据，但模拟的是“已授权上下文”，不是让评委现场手动填写大量信息。

核心原则：

- 用户输入越少越好，最多做轻反馈。
- 上下文由系统提前拿到或模拟得到。
- AI 根据上下文判断当前最该推什么。
- 输出必须是可执行行动，不是泛泛建议。
- 页面形态应像信息流推荐卡，而不是问卷、聊天框或配置面板。

## 2. 一句话定位

AI 根据你的时间、位置、天气、课程、任务和偏好，在信息流中主动弹出当前最值得做的一件事。

候选产品名：

- 校园此刻卡
- NowCard 校园即时推荐
- 刷到懂你的校园助手

建议最终表达：

> 一张会看时机的校园 AI 推荐卡，让学生不用搜索、不用填表，刷到就知道现在该做什么。

## 3. 目标用户与触发时刻

目标用户：

- 在校园里高频做轻决策的大学生。
- 对吃饭、赶课、DDL、活动、休息等即时场景有选择困难的人。
- 游园会现场评委、游客和其他选手。

触发时刻：

- 下课后不知道去哪吃饭。
- 快到上课时间，需要顺路完成一件事。
- 晚上临近 DDL，需要马上开始最低可交付版本。
- 小雨、降温、路程变化导致原计划不适合。
- 刷到某个校园活动，但系统判断它和当前用户高度相关。

## 4. Demo 中的模拟上下文

Demo 可以预置 3 到 5 个“已授权上下文快照”。这些数据不在主流程里让用户填写，只作为系统判断依据。

示例上下文：

```json
{
  "user": {
    "persona": "大三计科学生",
    "interests": ["AI", "竞赛", "高效率"],
    "preference": ["省时间", "少排队", "热食"],
    "recentFeedback": ["不喜欢太远", "更想要可直接执行的建议"]
  },
  "context": {
    "campus": "高新校区",
    "location": "信智楼",
    "time": "17:45",
    "weather": "小雨，18 度",
    "nextClass": "19:00 算法课，地点 GT-C102",
    "availableWindow": "75 分钟"
  },
  "signals": {
    "unfinishedTask": "明天 10:00 前提交 AI 黑客松作品说明文档",
    "mealState": "午饭较早，晚饭未吃",
    "activityNearby": "18:30 有 AI 创变者计划围炉会"
  }
}
```

路演口径：

> 当前 Demo 使用模拟授权上下文验证体验闭环。真实产品中，这些信号可以来自用户授权的位置、天气、课表、日程、校园活动库、历史反馈和实时校园服务数据。

## 5. 核心体验闭环

主流程：

1. 用户进入信息流式页面。
2. 系统展示一张“此刻推荐卡”。
3. 卡片直接说明：
   - 为什么现在推给你。
   - 推荐你做什么。
   - 预计花多久。
   - 下一步怎么执行。
4. 用户只需点击：
   - `去做`
   - `换一个`
   - `不感兴趣`
   - `保存`
5. AI 根据反馈生成下一张更贴合的推荐卡。

30 秒演示路径：

1. 打开 Demo，页面自动显示“现在最适合你的卡片”。
2. 展示系统上下文摘要，例如“小雨、离算法课 75 分钟、晚饭未吃”。
3. AI 推荐“先去二楼热餐窗口，18:25 前吃完，顺路回 GT-C102”。
4. 点击“换一个”，AI 改推“围炉会前 20 分钟准备 pitch”。
5. 点击“保存”，生成一条可复制行动提醒。

## 6. 推荐卡类型

MVP 建议做 4 类卡，不要做更多。

| 卡片类型 | 触发信号 | 输出内容 | 现场效果 |
|---|---|---|---|
| 饭点决策卡 | 时间、天气、位置、偏好、课程窗口 | 去哪吃、为什么、预计时间、邀约文案 | 共情强、容易试玩 |
| DDL 急救卡 | 任务、剩余时间、当前精力 | 15 分钟行动、最低可交付版本、求助文案 | AI 价值明确 |
| 活动机会卡 | 兴趣、空闲窗口、活动库 | 是否值得去、适合原因、准备事项 | 贴合校园 |
| 状态修复卡 | 连续上课、天气、疲劳状态 | 休息/补给/路线建议 | 体验细腻 |

MVP 主推：

1. 饭点决策卡：最容易让游客理解。
2. DDL 急救卡：最容易体现 AI 生成能力。
3. 活动机会卡：和比赛现场强相关。

## 7. AI 角色设计

AI 不只是写文案，而是参与四个关键环节：

- 上下文理解：把时间、地点、天气、课表、任务、偏好合并成当前状态。
- 推荐决策：判断现在最值得推哪类卡。
- 个性化解释：说明为什么这条建议适合当前用户。
- 反馈重排：用户点“换一个”或“不感兴趣”后，生成更合适的下一条。

推荐逻辑可以先用规则做候选召回，再让模型排序和生成：

```text
上下文快照
  -> 规则召回 3 到 5 个候选行动
  -> GPT / Claude 选择最合适的 1 个
  -> 输出固定 JSON
  -> 前端渲染推荐卡
  -> 用户反馈
  -> 模型生成下一张卡
```

这样做的好处是现场更稳：规则保证不会跑偏，模型负责让推荐更像“懂我”。

## 8. 模型调用策略

默认使用 GPT 或 Claude 中效果更好的一个，接口层不要绑定死。

建议策略：

| 用途 | 首选 | 备选 | 说明 |
|---|---|---|---|
| 上下文理解与推荐排序 | GPT 高阶模型 | Claude 高阶模型 | 要求稳定输出 JSON |
| 行动卡文案生成 | Claude 高阶模型 | GPT 高阶模型 | Claude 文案解释通常自然，实际以测试为准 |
| 兜底 | 本地缓存 JSON | 规则模板 | 接口失败时仍能演示 |

工程上建议抽象为：

```text
LLMProvider
  - provider: "openai" | "anthropic" | "mock"
  - model: configurable
  - generateRecommendation(context, feedback)
```

不要在前端写死模型名。模型名放在环境变量或后端配置里。

## 10. Prompt 草案

系统提示词：

```text
你是一个校园信息流 AI 推荐系统。你的任务不是聊天，而是根据用户已授权上下文，主动生成一张当前最值得展示的推荐卡。

要求：
1. 用户输入很少，因此你必须主要依据上下文判断。
2. 推荐必须具体、可执行、有时间和地点约束。
3. 不要泛泛建议，不要输出长篇解释。
4. 如果上下文不足，只能基于已知信息保守推断。
5. 输出必须是 JSON，不要输出 Markdown。
```

用户提示词模板：

```text
这是用户当前上下文：
{context_json}

这是用户刚才的反馈：
{feedback_json}

请选择此刻最适合主动弹出的推荐卡，并输出固定 JSON。
```

## 11. 页面结构

建议做成单页体验：

| 区域 | 功能 | 优先级 |
|---|---|---|
| 顶部状态条 | 产品名、当前时间、模拟上下文状态 | 中 |
| 信息流区域 | 展示当前推荐卡 | 高 |
| 上下文小面板 | 折叠展示系统已知信息 | 高 |
| 轻反馈按钮 | 去做、换一个、不感兴趣、保存 | 高 |
| 行动结果区 | 保存文案、分享文案、提醒文案 | 高 |
| Demo 控制区 | 切换模拟用户和场景 | 中，仅供演示 |

注意：Demo 控制区不能喧宾夺主。它是为了演示不同上下文，不是让真实用户填表。

## 12. MVP 开发拆分

第一阶段：静态可演示

- 预置 3 个用户上下文。
- 预置 6 到 8 张推荐卡 JSON。
- 完成信息流卡片 UI。
- 完成“换一个”“保存”“不感兴趣”的状态切换。

第二阶段：接入 GPT / Claude

- 写后端 `/api/recommend`。
- 输入上下文和反馈。
- 调用模型输出 JSON。
- 增加 JSON 校验和失败兜底。

第三阶段：体验增强

- 加推荐理由高亮。
- 加行动提醒复制。
- 加“为什么推给我”折叠解释。
- 准备录屏和离线缓存。

## 13. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 被质疑数据是模拟的 | 可信度下降 | 明确说是模拟授权上下文，验证体验闭环 |
| AI 技术感不如视觉赛道明显 | 评委不易感知 | 强调推荐排序、上下文理解、反馈重排 |
| 像普通广告推荐 | 创新性不足 | 输出必须是行动卡，而不是商品广告 |
| 模型输出不稳定 | Demo 中断 | JSON schema 校验 + 缓存卡片 |
| 用户输入过多 | 偏离赛道 | 主流程只允许轻反馈 |

## 14. 评分点对齐

| 评分关注 | 对齐方式 |
|---|---|
| 场景洞察 | 校园即时决策高频、碎片化、强共情 |
| 用户价值 | 用户不用搜索和填表，直接获得当前行动 |
| 体验完整性 | 刷到卡片 -> 理解原因 -> 点击反馈 -> 生成下一步 |
| AI 能力结合 | AI 负责上下文理解、推荐排序、个性化解释和反馈重排 |
| 创新性 | 从被动问答变成主动上下文推荐 |

## 15. 现场讲解脚本

60 秒版：

```text
我们做的是一张会看时机的校园 AI 推荐卡。

它不是让用户先填问卷，也不是聊天机器人，而是像信息流一样，在系统已经获得用户授权上下文后，主动判断现在最值得提醒什么。

比如现在是 17:45，小雨，用户在信智楼，19:00 有算法课，而且晚饭还没吃。系统会直接弹出一张卡：建议先去二楼热餐窗口，18:25 前吃完，顺路回教室。

用户只需要点去做、换一个或者不感兴趣，AI 会根据反馈继续调整下一张卡。我们想验证的是：AI 能不能从“你来问我”，变成“我在正确时刻帮你少做一次选择”。
```

## 16. 最终建议

赛道 1 可以并行推进，但不要和赛道 2 抢同一个产品形态。它应该独立成一个“主动推荐体验”。

最小可行目标：

- 3 个模拟上下文。
- 4 类推荐卡。
- GPT / Claude 实时生成至少一张卡。
- 接口失败时缓存卡可完整演示。
- 主流程中用户只做轻反馈。
