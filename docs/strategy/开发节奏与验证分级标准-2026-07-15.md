# 开发节奏与验证分级标准

生效日期：2026-07-15  
适用范围：冰箱晚餐 Agent 大区赛 Solo 开发  
状态：当前开发流程的权威标准

## 1. 为什么建立本标准

项目当前的主要风险已经不是“代码完全不可用”，而是开发 Agent 把小改动扩张成计划、全量回归、部署、报告和多文档同步，导致功能推进速度明显下降。比赛仍有多项高价值功能、真实评测和最终展示待完成，不能在每个中间状态执行接近最终发布级别的验证。

本标准的目标是：

1. 默认优先形成完整、可展示的纵向功能，不把清晰需求机械拆成多轮 MVP。
2. 验证强度与改动风险匹配，不与“能运行多少命令”匹配。
3. 维护少量权威文档，避免同一事实在多处机械追加后互相矛盾。
4. 把完整评测、跨设备、回滚和安全归档集中到发布候选与功能冻结阶段。

### 2.3 过度、过早或可避免工作

| 工作 | 问题 | 后续处理 |
|---|---|---|
| 公网 ASR 成功后立即跑 10 条合成语音 | 这是接近发布候选的稳定性门禁，不能替代真人手机；在功能未冻结时收益低 | 保留结果，但以后只在 RC/最终验收运行，不随小改动重复 |
| ASR 部署后又跑规划模型抽测 | 规划代码和 provider 未被本次 ASR 改动触及，属于扩大验证范围 | 部署只验证受影响端点；跨端点回归放到集成检查点 |
| 先用必然可能命中缓存的 fixture 验证真实视觉 | 测试输入与“必须 `source=model`”目标冲突，制造了一次可避免的失败和诊断 | 真实模型抽测一开始就使用新哈希/非缓存输入 |
| 为单次非缓存视觉请求新增独立脚本 | 现有评测器或一次性命令可以完成，新增永久脚本增加维护面 | 当前文件先不折腾删除；以后一次性检查放 `/tmp`，预期复用至少 3 次才入仓库 |
| `live provider`、`endpoint smoke`、`constraint eval` 三个语音脚本分散 | 功能重叠、参数和输出格式重复 | 功能冻结前不再扩展；RC 阶段再合并为一个语音验收入口 |
| 每个子步骤后重复 `check`、全量规则回归、`build`、生产 smoke | 验证级别高于改动风险，且多次覆盖相同代码 | 一个功能只在完成纵向切片后跑一次目标测试；全量命令只在集成/发布阶段运行 |
| 同一状态同步到 4 份文档 | 内容重复，出现“003/004”“候选/已部署”并存，维护成本高 | 状态只写一处，其他文档链接引用；不再逐步骤同步所有文档 |
| 小改动也创建计划、报告和证据文档 | 计划成本超过改动本身，且产生更多待维护文件 | 预计少于 2 小时、无跨模块合约变化的任务不新建 plan |
| 功能未冻结时反复 UI polish | 后续功能会改变布局，早期精修容易返工 | 当前只修阻断操作、溢出和歧义；统一视觉精修放到功能冻结后 |

从 004 部署后的动作类别看，3 类是当前立即需要的发布证据，至少 4 类可以推迟或避免。这个结论只用于纠正流程，不把已产生的合成语音结果或脚本伪装成新功能产出，也不为“清理这些文件”再启动一轮低价值重构。

## 3. 默认开发模式：完整纵向切片

需求和验收条件清楚、Agent 有能力一次完成时，默认直接实现完整纵向切片：

```text
用户入口 -> 状态管理 -> API/规则 -> 结果展示 -> 错误降级 -> 一次目标验证
```

禁止把同一个清晰功能机械拆成“占位按钮 -> MVP -> 补接口 -> 补文案 -> 补状态 -> 再重构”多轮。只有以下情况才允许先做 MVP：

- 产品假设尚未确定，需要低成本验证用户价值。
- 外部 API、权限或数据能否获得未知。
- 完整方案存在明显安全风险，需要先验证边界。
- 单次范围超过半天且能按独立可验收子系统自然拆分。

界面必须同时满足按钮语义清楚、主路径可操作、失败可回退；但非阻断性的阴影、间距、色彩和动画不在功能阶段反复精修。

## 4. 验证分级

| 级别 | 适用改动 | 当下最多执行 | 明确禁止 |
|---|---|---|---|
| V0 文档/文案 | Markdown、注释、非行为文案 | 人工查看 diff；必要时检查链接一次 | `npm run check`、build、部署、哈希、全量测试 |
| V1 小型局部改动 | 单模块、小样式、无合约变化 | 语法检查或一个目标单测；人工看一次受影响页面 | 全量回归、打包、跨设备、创建新计划 |
| V2 完整功能切片 | 新入口、新 API、状态流、规则引擎 | 目标测试 + 一次本地主路径；涉及前端构建时 build 一次 | 每完成一个子文件就回归；无关模型端点抽测 |
| V3 集成/云版本 | 多功能合并、环境变量、provider、部署 | 一次全量 check/build/smoke；严格 health；每个受影响外部端点一次 | 重复调用所有未受影响端点；批量准确率与跨设备大全套 |
| V4 RC/最终冻结 | 提交前、路演前、版本冻结 | 完整评测、真机/浏览器矩阵、随机输入、限流、安全、回滚、包哈希、录屏 | 验收中继续加非 P0 功能 |

例外：密钥泄漏、数据损坏、支付、食品安全结论或公共接口破坏可以立即提升验证级别，但必须先说明具体风险，不能用“更稳妥”泛化扩大范围。

## 5. 时间与停止条件

| 工作类型 | 默认预算 | 超时动作 |
|---|---:|---|
| 文档/文案小改 | 5-15 分钟 | 超过 20 分钟立即停止，说明为何不是小改 |
| 局部修复 | 15-45 分钟 | 达到 45 分钟仍未定位，先报告根因和下一步 |
| 完整中型功能 | 1-3 小时 | 先完成纵向切片，不追加旁支；超过 3 小时重新收敛范围 |
| 云版本发布验收 | 30-60 分钟 | 外部请求最多重试 2 次；失败后记录，不盲目循环 |
| RC 完整验收 | 单独排期 | 只在功能冻结后执行 |

附加硬规则：

- 功能冻结前，验证与文档时间原则上不超过该功能总时间的 20%；安全例外需说明。
- 一个失败先判断是否由测试选择错误、已知缓存或外部依赖导致，再决定是否修代码。
- 已知且符合设计的 fallback 不继续追成“全绿”。
- 一次性网络诊断不新建仓库脚本；预计至少复用 3 次或容易人工误操作时才固化。
- 未经用户要求，不 commit、不 push、不整理公开镜像、不扩展到相邻项目。

## 6. 计划触发条件

以下任一成立才创建或更新实施计划：

- 跨 3 个以上模块并改变数据流或 API 合约。
- 需要数据库迁移、部署架构变化或不可逆操作。
- 预计实现超过 3 小时。
- 用户明确要求比较方案或制定计划。

否则只在开始前写一句任务边界：

```text
本次交付：<一个可验收结果>
不做：<明确排除项>
预算：<时间>
验证：V0/V1/V2
```

禁止为同一功能同时创建升级计划、实施计划、部署计划和验证计划。当前项目只保留 `docs/roadmap/大区赛升级总计划-2026-07-13.md` 作为优先级入口。

## 7. 权威文档治理

### 7.1 目标结构

后续应逐步收敛为以下几类，而不是继续新增平行摘要：

| 文档类型 | 唯一职责 | 更新方式 |
|---|---|---|
| `AGENTS.md` | 稳定约束、权威入口、不可违反的产品/安全边界 | 定期重写；不记录逐次进度和测试流水 |
| 当前基线 | 从零重建当前版本所需的运行方式、接口、数据和部署事实 | 功能集成后替换相关章节，不在末尾机械追加 |
| 产品规格 | 场景、功能、页面、按钮语义、状态、失败路径和验收条件 | 设计变化时修改原章节，废弃设计直接标记替代关系 |
| 架构规格 | 模块边界、数据流、API 合约、模型路由和安全约束 | 合约变化时更新 |
| 变更记录 | 按日期记录已完成事实、兼容性影响和回滚点 | 每个完整功能最多一条 |
| `AGENT_STATE.md` | 当前唯一在途任务、外部阻塞和接下来 3-5 步 | 通过替换保持短小，不复制历史证明 |
| 升级总计划 | 候选优先级、状态和是否进入关键路径 | 只在优先级或状态改变时更新 |
| 部署记录 | 实际发布版本、配置、回滚点和最终验收 | 只在部署时更新 |

### 7.2 当前约束

- 不再为同一个状态同时更新 `AGENTS.md`、`AGENT_STATE`、升级总计划和部署计划。
- 小改只写一条变更记录；没有长期决策变化时不改 `AGENTS.md`。
- 旧设计被替代时修改权威章节并写“由 X 替代”，不在文末新增另一套当前方案。
- 每到功能冻结或文档明显冲突时进行一次集中重整；重整本身不得夹带研究、功能开发、Git 同步或全量测试。
- 当前 4 个语音/公网辅助脚本先冻结，不立刻删除；RC 阶段再决定合并，避免为纠正过度工程继续过度工程。

### 7.3 路演叙事资产

开发中形成的“一句话价值、评审锚点、技术取舍、能力边界、失败降级和现场讲解句”统一称为**路演叙事资产**。这类内容不是聊天附属品；若能帮助作品说明、路演、海报或答辩，应在当轮就地写回最相关的权威产品、算法或部署文档，避免最后总结时重新回忆。

归档规则：

- `[可讲]`：已有实现或证据支撑，可以直接用于对外材料。
- `[待验证]`：表达方式有价值，但事实或指标尚未验收，保留为后续验证目标。
- `[不要说]`：容易夸大能力、混淆模型与规则或超出安全边界的说法。
- 每次只保存 1-5 句高价值表述，不复制整段聊天，不为单条说法新建文档。
- 优先修改对应章节或增加“路演讲法”小节；同一说法不在多个文件机械重复。
- 功能被替代时同步改写旧讲法，避免最终材料继续引用失效设计。

Agent 在结束一个完整功能切片前，应额外判断一次：“本轮是否形成了以后能直接讲的产品或技术表述？”有则归档，无则不强行编造。

## 9. 每次结束前自检

- 我完成的是用户要求的交付，还是擅自增加了研究、审查、同步或发布？
- 验证级别是否高于改动风险？
- 是否为一次性命令新增了永久脚本？
- 是否把同一事实重复写进多个文档？
- 是否在功能未冻结时做了最终级 UI 或全量测试？
- 如果现在停止，新增产出中有多少是用户可见功能？
- 本轮是否形成了值得保留的路演叙事资产；若有，是否已就地归档并标明可讲范围？

任一项回答不合理，立即停止扩张，回到本次任务边界。
