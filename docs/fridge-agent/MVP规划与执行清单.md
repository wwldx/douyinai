```text

  -> 缺料就给抖音商城/本地生活模拟补齐
  -> 做完后可生成生活记录/Vlog 草稿
```

这个故事链用于回答“为什么是抖音”：普通聊天机器人主要回答菜谱问题，抖音场景可以把内容种草、现实库存、交易补齐和内容生产连成闭环。

目标菜复刻结果不使用“可做指数”或分数，因为现场难以解释计算依据。表达方式改为：

```text
尽量复刻路线 + 难点提醒 + 简化版本 + 补买/明日准备建议
```

## 1. 产品目标

让用户拍一张冰箱照片后，在 30 秒内得到一个现实可执行的晚餐方案。

系统需要回答三个问题：

1. 冰箱里大概有什么。
2. 这些东西能不能做出今晚满意的一顿饭。
3. 如果不能，应该补买什么，或是否应该直接外卖。

## 3. Demo 食材选择

为了降低识别风险，演示图片应使用容易识别的材料。

优先食材：

| 类别 | 推荐样例 | 原因 |
|---|---|---|
| 蔬菜 | 番茄、黄瓜、生菜、胡萝卜 | 颜色明显、形状稳定 |
| 蛋奶 | 鸡蛋、牛奶、酸奶 | 识别稳定，菜谱通用 |
| 主食 | 面条、面包、米饭、速冻饺子 | 容易生成晚餐方案 |
| 蛋白质 | 火腿肠、鸡胸肉包装、豆腐 | 可扩展菜谱 |
| 饮料 | 可乐、矿泉水、果汁 | 增加真实冰箱感 |
| 调味线索 | 酱油、辣酱、沙拉酱 | 只作为辅助，不强依赖 |

避免食材：

- 保鲜盒里的剩菜。
- 被袋子遮住的散装肉。
- 半透明包装里的模糊食材。
- 堆叠严重、光线太暗的冰箱。
- 需要专业判断新鲜度的食材。

## 4. 核心流程

```text
用户上传冰箱图片
  -> 视觉模型识别食材
  -> 生成可编辑库存卡
  -> 用户轻量确认
  -> 结合画像和时间约束
  -> 生成晚餐方案
  -> 输出保底菜 / 进阶菜 / 缺料清单 / 外卖兜底
```

## 6. 模型调用策略

优先使用 GPT / Claude 高阶视觉模型。

建议拆成两个模型任务：

1. 视觉识别：从图片中识别食材和包装线索。
2. 晚餐规划：结合食材、用户画像和时间约束生成方案。

工程接口：

```text
FridgeVisionProvider
  - provider: "openai" | "anthropic" | "mock"
  - analyzeFridge(image)

DinnerPlannerProvider
  - provider: "openai" | "anthropic" | "mock"
  - planDinner(inventory, userContext)
```

可以先用同一个高阶模型完成两个任务，但代码层面建议拆开，方便后续替换。

## 9. Prompt 草案

### 视觉识别 Prompt

```text
你是一个冰箱食材视觉识别助手。请从用户上传的冰箱照片中识别可见食材、饮料、速食和包装线索。

要求：
1. 只识别图片中能看到的内容，不要编造。
2. 对被遮挡或不确定的物品，放入 uncertainItems。
3. 不要判断食材一定新鲜，只能说“看起来可用”或“需要用户确认”。
4. 输出固定 JSON，不要输出 Markdown。
```

### 晚餐规划 Prompt

```text
你是一个现实主义晚餐规划 Agent。你需要根据冰箱库存、用户厨艺、口味偏好、近期饮食和今晚可用时间，推荐一顿现实可执行的晚餐。

要求：
1. 不要只给菜谱，要先判断今晚适不适合自己做。
2. 新手用户不要推荐高风险动作，例如油炸、复杂刀工、处理整鱼整鸡。
3. 推荐必须考虑可用时间，时间很晚时优先简单菜、速食或外卖兜底。
4. 至少输出一个现有材料可做的保底方案。
5. 如果缺料，只推荐 1 到 3 个关键补买项。
6. 商业建议必须克制，不能硬推消费。
7. 输出固定 JSON，不要输出 Markdown。
```

## 10. 商业化表达

可以讲商业延展，但要注意表达方式。

不建议说：

> 勾引用户消费。

建议说：

> 在用户真实晚餐决策中，自然衔接生鲜补货、外卖兜底和厨具升级建议。

可展示的商业场景：

| 场景 | 表达方式 |
|---|---|
| 缺少青菜 | 推荐补买一把青菜，提升菜品完整度 |
| 时间太晚 | 推荐外卖或速食兜底 |
| 经常做低油炸物 | 温和建议空气炸锅 |
| 长期重复外卖 | 推荐简单自炊计划 |

关键原则：商业推荐必须服务于用户当下决策，不能喧宾夺主。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 冰箱识别不准 | 推荐材料错误 | Demo 使用清晰样例，加入用户确认 |
| 食材新鲜度误判 | 安全风险 | 明确模型不能判断过期，要求用户确认 |
| 菜谱难度过高 | 用户执行失败 | 根据厨艺约束推荐，新手默认保守 |
| 推荐不考虑时间 | 不现实 | 必须输入可用时间，并在 prompt 中硬约束 |
| 商业推荐太硬 | 价值观风险 | 用“补货/兜底/升级建议”表达 |
| 功能太多 | Demo 发散 | MVP 只围绕今晚一顿饭 |

## 12. 评分点对齐

| 评分关注 | 对齐方式 |
|---|---|
| 用户价值 | 解决“今晚吃什么”这个高频问题 |
| AI 能力结合 | 视觉识别、偏好理解、时间约束和安全规划共同决策 |
| 体验完整性 | 拍冰箱 -> 确认库存 -> 推荐晚餐 -> 缺料/外卖兜底 |

| 现场表现 | 食材图直观，演示结果容易理解和讨论 |

## 14. 60 秒讲解脚本

```text
我们做的是冰箱晚餐 Agent，选择视觉搜索赛道。

很多人晚上回家打开冰箱，其实不是想知道里面有什么，而是想知道今晚到底吃什么。我们让用户拍一张冰箱照片，AI 先识别可用食材，再结合用户的厨艺水平、口味偏好、最近吃饭记录和今晚可用时间，给出一个现实可执行的晚餐方案。

比如用户是新手，今晚只有 25 分钟，那系统不会推荐复杂硬菜，而是优先给出番茄鸡蛋面这种低失败率方案。如果材料不够，它会告诉你补买一两样关键食材；如果时间太晚，也会建议速食或外卖兜底。

所以它不是单纯识别食材，也不是普通菜谱搜索，而是从真实冰箱状态出发，帮用户完成今晚这一餐的决策。
```

## 16. Agent 架构决策

当前继续使用轻量两段式 Agent：

```text
视觉识别 Agent
  -> 输出结构化库存
  -> 人工确认
目标菜图识别 Agent
  -> 输出菜名猜测 / 关键材料 / 工具 / 难点
  -> 用户可手动修改目标菜名
晚餐规划 Agent
  -> 读取确认库存 + 用户上下文 + 画像 traits
  -> 输出晚餐决策 JSON
目标菜复刻规划 Agent
  -> 读取确认库存 + 目标菜文字 + 用户画像
  -> 输出尽量复刻路线 / 缺料 / 难点提醒 / 商城模拟卡
```

暂不引入 LangChain、LangGraph、Dify 等成熟框架。

原因：

- 当前流程仍然是少量轻量 Agent，状态简单，原生 Node.js 更稳。
- 比赛 demo 的风险主要是模型耗时、网络不稳、识别误差和展示节奏，不是复杂编排。
- 重框架会增加依赖、调试成本和现场不确定性。
- 当前 JSON 合约清晰，后续迁移框架也容易。

后续触发迁移框架的条件：

- 出现 3 个以上工具/Agent，需要状态图管理。
- 需要多轮追问和可回滚分支流程。
- 需要长期任务、异步步骤、人工审批节点。
- 需要更完整的 memory/tool tracing。

届时优先评估：

- LangGraph：适合状态图、多节点编排、可控回滚。
- OpenAI Agents SDK：适合工具调用、追踪和 OpenAI 生态集成。
- Dify：适合快速搭建后台工作流，但比赛本地 demo 的可控性较弱。

## 18. 抖音生态亮点规划

当前差异化主线：

> 刷到想吃的，拍下冰箱，AI 判断今晚能不能复刻。

这条链路比“拍冰箱问菜谱”更适合抖音：

- 内容种草：用户在抖音刷到一道想吃的菜。
- 现实检查：拍冰箱确认已有材料和不确定食材。
- 决策支持：结合用户画像判断今晚能不能做、难点在哪里。
- 交易补齐：缺关键材料时展示抖音商城/本地生活模拟卡。
- 内容回流：做完后上传成品图，生成生活记录或 Vlog 草稿。

阶段实现：

1. V1 已实现：目标菜文字输入，例如“我今晚想吃番茄牛腩”。
2. V1 已实现：`/api/plan-target-dish` 输出目标菜、缺料、替代路线、难点提醒、模拟 commerceCards。
3. V2 已实现：支持第二张目标菜图片，先识别菜名和关键材料，再让用户确认或修改。
4. V2.5 待实现：多图自动分类，一次上传多张图后由 AI 判断哪张是冰箱、哪张是目标菜。该功能先不进入主流程，避免现场误分类。
5. V3 待实现：饭后上传成品图，生成抖音标题、封面文案、旁白、分镜和标签。

目标菜结果设计原则：

- 不展示可做指数或分数。
- 当前使用两个明确上传区，不做自动分类：冰箱照片只进冰箱识别，目标菜图只进目标菜识别。
- 语音只作为快捷输入，不作为主流程依赖；语音失败时必须能手动输入。
- 尊重用户想吃某道菜的意愿，先尽量给出可执行方案。
- 如果食材、时间、工具或厨艺不匹配，要温和提醒难点。
- 永远给至少一条不购买的替代路线。
- 商城/本地生活卡只在缺料、工具缺口或兜底场景出现。
- 厨具升级必须克制，例如空气炸锅只在目标菜依赖低油酥脆口感，且画像显示用户长期怕油烟、怕麻烦或低洗锅时出现。

语音输入策略：

- 当前采用可切换方案：浏览器录音，服务端 `/api/transcribe-audio` 调用 `ffmpeg` 转成 wav；默认 `SPEECH_TRANSCRIBE_PROVIDER=auto`，依次尝试已配置的腾讯云一句话识别、显式开启的 Audio Transcriptions API 和 `scripts/mac-speech-transcribe.swift` + macOS Speech Framework。
- 后端会用 `ffprobe/ffmpeg volumedetect` 做录音诊断；如果峰值音量过低，直接提示“录音几乎是静音”，避免把麦克风问题误判成模型问题。
- 识别结果只写入目标菜输入框；录音只在服务端临时目录转写，处理完成后删除，不保存到用户画像或 Git。
- 用户必须能手动修改文本后再调用复刻规划。
- 腾讯云 provider 使用 `TENCENTCLOUD_SECRET_ID`、`TENCENTCLOUD_SECRET_KEY` 和可选临时 Token；Secret 只保存在本机 `.env.local` 或 CloudBase Secret。Right Code 当前不支持本项目的 `/audio/transcriptions`，因此 `AUDIO_TRANSCRIPTION_ENABLED` 默认关闭。
- macOS 需要给启动本地服务的终端授予“语音识别”权限；如果提示权限被拒绝，到系统设置 -> 隐私与安全性 -> 语音识别里打开对应终端。
- 默认 `MAC_SPEECH_ON_DEVICE_ONLY=true` 且 `MAC_SPEECH_AUTO_FALLBACK=true`：优先设备端识别，如果设备端不支持或长时间没有返回，会自动回退到 macOS 系统识别。
- 如果比赛现场要求稳定语音，优先使用已通过 CloudBase 真机验收的腾讯云一句话识别；macOS Speech 只作为本地备用，文本始终是最终降级路径。
