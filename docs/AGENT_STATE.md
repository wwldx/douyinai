## 阶段 1 当前产品结构

手机是唯一设计权威；桌面只居中承载手机画布。

- S0 首屏：Feed 与冰箱两个真实时刻在同一舞台可逆互换，选路线前无进度。
- Feed：这道菜 → 现实冰箱对照 → 统一规划 → 目标菜行动单。
- 冰箱：拍冰箱 → 盘点与规划台 → 统一规划 → 自由推荐行动单。
- 统一规划状态：阶段提示、已用秒数、取消、超时提示与失败出口。
- 行动单：目标菜/自由推荐双变体、材料四态、模拟补购、已拿到、五类反馈与最近三版。
- 阶段 1 不含用户端救援、生活记录、先吃和冰箱整理入口。

## 本轮新增后端契约

- `/api/analyze-fridge`：`vision.sceneAssessment={kind,reason}`，模型三态为 `fridge | not_fridge | unusable`；旧空结果兼容为 `unknown`，不能推断空库存。
- `/api/analyze-fridge`：支持 `analysisMode:"fridge_detail"`，服务不确定项逐项补拍。
- `/api/analyze-target-dish`：`dishNameCandidates:string[]`，最多 3 个。
- 固定示例使用受控 `demoKey`；冰箱/菜图真实上传不再按普通文件名命中演示缓存。
- 两个 Planner 都读取 `timeBudgetId`；`flexible` 是“不赶时间”语义，做饭耗时不包含补购和配送。

## 固定边界

- 不保存 API Key、管理员令牌、认证头、原始照片或原始音频。
- 不自动判断过期、变质、气味、熟度或是否安全食用；用户确认始终是前置条件。
- 图片不是冰箱、图片不可用、模型失败与用户确认真实空库存必须保持不同状态。
- 模拟补购必须始终标成尚未真实购买；只有用户明确确认“已拿到”才可进入本次可用材料。
- 语音、相机和模型失败都必须有文字、换图、重试或人工确认兜底。
