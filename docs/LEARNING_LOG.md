# Learning Log

## 2026-07-21 - 前端重构验收必须同时核对状态快照、来源与真实请求

- React 中“先 set 库存、再立刻规划”可能读取旧闭包；跨场景请求应显式传入刚确认的数据快照，每个方案版本也要保存自己的请求快照，不能依赖当前页面 state 回推历史。
- “冰箱原有、模拟待补、用户已拿到、仍缺”是不同事实层。为了视觉简洁而合并数组，会直接造成库存污染和错误文案；展示层和 Planner 输入都应使用同一套结构化状态。
- 固定演示缓存不能按用户可控文件名命中。图片 hash 与受控 `demoKey` 可以保留现场稳定性，同时避免真实图片同名时被伪装成模型结果。
- 识别失败、图片不是目标场景、图片不可用、用户确认真实空库存必须是不同状态。旧结果缺字段且 items 为空时只能标为 unknown，不能替用户建立空库存事实。
- 不确定项的补拍结果也只是候选。用原不确定项 key 绑定近照结果、再由用户逐项确认，才能避免“为了少点一步”污染库存。
- 恢复模型要保存结构化事实而非原始媒体；进行中的请求刷新后应标为中断，不静默重放。浏览器验收除截图外，还应检查真实请求是否收到人工确认库存、版本切换是否保留来源、模拟状态是否跨刷新一致。

## 2026-07-19 - 评测、素材和发布验收必须使用同一条真值链

- 文件名不是图片真值。旧“黄焖鸡”素材实际更像干锅鸡块，继续调提示词只会把素材错误误归因于模型；正确顺序是先目检素材，再运行模型门禁，并保留旧文件作审计。
- 视觉评测输入要和展示端一致。本轮统一使用最长边 1400px JPEG，保留原始失败报告，再生成带新 request ID 或明确复用关系的最终报告，避免用“重跑成功”覆盖失败轨迹。
- 不确定项也可能是保守而正确的视觉行为。评测同时记录明确识别召回和“明确识别 + `uncertainItems` 覆盖”，才能避免鼓励模型为提高召回而硬猜；两者都不能包装成真实用户准确率。
- 消融不能只看通过数。`positive` 虽然同为 19/19，但没有质量增益且 token 增加 19.2%；`contrast` 为 18/19、token 增加 24.1%并出现动作退化，因此实验功能不应进入主演示。
- 浏览器验收应断言按钮唯一性、跨阶段状态、方案历史、两轮救援和双视口无溢出，而不只是保存截图。本轮 47/47 是本地 011 RC 证据，不能替代公网、iPhone、相机、麦克风或 CloudBase 持久化验收。
- Schema 合法和模型高置信度不能覆盖产品后置门禁。用户完全说不清做到哪一步时，`next_step` 必须由确定性规则降级为追问，避免模型在错误阶段给出具体操作。
- 内置浏览器运行时若因工具初始化错误不可用，可以降级到本地 headless Chrome，但报告必须写清工具边界、目标地址和视口；工具故障不能被写成产品故障。
- 当前发布顺序已经收敛为：011 本地门禁与制品冻结 -> CloudBase 定向验收 -> 当前版本 iPhone -> 回滚彩排与门户提交。新功能和前端大重构排在这条链之后。

## 2026-07-18 - 用运行记录和 provider 账单区分超时与 usage 故障

- 同一模型多次在应用门限的精确时间结束、返回 `MODEL_TIMEOUT` 且 provider 显示 0 token，通常表示请求在完整响应前被取消，不应先修 token 解析器。
- 对照一次接近门限但成功且 usage 正常的请求，可以快速排除 SSE usage 提取故障；随后只需比较少量候选模型，而不是重跑全量评测。
- JSON Schema 能保证数组元素是字符串，却不能阻止模型把两个逻辑元素和 JSON 引号拼进一个合法字符串。面向结果卡的关键列表应在模型后增加窄范围确定性清洗，并用真实失败样本写目标测试。

## 2026-07-14 - 模型路由要按任务评测，而不是按旗舰名统一配置

- 同一代模型的低价档不一定只是“更弱但更快”：luna 在固定视觉小集为 0/4，说明必须先过质量门槛；terra 与 sol 首轮同为 3/4，但平均延迟约快 3.1 倍，才具备路由价值。
- 平均延迟不能掩盖长尾。安全规划首次 120 秒超时、单例重跑 81 秒通过，应该同时保留两个事实，而不是用重跑覆盖原失败。
- 细粒度菜名存在视觉歧义和非确定性，产品需要把模型输出定位为候选，把用户确认定位为真实意图。
- Responses SSE 的 usage 可以作为请求级工程证据，但费用仍应以 provider 账单和当期单价为准。

## 2026-07-14 - 手动 ROI 比伪装自动检测更适合 Solo 视觉搜索

- 用户在暂停帧上主动框选，直接减少背景干扰并降低表达成本，已经满足“所见即所想”的交互价值。
- 浏览器裁剪是确定性操作；目标菜识别仍走既有视觉 Agent，组件边界清楚，失败时可恢复整图或改文字。
- 对外准确命名很重要：手动矩形选区不是模型定位，更不是像素级分割。诚实边界不会削弱 Demo，反而便于解释系统如何处理不确定性。

## 2026-07-14 - 内容回流也需要事实边界和可审计兜底

- 成品图能支持菜名猜测、颜色、摆盘和可见食材线索，但不能证明口感、营养、实际耗时或完整制作过程。
- “分镜”必须写成用户之后可补拍的建议，不能把没有上传的过程镜头描述成已经发生。
- 内容回流的稳定闭环不需要真实发布权限；可编辑草稿、人工确认和明确“不自动发布”已经能验证产品链路。
- 固定演示缓存必须在开发台标出 `model-timeout-cache` 或 `model-error-cache`，用户端也不能把缓存包装成实时模型事实。
- 模型端点的 TLS/网关错误与 Schema 错误需要分开记录。真实请求失败时，先拿诊断再决定是否重试，不能用缓存成功替代真实模型证据。

## 2026-07-13 - 食品视觉能力必须拆开“看见、推断和安全结论”

- 单张冰箱照片可以用于识别可见食材、包装和粗粒度分区，但不能据此证明食品未过期、未腐败或可以安全食用。
- 包装日期 OCR 只能作为候选，购买、开封和标签日期都需要用户确认；信息缺失时应该追问，而不是让模型补全。
- 冰箱整理适合用“视觉候选 + 用户确认 + 确定性规则 + 可视化箭头”的组合。LLM 负责理解和表达，安全规则和优先级不能交给自由生成。
- 复杂三维摆放会引入遮挡、容量、深度和空间关系误差。比赛版本只做门架、层架、抽屉等分区，既可评测，也更容易稳定演示。
- 对外价值应表述为减少遗忘、帮助优先处理和降低交叉污染风险，不能夸大为自动防腐败或食品安全保证。

## 2026-07-13 - 算法含量不等于训练规模

- OneReason 的完整路线是多粒度预训练、结构化 CoT SFT、分领域 GRPO，再通过 RFT 或 MOPD 统一。它依赖领域数据、reward、teacher、训练基础设施和长期实验，不能因为概念先进就迁移到 Solo 黑客松。
- FinFRE-RAG 类“结构化表示、相似 case 检索、正反例上下文、受约束生成”不需要训练底模，更适合个人项目形成可验证的算法增量。
- 算法可信度来自独立数据、基线、消融、失败案例、延迟和成本，而不是在架构图上增加 SFT、RL、蒸馏或多 Agent 名词。
- 参考论文方法时必须说明“借鉴了什么”和“没有复现什么”；没有真实结果前只能写假设和实验设计。

## 2026-07-13 - 获奖项目需要同时管理可见价值和后台证据

- 评委和观众首先感知首屏故事、真实图片、操作成本和结果是否有行动价值，因此正式界面不是可有可无的装饰。
- 好看但没有公网、真实模型和稳定兜底的页面无法满足非现场评审；只有后台评测但首屏看不懂，也难以获得游园传播和第一印象优势。
- 当前合理顺序是：公网与真实基线 -> Feed 优先界面 -> 满足反馈 -> 历史 case 检索 -> 消融与失败分析 -> 录屏和路演冻结。
- 项目推进应遵循“问题 -> 假设 -> 证据 -> 验证 -> 价值 -> 方法沉淀”，避免从模型名或技术名词反推需求。
