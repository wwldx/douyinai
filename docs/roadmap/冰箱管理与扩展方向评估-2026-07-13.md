# 冰箱管理与扩展方向评估

更新日期：2026-07-15  
状态：R0-R2 已实现；U20 已完成本地端到端、3 例真实模型与 005 iPhone 真机验收  
目标：判断“调整冰箱内食材位置、减少遗忘和浪费”能否成为大区赛亮点，并比较其他可扩展方向

## 1. 结论

这个方向可以真正实现，也有较强视觉记忆点，但必须换一个更可信的产品定义：

> 冰箱救援模式：拍一下冰箱，AI 识别食材和大致分区，用户确认开封/购买/标签日期后，系统给出“先吃哪些、移到哪里更容易看见、如何减少交叉污染”的建议，并把优先食材带回今晚的菜谱规划。

本次可以做：

- 识别食材位于门架、上层、中层、下层、果蔬抽屉等大致分区。
- 识别可见包装和日期候选，但日期必须由用户确认。
- 根据用户确认信息生成“先吃清单”。
- 用确定性规则给出分区移动建议。
- 用图片标记、分区卡和箭头展示移动前后。
- 重新拍照后让用户确认是否完成整理。

本次不能做：

- 仅凭照片判断食材已经过期、腐败或可以安全食用。
- 根据颜色和外观自动判断肉类、剩菜或开封食品安全。
- 声称调整位置能够保证食物不腐坏。
- 让通用 VLM 自由输出厘米级位置或复杂三维摆放方案。
- 把通用储存建议包装成医疗或权威食品安全结论。

推荐对外措辞是“减少被忘记、帮助优先处理、降低交叉污染风险”，不是“自动防过期、防腐烂”。

## 2. 为什么有获奖潜力

### 2.1 对评委和观众可见

普通菜谱生成的算法链路藏在后台，观众不一定能立刻感知差异。冰箱整理可以直接展示：

```text
原始冰箱照片
-> 标出“门架/上层/下层/抽屉”的食材
-> 三条移动建议
-> “先吃这些”优先队列
-> 整理后照片
```

移动箭头、颜色分区和前后对比具有明显的视觉传播性，适合游园展示和海报截图。

### 2.2 复用现有主线

它不需要新建独立产品：

- 复用 `/api/analyze-fridge` 的食材候选。
- 复用用户确认库存。
- “先吃清单”可以直接影响 `/api/plan-dinner` 的食材优先级。
- 历史 case 可以记录“某类位置建议是否被接受”。
- 结果仍然落到今晚吃什么，而不是另做一个冰箱管理 App。

### 2.3 增长与 ROI 更容易解释

相比只在“今晚吃什么”时使用，整理/先吃模式能形成更高频入口：

- 买菜后整理一次。
- 每周清理一次。
- 做饭前检查一次。
- 用户反馈哪些建议实际执行，形成复访和满足率。

可以用“先吃建议采纳率、整理完成率、重复使用率、优先食材进入晚餐方案的比例”衡量，不需要虚构真实减少浪费金额。

## 3. 食品安全边界

食品安全相关建议必须由规则和权威资料约束，不让 LLM 自由发挥。

可作为规则来源的公开材料：

- [USDA Refrigeration & Food Safety](https://www.fsis.usda.gov/food-safety/safe-food-handling-and-preparation/food-safety-basics/refrigeration)：冰箱应保持在约 4°C 或以下；生肉、禽肉、海鲜需要密封，避免汁液污染其他食物；门架温度波动更大，蛋应放原包装并置于层架。
- [FDA Are You Storing Food Safely?](https://www.fda.gov/consumers/consumer-updates/are-you-storing-food-safely)：不要塞得过满，保证冷空气循环；覆盖食品并及时清理溢出物；外观和气味不能证明不存在致病菌。
- [FoodSafety.gov FoodKeeper](https://www.foodsafety.gov/keep-food-safe/foodkeeper-app)：用于理解不同食品的储存与质量建议，若以后引入具体时长，应逐项核对来源和地区适用性。

产品实现中：

- 图片只能产生 `needsConfirmation`，不能产生 `safeToEat=true`。
- 日期来自包装 OCR 时必须让用户确认。
- 不知道开封/购买时间时，系统只追问，不推算。
- 高风险项只提示检查标签、温度、包装和存放信息，不给食用保证。

## 4. 分级实现

### R0：先吃清单

预计投入：0.5-1 天  
推荐级别：高，最小可行版本

流程：

1. 用户确认识别食材。
2. 对少量食材选择“刚买/已开封/快到标签日期/不确定”。
3. 可选输入购买日、开封日或包装日期。
4. 系统按已确认信息输出“今晚优先、这两天优先、无需提醒”。
5. 晚餐规划优先使用高优先级但安全信息已确认的食材。

核心限制：没有日期和状态就不排序为“快过期”，只列入待确认。

### R1：冰箱分区移动建议

预计投入：1-1.5 天  
推荐级别：中高，可作为可见亮点

视觉模型输出粗粒度位置：

```text
door / top / middle / bottom / crisper / freezer / unknown
```

规则引擎输出：

```json
{
  "item": "盒装鸡蛋",
  "currentZone": "door",
  "suggestedZone": "middle",
  "reason": "门架温度波动较大；请保留原包装并放到层架",
  "requiresUserConfirmation": true
}
```

展示端只画分区和移动箭头，不依赖精确 bounding box。

### R2：约束优化与前后对比

预计投入：1 天  
推荐级别：中，仅在 R0/R1 稳定后实施

将整理抽象为小规模约束分配：

```text
目标：最小化安全规则惩罚 + 被遗忘风险 + 移动成本
约束：分区容量、密封要求、类别允许区域、用户不愿移动项
输出：最多 3 条最值得执行的移动建议
```

这部分可以用确定性搜索或加权匹配完成，不需要让 LLM 求解。用户重新拍照后，系统只验证大致分区是否变化，不评价食品安全结果。

### R3：精确 AR 自动重排

预计投入：3-5 天以上  
推荐级别：拒绝进入本次比赛

它要求稳定目标检测、遮挡处理、深度/容量估计、多视角一致性和精确空间规划。当前多模态模型空间推理仍不稳定；例如 [SpatialMQA](https://arxiv.org/abs/2505.19015) 报告的多模态模型空间关系准确率与人类仍有显著差距。因此本次只做分区，不做精确三维放置或自动执行。

## 5. 建议数据结构

视觉输出增加候选字段：

```json
{
  "itemId": "item-01",
  "name": "盒装鸡蛋",
  "category": "protein",
  "approximateZone": "door",
  "zoneConfidence": 0.82,
  "labelDateCandidate": null,
  "needsConfirmation": ["位置", "标签日期", "包装完整性"]
}
```

用户确认状态：

```json
{
  "purchaseDate": null,
  "openedDate": null,
  "labelDate": null,
  "userUrgency": "unknown",
  "doNotMove": false
}
```

先吃优先级只能使用用户确认字段：

```text
priority =
  0.40 * confirmed_date_urgency
  + 0.20 * confirmed_opened_state
  + 0.15 * visibility_risk
  + 0.15 * current_meal_relevance
  + 0.10 * user_intention
```

权重是待验证假设；没有已确认日期时，`confirmed_date_urgency` 必须为 0。

## 6. 评测方案

| 指标 | 说明 |
|---|---|
| zone accuracy | 模型识别门架/层架/抽屉的准确率 |
| rule violation rate | 输出是否违反确定性储存规则 |
| date hallucination rate | 未提供日期时是否编造临期判断，目标为 0 |
| suggestion acceptance | 用户是否采纳移动或先吃建议 |
| before/after completion | 用户是否完成建议的大致分区变化 |
| added latency | 新链路增加的 P50/P95 延迟 |

第一版准备 10-15 张人工标注分区的冰箱图即可验证链路，但只能描述为小样本 Demo 评测。

## 8. U20：做到一半卡住了

### 8.1 产品定义

结果页增加“做到一半卡住了”入口。用户拍摄当前锅内或盘中画面，选择问题类别，并可用语音或文字补充自己的感觉。系统结合原菜谱、当前步骤和人数，只给一到三个可验证动作，而不是重新生成一整份菜谱。

四类入口固定为：

1. **状态不对**：太稀、太干、粘锅/糊锅、不成形、油水分离、结块、颜色不对、快溢锅。
2. **味道不对**：太咸、太淡、太辣、太酸、太甜。味道只能来自用户试味后的选择或描述。
3. **调料怎么补**：忘记放调料、放多了、现在该放什么、替代调料。结合菜名、人数和当前步骤，采用“少量分次加入、每次确认”，不从照片虚构精确克数。
4. **不知道下一步**：结合原方案和当前图片判断更可能处于哪个阶段，并给一个下一动作；证据不足时必须追问用户确认。

用户选择类别后才显示对应症状；语音/文字描述始终保留，用于表达图片无法提供的信息。

### 8.2 多模态分工

| 信息来源 | 负责什么 | 不负责什么 |
|---|---|---|
| 当前做菜画面 | 稀稠、形态、分层、可见焦糊迹象、颜色、液面和大致阶段 | 味道、气味、准确用量、肉蛋安全熟度 |
| 语音/文字 | 用户尝到、闻到、担心或刚做过什么 | 不替用户自动补齐事实 |
| 原菜谱上下文 | 菜名、步骤顺序、当前步骤、下一动作 | 不覆盖用户现场确认 |

这段产品逻辑可直接用于方案、路演和演示讲解：

> 视觉负责“看见锅里发生了什么”，语音负责“表达用户尝到或担心什么”，原菜谱上下文负责“决定下一步”。三种信息缺一不可；系统不知道时追问，不把图片无法证明的味道、用量和熟度硬猜出来。

它比“拍照识别这是什么”更符合赛道四，因为视觉结果直接驱动用户当下动作，并自然体现视觉、语音和上下文各自不可替代的价值。

### 8.3 当前实现与边界

- React 结果页已接入折叠入口、四类动态症状、当前步骤、人数、相机/相册和现有语音转写。
- `/api/rescue-dish` 使用严格结构化 Schema 返回可见证据、判断、动作、观察点、追问和能力边界。
- 两张固定过程图为 AI 生成演示素材，界面明确标注“不作为真实用户评测”；固定样例仍先调用模型，只有超时或错误时才加载经安全复核的缓存。
- 缓存由“图片文件名 + 问题类别 + 具体症状”共同匹配，同一张图选择“太稀”和“太咸”不会复用同一个结论；普通用户图片无匹配缓存时，模型失败只返回明确的 `rules-fallback`。
- 5 条目标测试全部通过；本地生产链路从冰箱示例走到“番茄炒蛋太稀”救援结果，页面无控制台错误或横向溢出。
- `gpt-5.6-terra` 代表性真实调用已覆盖“太稀”“粘锅/糊锅”“太咸”，分别验证可见状态判断、焦糊隔离动作和用户试味事实优先；“不知道下一步”目前只有确定性目标测试，尚未做真实模型验证。
- 005 已部署且健康端点确认 `dishRescueAgent` 和任务路由生效；用户已在 iPhone 移动网络验证公网主流程、固定救援样例、真实相机、允许麦克风后的语音输入和拒绝权限后的文本兜底。现场噪声、无痕窗口和其他设备仍待彩排，不得把演示素材写成真实用户数据。

继续禁止：持续视频监控、自动判断肉蛋熟透或可安全食用、根据照片猜味道、根据照片给精确克数。

### 8.4 路演叙事资产

- `[可讲]` 这不是给用户重新生成一份菜谱，而是在最容易放弃的做饭中途，只给一个现在能做、做完能观察的动作。
- `[可讲]` 视觉负责看见稀稠、分层、焦糊和颜色，语音负责表达用户尝到或担心什么，原菜谱上下文负责决定下一步；这正是多模态不可互相替代的地方。
- `[可讲]` 固定演示也不直接写死结果：系统先请求真实模型，超过等待阈值或上游失败后才回到经安全复核、按问题签名匹配的缓存。
- `[待验证]` 现场噪声、无痕窗口、其他设备和“完全说不清做到哪”的真实模型表现。
- `[不要说]` 不称演示图为真实用户照片，不称缓存为实时模型结果，不声称能从照片尝味道或判断肉蛋安全熟度。

## 9. 推荐组合

### 获奖导向的主版本

```text
主故事：Feed 刷到菜 -> 拍冰箱 -> 今晚能否照着做
可见亮点：结果页提示“还有两样建议先处理”，进入冰箱救援
算法证据：结构化历史 case 检索 + 先吃/分区规则引擎
生态闭环：缺料补齐 + 成品内容草稿
```

### 如果只能增加一个低成本功能

选择“Feed 圈选食材 -> 用冰箱现有食材替代”。它最直接响应“视觉搜索”和抖音 Feed 场景。

### 如果只能增加一个记忆点功能

选择“冰箱救援：先吃清单 + 最多三条分区移动建议”。它复用当前冰箱识别，前后对比明显，也能解释留存与减少浪费价值。

### 与历史 case 检索的取舍

- 历史 case 检索更适合技术答辩和算法秋招，但观众不容易直接看见。
- 冰箱救援更适合第一印象和游园传播，但必须投入视觉和规则设计。
- 时间充足时二者分别承担“后台可信度”和“前台记忆点”；时间不足时先保证公网、正式界面和一个可见亮点，检索可以只保留离线消融。

## 10. 启动门槛

只有以下条件满足后才开始冰箱救援开发：

- 公网 staging 已经可访问。
- 真实模型四个端点已经验证。
- Feed 优先界面结构已冻结，不再大改导航。
- 主流程移动端没有阻塞缺陷。
- 仍有至少 2 个完整开发日和 1 个验证日。

如果不满足，R0 可以作为一张静态/规则结果卡保留，R1/R2 延期，不影响主线交付。
