## 1. 作品简介

用户在抖音 Feed 刷到想吃的菜时，往往只能收藏、在评论区问做法，或截图去站外搜索。冰箱晚餐视觉搜索 Agent 把这段链路留在一次体验中：用户上传刷到的菜图，说一句“今晚只有 25 分钟”，再拍一下冰箱；AI 根据用户确认的现实库存判断今晚能否照着做，并给出做法、缺料、简化路线和下一步行动。

```text
内容种草
  -> 目标菜视觉理解
  -> 语音 / 文本补充约束
  -> 冰箱视觉库存
  -> 用户确认与局部补拍
  -> 材料三态核对与晚餐规划
  -> 补购后重新规划 / 做饭过程救援
  -> 满意度判断与内容回流
```

它不是停在“这是什么”的视觉识别，也不是脱离现实库存的通用菜谱问答，而是从“看见”延展到“今晚怎么做”。

## 2. 真实场景与多模态必要性

- Feed 浏览会自然触发“这是什么、怎么做、我家能不能做”的连续需求。
- 菜品外观、锅中状态和冰箱现有食材很难靠关键词完整描述，图像能显著降低表达成本。
- 语音适合补充“只有 25 分钟”“不想洗锅”“刚尝了一口偏咸”等即时约束，文本始终是可编辑的稳定入口。
- 抖音可以承接 Feed 内容种草、商城补料和饭后生活记录，使视觉搜索形成站内闭环。

## 3. 已实现的核心闭环

1. **双场景入口**：用户可从“刷到想吃的”出发，也可直接拍冰箱请 Agent 决定今晚吃什么。
2. **目标菜视觉与人工确认**：支持拍照、相册、固定示例和暂停帧手动矩形框选；菜名识别后必须由用户确认或修改。
3. **冰箱视觉净化**：只把可确认食材交给 Planner；锅具、水瓶等非食材被排除，看不清的袋装、盒装物保留为待确认项。
4. **不确定性驱动的局部补拍**：当画面只有一个区域看不清时，Agent 只请求补拍门架、抽屉或某个包装；新确认的食材合并回当前库存，不让用户从头再来。
5. **目标菜材料三态**：根据整道菜的核心主料与人工确认库存，显式区分 `enough`（主料齐）、`missing`（明确缺料）和 `unresolved`（证据不足）；未核清时不生成误导性的“材料够了”或购物结论。
6. **行动规划**：Planner 比较确认库存、目标菜、时间、厨艺和显式偏好，输出现在做、简化做、补买后做、明天准备或成品兜底中的一条主路线。
7. **补购后重新规划**：购物卡明确为模拟。用户选择补购后，所选材料会被重新加入规划输入，Planner 真正重新判断材料与做法，而不是只更换按钮文案。
8. **满足判断与重新规划**：用户可反馈“正合适”“太麻烦”“缺料太多”“不想洗锅”或“换清淡点”；负反馈会成为下一轮约束。
9. **最多两轮做饭救援**：做到一半卡住时，用户拍当前画面并说明问题；第一轮只给一个可验证动作，第二轮根据新画面检查观察点，未改善时不重复原动作；第二轮后停止连续试错。
10. **饭后内容回流**：上传成品图后生成可编辑的标题、封面文案、旁白、后续补拍镜头和标签，不自动发布。

已从主展示撤回 U15“先选一种画面食材再做单项替代”步骤。整道菜与确认库存的对比现在由材料三态和 Planner 统一完成，不再让用户做重复选择。

## 4. AI Workflow 与工程实现

```text
需求理解
  -> 目标菜图 + 语音 / 文本约束
视觉理解
  -> 目标菜、冰箱库存或锅中状态
事实核对
  -> 用户确认 + 局部补拍 + 材料三态
工具与规划
  -> 确定性规则 + 结构化 Planner + 可关闭 Case 检索
结果与满足判断
  -> 行动页 + 反馈重规划 + 补购重规划 + 最多两轮救援
```

生产环境由一个 Node.js 服务同源承载 React H5、示例素材和 API。模型端点均使用严格 JSON Schema，不依赖自由文本解析。主要职责包括：

- 冰箱视觉、目标菜视觉和做饭过程视觉救援。
- 自由晚餐规划与目标菜规划。
- 成品图生活记录草稿。
- 用户确认状态后的先吃清单、粗分区建议和布局预览等确定性规则。

CloudBase 010 已把视觉、规划和生活记录三类模型任务统一路由到 `gpt-5.6-terra`。模型或网络波动时，只有固定演示素材可以使用预分析缓存；开发检验台和内部运维台会区分 `model`、超时缓存和错误缓存，不把缓存结果包装成实时模型。

## 5. 比赛运维台与可观测性

CloudBase 010 公网版本启用 `agent_runs` 和受管理员令牌保护的 `/ops.html`，用于评委演示和小范围测试期间的问题定位。它可按请求 ID 查看路由、状态、来源、模型、阶段耗时、token usage 以及排障所需的白名单结构化输入输出。

这个页面是赛事运维工具，不进入用户主导航，也不伪装成用户量或抖音画像后台。运行记录不保存原始照片、原始音频、API Key、管理员令牌或认证请求头；记录写入失败时主链路继续运行。

## 6. 固定评测与算法取舍

当前固定回归集包含 11 例视觉和 19 例规划 / 安全用例。2026-07-18 在统一 `gpt-5.6-terra`、关闭检索且要求真实模型来源的条件下：

- 30/30 通过，30 例来源全部为 `model`。
- 平均延迟 18.33 秒，P95 延迟 28.03 秒。
- 总 token usage 为 114,467。
- Schema、规划动作与安全语义门禁在这个固定集上均通过。

当前仓库固定菜图已更换为内容与标签一致的 `assets/菜/黄焖鸡-示例.png`；旧的错标图不再参与当前演示或评测。上述 30 例固定回归已使用新图，但公网录屏须使用包含该素材的后续发布版本。

结构化历史 Case 检索使用 24 条独立人工参考 Case，不训练底模，也不使用向量数据库。针对 terra 的完整 19 例规划对照结果为：

| 模式 | 通过 | 结论 |
|---|---:|---|
| `off` | 19/19 | 当前公网基线 |
| `positive` | 19/19 | 没有比基线多通过用例 |
| `contrast` | 18/19 | 出现 1 例规划动作质量失败 |

因此公网继续使用 `CASE_RETRIEVAL_MODE=off`。这个取舍表明开发检验台中的检索实验可以被审计，但不会为了技术堆叠强行进入主演示。

上述数据只说明当前模型、提示词和固定数据集上的离线回归结果，不代表真实用户分布、线上满意度或业务指标。

## 7. 安全与可信边界

- 不凭图片判断过期、新鲜度、剩菜安全或肉蛋是否安全熟透。
- 不自动推断过敏、疾病或医疗饮食要求。
- 不把遮挡物、不明包装和低置信食材直接用于规划。
- 缺定义性主料时，不声称能做出完整目标菜。
- 商城补购明确为模拟；生活记录只生成可编辑草稿，不声称已下单或已发布。
- 缓存只服务固定演示素材，来源在开发与运维工具中明确可见。

## 8. Skill 交付

核心流程封装为 `fridge-dinner-visual-search` Skill：

- `SKILL.md`：输入、Workflow、材料三态、补购重规划、救援闭环和安全规则。
- `references/contracts.md`：视觉、库存、目标菜规划、局部补拍、补购和救援的结构化合约。
- `agents/openai.yaml`：Skill 展示元数据。

提交前通过 `npm run skill:package` 生成 `.skill` 文件。

## 9. 增长与 ROI 验证路径

冷启动先聚焦美食 Feed 和厨房相机两个入口，逐步验证：

- 有效 PV：有明确视觉搜索意图并进入体验的用户数。
- 搜索渗透：暂停帧、框选或菜图入口的触发率。
- 满足率：用户接受方案、完成规划或无需继续追问的比例。
- 留存：用户是否在下一次做饭决策中再次使用。
- 转化：确有关键缺料时的补购点击和后续购买。
- 内容回流：完成做饭后生成生活记录草稿的比例。

大区赛版本只把“刷到想吃的菜，回到现实冰箱完成一餐”做深做稳，不扩展成泛用聊天助手。
