# 路演讲稿：冰箱晚餐视觉搜索 Agent

当前公网模型基线：CloudBase 011

更新日期：2026-07-19

CloudBase 011 已验证三类模型任务均路由到 `gpt-5.6-terra`，固定规划和运维记录定向通过。75 秒备用视频、新黄焖鸡固定图与新增交互均以 011 为准；当前版本 iPhone 现场扫码和权限链路仍待复验。

## 30 秒版

我做的是赛道四的冰箱晚餐视觉搜索 Agent。

用户在抖音刷到一道想吃的菜，真正的问题不只是“这是什么”，而是“我家现在能不能做”。他可以上传这帧菜图，说一句“今晚只有 25 分钟”，再拍一下冰箱。AI 会先让用户确认菜名和现实库存，再明确告诉他主料是够了、明确缺料，还是证据没核清，最后给出照着做、简化做或补买后做的现实路线。

它把内容种草、视觉搜索、现实行动和饭后内容回流连成了一次体验。

## 90 秒版

大家好，我的作品是冰箱晚餐视觉搜索 Agent。

用户在 Feed 刷到美食，即使搜到菜谱，仍不知道家里能不能做。这个 Demo 先让他上传或框选菜图，确认菜名，再说一句“今晚只有 25 分钟”；接着拍冰箱，只把用户确认的食材交给 Planner。包装看不清时，只补拍那一处并合并回原库存，不用重来。

系统按整道菜而不是某一种食材核对，明确告诉用户主料齐、缺料，还是尚未核清，再给出照着做、简化做或补买后做。模拟补买后，用户选中的材料会真正回到 Planner 重新生成方案。做饭中途卡住，还可拍当前画面，最多救援两轮，每轮只给一个动作和观察点。

CloudBase 011 的三类模型任务都使用 `gpt-5.6-terra`。固定 30 例全部来自真实模型并 30/30 通过，平均 18.33 秒，P95 28.03 秒。Case 检索对照是 `off=19/19`、`positive=19/19`、`contrast=18/19`，所以公网继续关闭。运维台可按诊断编号核对来源、耗时和 token，缓存不会被包装成实时模型。

它不是通用聊天机器人，而是把“看见一道菜”变成“今晚真的能做什么”的视觉搜索闭环。

## Demo 操作顺序

1. 首屏点击「刷到想吃的」，再点击「用示例黄焖鸡」。当前公网 011 使用内容与标签一致的 `assets/菜/黄焖鸡-示例.png`，旧错标图已撤回。
2. 指出菜名会先写入可编辑文本框；用户可手动框选画面重点，也可用语音或文本修改菜名和约束。
3. 点击「下一步，看冰箱」，再点击「用示例体验」并识别冰箱。
4. 讲解可确认食材与待确认包装的分工。如果当前结果有不确定区域，展示「补拍这个区域」如何把新食材合并回库存；没有时不为了演示强行制造不确定项。
5. 确认库存后点击「看看家里够不够做」，重点讲解材料三态、主要缺料和今晚路线，不讲模型品牌。
6. 有明确缺料时，点击模拟补购并展示补买材料重新进入 Planner；强调没有发生真实下单。
7. 打开「做到一半卡住了」，使用「番茄炒蛋太稀」固定演示素材；首轮展示“一个动作 + 观察点”，再点击「做完了，拍一下复查」或「没改善，换个办法」说明最多两轮。
8. 有时间再展示饭后生活记录草稿；草稿可编辑，不自动发布。
9. 如被追问链路是否写死，打开开发检验台展示原始 JSON 与 Case 对照，或在内部 `/ops.html` 用诊断编号查询来源、耗时和 token。管理员令牌不得出现在投屏、讲稿或录屏中。

录制要求：

## 答辩重点

- **为什么必须多模态**：菜品外观、冰箱库存和锅中状态很难靠关键词完整表达；语音适合补充时间、做饭负担和用户试味结果。
- **为什么是抖音场景**：从 Feed 种草触发，商城只在明确缺料时承接，做完后生成可编辑生活记录，形成内容闭环。
- **为什么不是 API 拼装**：系统有结构化合约、库存净化、人工确认、材料三态、局部补拍合并、补购重规划、最多两轮救援、固定评测和可审计降级。
- **评测证据**：固定 30 例在当前 terra 路由下 30/30，全部为 `model`，平均 18.33 秒，P95 28.03 秒，总 token 114,467。这是离线固定集，不代表真实用户满意度。
- **为什么关闭 Case 检索**：terra 的完整 19 例规划中，`off=19/19`、`positive=19/19`、`contrast=18/19`；未证明质量增益，因此不为了技术堆叠强行开启。
- **模型失败如何处理**：固定示例可切换到预分析结果，用户依然可操作；页面明示已切换稳定方案，运维台保留来源、失败位置和诊断编号。
- **安全边界**：图片不能判断过期、气味、味道或肉蛋安全熟度；关键主料缺失时不伪装成完整目标菜。
- **为什么不用重 Agent 框架**：当前流程有明确分支和结构化合约，轻量函数更易验证、延迟更低，也更适合 Solo 交付。
- **增长怎么验证**：按有效 PV、搜索渗透、满足率、留存、补购转化和内容回流逐步验证，不预写线上数据。
