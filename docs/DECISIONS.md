# Decisions

## 2026-07-20 - 012 第三轮重构冻结功能真实性，不冻结视觉、结构或后端上限

Decision: 第一、二轮 012 界面只保留为 `b743c2c` Git 回滚点，不作为第三轮设计基础。第三轮必须在全新 Kimi 3 会话中从产品任务重新形成设计；不预设颜色、背景、页面数量、入口形态、信息顺序、组件、DOM 或 CSS。现有 API 与后端是已验证能力基线而非产品上限，Kimi 可以提出或实现能显著增强比赛呈现的新字段、接口、状态流和 Agent 能力，Codex 负责契约审计、后端补齐与定向验证。

Reason: 第二轮提示一边要求“彻底重构”，一边又规定暖白/绿橙配色、五段页面、固定结果顺序、沿用草稿并禁止重写 `App.jsx`，实际把设计自由压缩成 CSS 换肤。大量代码差异集中在样式，用户体验结构没有产生相应变化。继续恢复旧 Kimi 会话或旧视觉约束会重复同一错误。

Impact: `docs/frontend/012第三轮真正前端重构设计简报-2026-07-20.md` 成为第三轮唯一设计权威；旧 `012前端重构实施约束` 标记为历史。新会话先做独立设计命题与旗舰路径检查点，用户确认方向后再迁移全部功能与必要后端能力。当前 CloudBase 011、提交制品和线上流量不随本地设计阶段改变。

## 2026-07-19 - 011 以完整 terra 证据收口，Case 检索继续关闭

Decision: 当前视觉、规划和生活记录统一使用 `gpt-5.6-terra`，缺少任务级变量时 `OPENAI_MODEL` 也回退到 terra。固定 30 例门禁通过后，不因“最新模型”再次换路由；完整 19 例 Case 消融没有证明规划质量增益且增加 token，`contrast` 还引入一例动作退化，因此比赛公网继续 `CASE_RETRIEVAL_MODE=off`。

Reason: 当前配置的固定 30 例真实模型回归为 30/30、平均 18.33 秒、P95 28.03 秒；Case 消融为 `off=19/19`、`positive=19/19`、`contrast=18/19`，后两者 token 分别增加 19.2% 和 24.1%。这些证据覆盖了 2026-07-13/14“完整评测未运行、规划默认 sol、Case 增益未知”的阶段性决策，但 30/30 仍只代表固定集。

Impact: 011 只合并 `confirmAtHome` 窄范围清洗、未知步骤确定性确认门禁、目标菜材料收口和正确示例素材，不改变 API 架构。当前公网仍是 010；011 部署异常时首选保持或回滚 010，009 是次级回滚点。即使真实模型对 `next_step` 返回合法高置信输出，只要用户无法说明当前阶段，服务端仍强制 `needsConfirmation=true` 并追问。

## 2026-07-19 - 当前阶段冻结比赛制品，产品级隐私和新前端架构后置

Decision: 真机前先冻结 011 的部署包、Skill、海报、固定截图和 75 秒字幕/旁白备用视频；现阶段不启动 Kimi 3 前端重构，也不追加复杂同意流、字段级加密或云端画像后台。

Reason: 当前剩余风险集中在 CloudBase 011 定向验收、iPhone 相机/麦克风和现场回滚，而不是架构能力。比赛是小范围创意验证，可观测和快速定位比产品级隐私工程更有评分价值；现有最低敏感数据边界已经足够支撑受控测试。

Impact: 后续前端重构必须先冻结现有 API/JSON 合约并通过适配层迁移；只有新增流式、多图或状态字段确有必要时才同步调整服务端。运行记录可以保留白名单结构化内容，但仍不得保存密钥、认证头、原始照片或原始音频。

## 2026-07-18 - 公网 010 将规划路由从 sol 切换到 terra

Decision: 视觉、规划和生活记录三个任务在公网 010 统一使用 `gpt-5.6-terra`；009 的 `terra/sol/terra` 作为版本级回滚配置。目标菜 Planner 同时加入主食、预制调味包、自炊优先和肉类熟度四条业务门禁。

Reason: 009 的两次 `gpt-5.6-sol` 规划在应用 50 秒门限结束并显示 0 token，另一次约 47 秒才完成，已接近 CloudBase 请求硬上限。定向对照中 terra 的业务质量优于两个 5.5 候选，且本地目标菜/自由晚餐分别约 34.9/16.1 秒；010 公网目标菜固定请求约 31.0 秒并正常记录 6,447 tokens。

Impact: 0 token 按模型未在超时前完成处理，不再作为 usage 解析故障排查；暂不提高 50 秒应用门限。该小样本只支持现场稳定性的路由决策，不能声称 terra 在完整评测上全面优于 sol。

## 2026-07-18 - 比赛阶段可观测性优先于产品级隐私建设

Decision: 当前评委和熟人小范围测试阶段保持 `AGENT_RUNS_CAPTURE_CONTENT=true`，允许保存白名单结构化库存、目标菜文本、显式偏好、检索证据和规划结果，用于排障与复盘；不主动建设复杂同意流、字段级加密、自动匿名化或隐私后台。

Reason: 项目当前目标是创意比赛呈现与现场稳定，产品级隐私工程的边际评分价值低，且会挤占真实链路、视觉体验和创新功能时间。

Impact: 仍不记录 API Key、管理员令牌、认证头或原始照片/音频，这是最低运行边界而非新的隐私项目。只有测试范围升级为真实公开产品、用户明确要求或出现具体合规要求时才单独立项。

## 2026-07-14 - 视觉与规划采用任务级模型路由

Decision: 服务端支持 `VISION_MODEL`、`PLANNING_MODEL` 和 `LIFE_LOG_MODEL` 独立配置；本地默认视觉/生活记录使用 `gpt-5.6-terra`，规划使用 `gpt-5.6-sol`。Responses SSE 完成事件中的 usage 作为非业务元数据写入接口和评测报告。

Reason: 固定 4 例视觉首轮中 terra 与 sol 同为 3/4，但平均延迟约 20.3s 对 63.2s；luna 为 0/4。任务级路由比全链路固定旗舰模型更符合现场延迟和成本目标。

Impact: CloudBase 002 暂不变；下一版本需显式增加三个路由变量。菜名重复识别仍有波动，人工确认不能移除；账单金额以 provider 控制台为准，不凭 token 自行虚构成本。

## 2026-07-14 - Feed ROI 采用用户手动裁剪

Decision: U11 用浏览器端矩形框选和图片裁剪实现，裁剪区域再调用既有目标菜视觉接口；保留选整张、恢复原图和手动改菜名。

Reason: 手动 ROI 能直接表达“暂停后圈选继续探索”，同时不引入目标检测模型、框标注数据和自动定位误差，Solo 可稳定交付。

Impact: 对外只能称“手动框选画面重点”，不得称自动目标检测、跟踪或像素级分割。无 Key 或模型失败时继续使用文本/文件名兜底。

## 2026-07-14 - U10 只生成可编辑生活记录草稿，不接真实发布

Decision: 饭后内容回流采用“真实成品图 + 用户确认菜名 -> 结构化可编辑草稿”。输出限定为标题、封面文案、短旁白、未来补拍镜头、标签和人工确认提醒；不接抖音发布权限，不自动上传，也不声称口感、营养、实际耗时、已有过程镜头、播放量或反馈。

Reason: 该功能可以把抖音内容种草和饭后内容回流真正连成可操作闭环，同时控制 Solo 账号权限、隐私和事实幻觉风险。开发检验台保留模型/缓存来源，用户端只展示可编辑内容。

Impact: 新增 `/api/generate-life-log`、`lifeLogDraftSchema`、固定示例缓存、确定性草稿回归和 React 编辑界面。无 Key 缓存端到端、发布冒烟和 390px 布局已通过；真实回锅肉图调用因 Right Code TLS 握手错误待复验，不能写成真实模型已通过。U10 结束后唯一在途项切换到 U02 真实评测。

## 2026-07-14 - U16 采用“用户确认状态 + 确定性排序 + Planner 约束”

Decision: 库存确认后提供可选状态入口，只有用户显式选择已开封、确认标签日期临近或状态不确定时才运行 `/api/eat-first`。规则结果分为本餐优先、近两餐和待确认；可用优先项进入 Planner，结果页同步解释来源。

Reason: 单张冰箱图不能判断日期、新鲜度或可安全食用。把安全敏感信息交给用户确认、把排序交给确定性规则，可以形成可见的冰箱救援价值，又不增加模型调用和食品安全幻觉。

Impact: 新增 10 例规则回归、发布冒烟和桌面/390px 交互验收。真实 `gpt-5.6-sol` 规划已使用用户确认的优先食材。U16 本地验证完成，唯一在途升级切换为 U17 粗粒度分区；U17 不得做精确位置、三维重排或安全食用结论。

## 2026-07-14 - U15 确定性替代规则保留，但用户选择步骤已撤回

Decision: 2026-07-16 从主展示端移除 `likelyIngredients` 单项选择和结果页附加对照卡。目标菜路线在确认菜名后直接进入拍冰箱；整道菜所需材料与确认库存由 Planner 统一处理。`/api/ingredient-substitution`、白名单规则和 12 例回归仅保留给开发检验与后续自动化比较，不再构成用户步骤。

Reason: 用户后续本来就必须拍冰箱并确认库存，提前再选一种材料既重复又增加界面复杂度；原实现还只生成独立结果卡，没有真正改变主规划，因此产品价值不足。确定性规则本身仍有可审计和独立评测价值，可以保留在开发层。

Impact: 主展示减少一个选择区、一次接口调用和一张结果卡；相关前端状态、组件及样式已删除。不得再将 U15 描述为当前用户可见功能，也不得在没有整道菜自动比较设计时重新加入单项选择。

## 2026-07-14 - 受控模型测试成本不是当前阻塞

Decision: 继续保留 20 元 Right Code Key 限额，但不因成本暂停功能开发；完整评测仍需记录分项成本。

Reason: 用户核对本轮真实测试账单约 0.21 元，且客户端没有自动重试，当前没有费用放大迹象。

Impact: 当前开发优先级转向功能闭环和评测证据。不能把 0.21 元外推为完整 30 例成本，也不能在未运行完整评测前填写平均 token 或单例成本。

## 2026-07-14 - CloudBase 作为公网主平台，gpt-5.6-sol 进入受控基线

Decision: 公网主平台固定为腾讯云 CloudBase Run，使用单容器、默认 HTTPS 域名和版本流量管理；当前候选主模型改为 `gpt-5.6-sol`，`gpt-5.5` 保留为环境变量级回滚。

Reason: CloudBase 001 已完整构建并通过公网基础冒烟。`gpt-5.6-sol` 在真实 Key 下已跑通两个视觉和两个规划端点，兼容 `input_image`、SSE 和 JSON Schema；但当前证据只有四次小样本，不足以声称质量优于 5.5。

Impact: 先在 20 元受控额度下运行小集并核对账单，无异常重试后才扩大到 30 例和 Case 消融。公网最大实例数保持 1，比赛前改为最小/最大都为 1。模型、提示词或 Schema 变更必须重跑基线，不以“最新”代替实测。

## 2026-07-13 - 冰箱管理只以“用户确认后的冰箱救援”进入候选

Decision: 初赛提出的冰箱内食材位置调整方向保留，但重新定义为主流程中的“冰箱救援模式”：视觉模型只识别食材和门架/层架/抽屉等粗粒度分区；用户确认购买、开封或包装日期后，确定性规则引擎生成先吃清单和最多三条移动建议。自动判断过期、腐败或可安全食用明确拒绝进入本次比赛。

Reason: 先吃清单、移动箭头和整理前后对比对评委可见，能够复用现有冰箱识别与晚餐规划，也能解释复访和减少遗忘价值；但单张冰箱图无法可靠判断食品安全，通用多模态模型的精确空间推理也不足以支撑厘米级或三维自动摆放。

Impact: U16“先吃清单”和 U17“分区移动建议”保持 Candidate，只有公网、真实模型基线、Feed 界面和移动主流程稳定且仍有至少两个开发日、一个验证日时才可启动。对外只能使用“减少被忘记、帮助优先处理、降低交叉污染风险”等措辞。详细方案见 `docs/roadmap/冰箱管理与扩展方向评估-2026-07-13.md`。

## 2026-07-13 - 升级范围由单一总计划治理

Decision: `docs/roadmap/大区赛升级总计划-2026-07-13.md` 是大区赛后续升级的唯一总入口；部署和算法细节分别进入专门文档。Solo 同时最多一个升级处于 `In progress`，每项必须先写清评分价值、评委可见性、成本、风险、验收和回滚。

Reason: 当前项目已经产生较多历史文档，如果新想法继续散落在聊天或并列计划中，后续 session 会重复开发、误读优先级或让复杂方案污染当前范围。

Impact: 新功能先登记后开发；7 月 23 日进入功能冻结，只修 P0。若排期延误，按公网、真实评测、界面、满足反馈、case 检索的顺序删减。

## 2026-07-13 - 历史 case 检索是本次唯一批准的算法增强路线

Decision: 在真实模型基线完成后，实现结构化历史用餐 case 检索、成功/失败对照 ICL 和受控消融；先做不依赖向量数据库的可解释 V1，只有 V1 证明有效后才考虑 embedding 混合检索。

Reason: 该路线能够参考 FinFRE-RAG 的“结构化表示 + 相似 case + few-shot”方法，同时符合 Solo 时间、现有 Schema 和评测基础。它可以产生检索指标、规划指标、失败案例、延迟和成本证据，比强行增加 Agent 框架更有算法可信度。

Impact: 现有 19 例规划评测不能同时作为检索库和测试集；case 来源必须区分人工、演示、显式反馈和合成数据。没有消融结果前不得声称检索提升效果。

## 2026-07-13 - 不复现 OneReason 后训练体系，界面重构列为高优先级

Decision: 本次比赛不做多粒度预训练、CoT SFT、分域 GRPO、RFT、MOPD、teacher 蒸馏或比赛专用微调。公网和真实基线完成后，优先把展示端升级为 Feed 优先双入口、真实图片主视觉、移动相机和满意度闭环。

Reason: OneReason 是大团队训练体系，缺少数据、reward、teacher、训练预算和验证周期；个人硬做无法产生可信结论。相反，大区赛评委和观众会直接感知首屏故事、视觉质量和交互完整度，界面质量对获奖更具即时价值。

Impact: 算法叙事以检索、评测、消融和失败分析为主；界面重构必须服务官方评分，不做纯装饰，也不得挤占公网部署和真实评测。

## 2026-07-13 - 生产采用单服务同源部署

Decision: 生产环境先构建 `frontend/dist`，再由 `demo/server.mjs` 同源提供 React H5、示例资源和 `/api/*`；使用一个 Docker 容器和一个公网域名，不拆分前后端服务。

Reason: Solo 交付要减少账号、跨域、代理和多服务运维成本；官方只要求部署后可体验，单服务已经覆盖远程评审需要。

Impact: 明天云平台只需创建一个容器服务、配置 Secret 和 HTTPS 域名。`npm run build && npm start` 是生产验收基线。

## 2026-07-13 - 语音是可选多模态入口，文本不能被移除

Decision: React 展示端使用浏览器 Web Speech 优先，失败后录音调用 `/api/transcribe-audio`，最终回到可编辑文本框。语音不作为生成规划的必要前置条件。

Reason: 赛道强调视觉与语音，但浏览器、权限和 ASR provider 都可能不稳定；可选入口既能证明多模态交互，也不会让现场主流程被单点故障阻断。

Impact: 公网必须使用 HTTPS；现场先演示语音，失败时立即手动输入，不继续排查权限。

## 2026-07-13 - 用固定评测集证明算法增量

Decision: 建立 30 例回归集，分别检查视觉 Schema/召回、规划动作、关键缺料、安全禁用语义和延迟。缓存结果与模型结果必须分开记录。

Reason: 项目容易被评价为纯 Vibe/开发；可重复评测、失败案例和后续消融才是对算法岗位有意义的可信增量。

Impact: 模型、提示词或 Schema 变化后运行 `npm run eval`。真实 Key 已配置并完成四端点小样本，但在完整 30 例、账单和失败分析完成前，仍不填写“全集通过率”或模型提升结论。

## 2026-07-13 - 重庆大区赛按单人参赛模式推进

Decision: 用户单人参加赛道四重庆大区赛，原队友均不参加。开发、部署、评测、Skill、海报、路演和现场应急全部按单人可完成、可维护的标准设计，不再给队友分配职责或把任何交付放入队友关键路径。

Reason:

- 官方规则允许大区赛重新组队，队伍仍为 1-4 人，参赛者需现场签到，因此单人参赛符合规则。
- 交流赛作品事实上由用户独立完成，原队友没有形成稳定、可验收的工程或现场交付能力。
- 大区赛前还需兼顾 PDD 实习和 2026-08-06 字节秋招面试，必须控制协作不确定性和沟通成本。

Impact:

- 功能范围必须收敛，优先公网体验、核心多模态闭环、评测、Skill 和现场稳定性。
- 队友是否临时出现不再影响项目排期；即使有人到场，也不承担关键账号、部署、提交或技术答辩职责。
- 后续分析不再把“是否重新组队”列为开放问题。

## 2026-07-07 - 大区赛主线锁定赛道四视觉搜索

Decision: 当前项目主线从历史文档中的「赛道 2 视觉搜索」表述，统一修正为大区赛「赛道四｜视觉搜索：视觉 + 语音，所见即所想」。作品仍沿用冰箱晚餐 Agent，但对外叙事要从单纯冰箱识别升级为「抖音内容种草 -> 视觉/语音触发 -> 冰箱库存判断 -> 做法与补齐 -> 饭后发布」闭环。

Reason:

- 官方大区赛赛道四明确要求视觉 + 语音多模态，不止识别“这是什么”，而要从看见延展到理解、追问、比较、行动和闭环。
- 赛道四最高权重是 AI 链路可落地 25%，现有两段式 Agent、结构化 JSON、开发检验台和缓存兜底可以直接支撑这个评分点。
- 抖音生态放大占 20%，现有目标菜复刻、商城补齐和成品发布 CTA 需要被放到主叙事中，而不是作为边缘功能。

Impact:

- 后续文案、路演、展示页和提交材料应优先使用「赛道四视觉搜索」而不是旧的「赛道 2」编号。
- 继续保留冰箱晚餐 Agent 的产品主体，但要显式解释多模态必要性、抖音生态闭环和增长指标。
- 历史海报方案只作为 archive，不应被后续 Agent 误判为当前主线。
