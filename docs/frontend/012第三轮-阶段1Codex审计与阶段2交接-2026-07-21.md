## 3. Codex 接手后发现的关键问题

以下不是视觉偏好问题，而是会让演示结果与真实数据不一致的问题：

1. Feed 首次确认冰箱后立即规划时，React 状态尚未更新，规划可能读取旧库存或空数组。
2. 模拟补购和“本次已拿到”可能被混进确认库存，并在行动单上被误标成“冰箱原有”。
3. 会话保存依赖旧闭包，刷新后可能恢复不完整；进行中的请求也可能被误认为仍在等待。
4. 首次规划失败虽有状态变量，但页面没有可靠出口；重规划失败也可能污染版本。
5. 选择上次库存、回去改库存、取消或切换图片时，部分状态会停在错误场景或丢失人工修正。
6. Kimi 已画出“说出是什么 / 补拍”入口，但“说出”实际只是普通文本框，补拍也没有专用识别语义。
7. 前端读取 `not_fridge / unusable`，但后端 Schema 和提示词没有输出该字段，失败三态无法真实成立。
8. 示例缓存仍可能按文件名命中；真实上传若恰好同名，可能拿到示例结果。
9. 正反馈使用 `fit`，而既有画像后端只认识 `accept_meal`。
10. 示例自动预置的 25 分钟可能残留到后来换入的真实图片，违背真实路径必须用户亲选时间的结论。
11. 页面跨场景保留滚动位置，行动单可能从中部打开。
12. 行动单的“已有、模拟待补、已拿到、仍缺”及常备调料文案存在互相矛盾的可能。

## 4. Codex 已完成的前端修复

### 4.1 规划请求与版本快照

- 首次规划显式传入刚刚确认的 `inventorySnapshot`，不再等待异步 state 更新。
- 每个方案版本保存 `requestSnapshot`：库存、库存来源、时间档、意图和补充要求。
- 每个方案保存 `inputProvenance`，行动单可以解释本版来自本次图片、上次库存、手动确认还是用户确认空库存。
- 反馈、模拟补购、部分材料已拿到等重规划，都从当前版本快照派生，而不是读取页面上可能已经变化的全局状态。
- 最近三版带稳定 sequence；切换旧版不会偷偷改写当前方案。

### 4.2 四种材料状态严格分开

- 确认库存只包含用户确认的冰箱原有食材。
- `materialState.acquiredItems` 表示用户确认本次已经拿到的材料。
- `materialState.simulatedItems` 表示仅在模拟购物中选择、尚未真实购买的材料。
- 发给 Planner 的真实可用库存 = 确认库存 + 已拿到；模拟待补不会进入真实库存。
- 全部缺料都确认已拿到时，只更新本版执行状态，不浪费模型调用。
- 只拿到一部分或条件发生变化时，才产生新规划请求和新版本。
- 行动单分别显示冰箱原有、常备调料待确认、模拟待补、已拿到和仍缺，不靠颜色混淆语义。

### 4.3 会话恢复和请求中断

- 会话恢复集中在一次 hydration 后执行，避免旧闭包覆盖新状态。
- 保存路线、场景、确认库存、完整时间语义、意图、最近三版、材料状态和来源标记。
- 不保存原始菜图、冰箱图、近照或音频。
- 刷新后若发现上次请求进行中，显示“上次请求已中断”，不静默重发，也不伪装成仍在等待。
- 返回修改库存时保留已确认内容；真正重拍或“换一种开始”才清理相应状态。
- 场景或方案版本改变时滚动回顶部。

### 4.4 看不清项的三动作

- “我知道是什么”：加入真实 `SpeechInput`，同时保留可编辑文字；空值不能提交。
- “我自己也看不清”：逐项补拍，并以该不确定项的稳定 key 绑定返回候选。
- “我不想处理”：忽略；忽略项仍不进入库存。
- 补拍调用 `/api/analyze-fridge` 时带 `analysisMode: "fridge_detail"`。
- 近照识别出的候选不会自动进入库存，用户必须对原不确定项再次确认。
- 补拍成功后显示“已确认并加入库存”，不再误显示为已忽略。
- 盘点页的普通手动添加也增加了语音入口。
- 当前仍保持逐项补拍；没有因为粗分区相同就自动合并多个不确定项。

### 4.5 菜图、时间和反馈

- ROI 识别保留 `originalImage`，用户可以恢复整图。
- 用户手改或语音确认菜名后，后续 ROI 重识别不覆盖人工确认。
- 示例路径可以自动显示“25 分钟左右”；用户换成真实图片后，如果时间只是示例自动值，就会清空并要求亲选。
- `flexible` 保持语义值，表示“今晚不赶时间”，不转换为无限分钟。
- 正反馈在界面仍可叫“正合适”，发给既有画像后端时映射为 `accept_meal`。

### 4.6 失败和可访问性

- 首次规划失败进入真实可见页面：重试、使用明确标注的保守规则兜底、返回改条件。
- 重规划失败保留原方案，不生成一份失败版本。
- 用户主动取消不显示成模型失败。
- 等待层补充 dialog、Escape 和焦点处理，计时不会每秒打断屏幕阅读器。
- 首屏 390px 下字幕为点赞数预留空间，避免两者重叠。

## 5. Codex 已补齐的后端契约

### 5.1 冰箱画面类型

`/api/analyze-fridge` 的结构化输出新增必填：

```json
{
  "sceneAssessment": {
    "kind": "fridge | not_fridge | unusable",
    "reason": "可复核的画面依据"
  }
}
```

- `fridge`：能确认拍到冰箱内部；即使没有认出食材，也不能自动等同于真实空库存。
- `not_fridge`：明确不是冰箱内部。
- `unusable`：过暗、严重模糊或遮挡，无法可靠判断。
- Sanitizer 兼容旧缓存：旧结果有可确认食材时归为 `fridge`；旧结果空且没有场景字段时归为 `unknown`，不能据此建立空库存。
- 非冰箱或不可用结果的 items 会被清空，避免污染库存。

### 5.2 菜名候选

`/api/analyze-target-dish` 新增必填 `dishNameCandidates: string[]`，最多 3 个，不重复主菜名；没有合理候选时返回空数组。前端只在字段存在且非空时显示候选 chips。

### 5.3 示例缓存隔离

- Feed 示例固定使用 `demoKey: "sample-dish-huangmenji"`。
- 冰箱示例固定使用 `demoKey: "sample-fridge-01"`。
- 冰箱与目标菜缓存优先按图片 hash 命中，其次只接受受控 `demoKey`。
- 真实上传不再因为 `sourceFileName` 与示例同名而命中固定演示缓存。
- 生活记录与救援的旧缓存策略没有被这次改动无关破坏。

### 5.4 近照识别和时间语义

- `analysisMode: "fridge_detail"` 会让冰箱视觉 Agent 按“某一处补拍近照”识别，而不是把近照强行当成整台冰箱盘点。
- 两个 Planner 都明确读取 `userContext.context.timeBudgetId`。
- `flexible` 明确表示不赶时间，而非无限时长。
- 做饭耗时只计算从备菜到出锅；补购、配送与清理不混进该时间。
