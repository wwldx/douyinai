## 1. 为什么重新开始

第二轮虽然修改了大量代码，但主要变化集中在 CSS、色彩、间距、圆角和既有页面的展示层整理。任务提示同时预设了颜色、页面结构、结果顺序，并禁止重写视图骨架，导致“彻底重构”实际退化为换肤。

第三轮必须改正这一点：先从产品任务和体验命题出发形成独立设计，再把现有能力接入。不能从旧 DOM、旧 CSS 或旧截图反推新方案。

判断重构是否成立的最低标准：即使暂时移除颜色，也能从信息架构、页面轮廓、交互机制和核心组件上看出这是一套重新设计的体验，而不是 012 的换色版本。

## 2. 核心产品故事

这不是菜谱搜索器，也不是泛化聊天助手。

产品发生在两个真实时刻：

- 用户在抖音刷到一道想吃的菜，希望马上知道：家里现有食材够不够、今晚能不能照着做、缺什么、最现实的做法是什么。
- 用户打开冰箱却没有想法，希望 AI 根据可见食材、本人确认的库存和当晚约束，直接给出能落地的一顿饭。

核心价值链：

> 视觉内容或冰箱实景 → AI 理解 → 用户确认现实条件 → 给出今晚可执行的决定 → 必要时模拟补齐材料 → 饭后生成生活记录草稿

多模态不是装饰：目标菜图表达“想吃什么”，冰箱图表达“现实里有什么”，语音或文字补充“今晚有什么要求”，用户确认负责校正视觉不确定性。

抖音生态价值不是贴一个商城按钮，而是把内容种草、现实决策、材料补齐和饭后内容记录串成可理解的闭环。

## 3. 评委 30 秒目标

第一次接触后的 30 秒内，评委应能自然回答：

1. 这是一个帮助用户决定今晚能不能做、具体怎么做的冰箱晚餐 Agent。
2. 它为什么必须使用视觉：既要理解想吃的菜，也要理解现实冰箱库存。
3. AI 不只识别物品，而是把识别结果变成可执行的晚餐决定。
4. 它承接抖音内容种草，并延伸到材料补齐和饭后内容记录。
5. 当前下一步是什么，为什么值得继续操作。

这些理解应主要来自图片、任务、选择、状态变化和结果本身，而不是依赖大段说明、功能列表或算法关键词。

## 5. 不可丢失的功能结果

这里冻结的是用户最终能完成的事情，不是旧按钮、旧页面或旧信息顺序。

### 5.1 从想吃的菜出发

- 用户能够提供目标菜图片，真实相机、相册和固定示例都可用。
- 用户能够手动框选画面重点，并把裁剪区域重新交给目标菜视觉能力。
- 识别得到的菜名必须允许用户确认、修改和补充要求，不能直接替用户确定意图；用户手动修改后，ROI 重识别或恢复整图不得无故覆盖手工输入。
- 用户能够通过语音或文字表达菜名和约束；语音失败时必须无阻塞回到可编辑文本。
- 用户能够再提供冰箱图片，并对识别库存做人工增删和确认。
- 最终能够得到：今晚是否现实可做、家里已有、仍缺什么、时间、难度、可执行步骤和必要提醒。

### 5.2 从冰箱出发

- 用户能够直接提供冰箱实景，真实相机、相册和固定示例都可用。
- 视觉识别结果必须经过用户确认；AI 不确定的食材不能自动当作可用库存。
- 非食物和未确认的不确定物品不能进入规划库存；局部看不清时允许补拍并合并结果，也允许跳过，不能强迫用户从头开始。
- 可以继续使用或清除本设备上次人工确认库存，但必须提示它不代表这些食材现在仍然存在。
- 用户既能让 Agent 根据库存自由决定，也能补充自己想吃的菜。
- 最终能够得到由确认库存和当晚约束驱动的可执行晚餐方案。

### 5.3 两类任务共有的能力

- 餐次、可支配时间、精力或相关现实约束由用户确认，不由 AI 擅自断言。
- 等待过程有明确状态、已用时间和用户可理解的下一步。
- 超时、识别失败和模型失败时不得把缓存伪装成实时模型成功；降级状态必须诚实可辨。
- 用户能够重新规划、调整条件、生成另一方案或换一种开始方式；状态保留与清空符合操作语义。
- 用户能够对结果反馈，并用明确反馈约束下一次规划。
- 多次规划结果可以被理解和切换，当前看到的是哪一版必须清楚。
- 目标菜的“已有、缺少、待确认”必须互斥；不能再次出现“还差 / 主要材料够了”，也不能把另一道菜包装成目标菜完整版。
- “先吃清单”只使用用户主动确认的开封、标签或不确定状态，不自动判断过期或安全食用。
- 冰箱整理和布局建议仍可到达，但不必沿用当前折叠卡片或占据主流程。
- 缺料时可以模拟加入购物车并重新规划；必须区分“家里原有”“本次模拟补入”“尚未真实购买”，不得暗示真实下单或扣款。
- 做饭过程中可上传当前画面、选择问题与症状并描述当前步骤，获得画面观察、最多三个动作、检查点和最多两轮的下一步救援；味道只能来自用户试味描述，不能从图片判断。
- 饭后可拍摄、选择或加载示例成品图，生成可编辑的标题、封面文案、旁白、补拍建议和标签；生成失败也要有可编辑兜底，确认草稿不得暗示已经真实发布。
- 正常评委界面不展示模型名、provider、JSON、confidence、Schema、缓存路径、内部画像或管理员能力。

## 6. 真实能力与最低边界

- 相机文件输入保留 `capture="environment"`；相册文件输入不得增加 `capture`。
- 图片压缩、目标菜 ROI、冰箱局部补拍、语音降级和人工库存确认仍需存在，但展示机制可完全重做。
- 不能根据单张图声称判断食材过期、新鲜度、气味、肉类熟度或是否安全食用。
- 不保存或输出 API Key、管理员令牌、认证头、原始照片和原始音频。
- 商城只做补购模拟，生活记录只生成可编辑草稿。
- 失败时页面不能空白，也不能把固定样例悄悄包装成实时结果。
- 目标菜识别失败时回到文件名或手动输入；真实冰箱识别失败时进入明确的空库存确认；规划、救援和生活记录失败都要有保守、可继续的兜底。
- 等待过程中保留阶段和耗时；模型、缓存、超时与错误兜底不得相互冒充。所有 Agent 请求应保留可关联的 session ID 和 request ID。
- 关键操作应适合手机触控，并具有键盘焦点和非纯颜色的状态表达；具体尺寸、组件和视觉方案由设计决定。

## 7. 现有能力基线与后端扩展自由

现有接口只说明哪些能力今天已经可用，不能反过来限制产品设计。Kimi 可以大胆提出或实现新的展示能力、数据字段、状态流、接口和后端 Agent 支持；后端工作可以由 Kimi完成，也可以明确写出契约后交给 Codex 补齐。

任何新增能力都应直接增强评委可见价值、核心闭环或交互可信度，而不是为了显得功能多而堆模块。需要后端配合时，记录四项即可：用户价值、建议接口/字段、失败兜底、当前实现状态。不要因为后端尚未存在就把好设计退回旧结构。

| 能力 | 现有接口 | 当前请求关键字段 | 当前前端依赖的业务结果 |
|---|---|---|---|
| 识别冰箱 | `POST /api/analyze-fridge` | `imageDataUrl`, `sourceFileName` | `vision.items / uncertainItems / warnings` |
| 识别目标菜 | `POST /api/analyze-target-dish` | `imageDataUrl`, `sourceFileName` | `targetVision` 的菜名候选、材料、工具、耗时、难度和提醒 |
| 自由晚餐规划 | `POST /api/plan-dinner` | `inventory`, `userContext` | `plan` 的结论、主方案、步骤、升级、兜底和商业建议 |
| 目标菜规划 | `POST /api/plan-target-dish` | `inventory`, `userContext`, `targetDish{text,intentTime,imageAnalysis,shoppingDecision}` | `targetPlan` 的目标菜、结论、已有/缺少、补购、做法和用户适配 |
| 语音转写 | `POST /api/transcribe-audio` | `audioDataUrl`, `mimeType` | `transcript`；失败回手动输入 |
| 先吃清单 | `POST /api/eat-first` | `itemStates[{name,status}]` | 优先项、待确认项、摘要和 Planner 约束 |
| 冰箱整理 | `POST /api/fridge-organization` | `inventory`, `itemStates`, `storageConfirmations` | 粗粒度建议与前后布局预览 |
| 做饭救援 | `POST /api/rescue-dish` | 当前图片、问题/症状/描述、`dishContext`, `followUp` | 观察、判断、动作、检查点、追问与轮次状态 |
| 生活记录草稿 | `POST /api/generate-life-log` | 成品图片、文件名、`mealContext` | 画面理解、可编辑标题/封面/旁白、补拍建议和标签 |
| 结果反馈 | `POST /api/users/xiaolin/feedback` | `type`, `source`, `mealName` | 保存显式反馈；失败不阻断重规划 |

对复用的现有请求，继续通过 `frontend/src/lib/agentSession.js` 或等价适配保留 `x-agent-session-id` 与 `x-agent-request-id`。如果新体验需要新的请求体、响应字段或端点，可以设计并实现新的契约；替换旧契约时必须写清迁移关系和稳定降级，不能让失败状态变成空白页面。

当前构建接口保持：

```bash
npm run showcase:build
```

当前生产由 `demo/server.mjs` 同源提供 `frontend/dist` 和 `/api/*`。第三轮允许按新体验需要修改 `demo/server.mjs`、`demo/agent/`、Schema、固定演示数据和前后端适配；不读取或写入真实用户数据。除非新设计确实要求改变部署形态，否则继续沿用单服务同源。设计和本地实现阶段不部署、不推送，也不修改 CloudBase 线上流量。

## 10. 分阶段交付

### 阶段 A：体验建模

用简短文字确定：用户任务、新的信息架构、核心设计命题、主要交互机制、信息披露策略，以及“功能结果 → 新体验位置”的映射。不要从旧页面反推结构，也不要输出三套泛化风格拼盘。

### 阶段 B：独立方向与旗舰路径

选择一个最有把握、可实施的方向，并直接做出高保真、可交互的旗舰任务路径。优先证明：用户看到想吃的菜，结合现实冰箱，最终获得能行动的决定。

第一检查点只要求方向和旗舰路径成立，不要急着把所有次级功能塞回去。用户将在本地浏览器直接评价和批注；确认方向前停止大规模迁移。

### 阶段 C：功能迁移、能力扩展与双任务闭环

方向确认后，再读取旧实现核对逻辑，并把另一类核心任务、真实输入、加载、失败、重规划和状态恢复接入新体验。新设计需要现有后端没有提供的能力时，直接新增实现或写出可执行契约，由 Codex 接力补齐。

Kimi 负责保持设计一致性；Codex 负责审计 API、边缘状态、安全边界和功能遗漏。不能为了迁移旧功能破坏新的主体验。

### 阶段 D：次级能力与浏览器验收

把反馈、方案历史、先吃清单、冰箱整理、模拟补购、做饭救援和生活记录迁移到合理位置，并完成已经批准的新后端能力。随后只做桌面和手机主路径、固定示例、失败降级及补购前后状态的定向验证；不因新增接口自动升级为无关模型端点的全量回归。

## 11. 验收标准

### 11.1 重构成立

- 用户第一眼不能把它判断为 012 的换色版。
- 页面轮廓、信息架构、交互方式或核心组件体系有实质变化。
- 即使移除颜色，仍能看出是重新设计。
- 代码差异不能主要由 CSS 重写构成。
- 不熟悉旧版的人无需学习内部术语即可使用。

### 11.2 30 秒表达成立

随机体验者能够用自己的话说清：用户遇到了什么问题、AI 看了什么、用户确认了什么、最终做了什么决定、抖音闭环体现在哪里。

### 11.3 功能成立

- 两类核心任务最终均能走通。
- 必要功能结果都有明确、可理解的到达方式。
- 固定示例、真实输入、加载、失败和重规划均可验证。
- 模拟补齐前后的库存和方案语义清楚，不产生“已经买过”的误解。
- 次级能力不丢失，也不淹没主任务。

### 11.4 体验成立

- 手机端无横向溢出、遮挡或无法触达的主要操作。
- 桌面演示不是把手机页面机械拉宽。
- 主行动明确，用户不需要读大量说明才能继续。
- 没有重复标题含义的空洞副标题。
- 视觉内容服务于理解，不只是装饰。
- 新方案、失败、模拟补齐和其它状态变化具有可感知的反馈。

### 11.5 工程成立

- 已复用能力保持兼容；新增或替换能力具有明确接口、迁移关系和稳定兜底。
- 不暴露密钥、管理员令牌和内部调试信息。
- `npm run showcase:build` 与 `git diff --check` 通过。
- 浏览器完成两类核心任务的定向验收。
- 旧版仅保留 Git 回滚点，不作为设计基础。
