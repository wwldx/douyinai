## 2. 阶段 2 已实现能力

### 2a：先吃与规划版本

- 库存确认页可标记已开封、用户确认标签日期临近或状态不确定。
- `/api/eat-first` 失败不阻断规划；成功或失败结果都冻结进每版 `requestSnapshot.eatFirst`。
- 反馈、模拟补购、部分已拿到、补目标菜和“另一个思路”都从当前版本快照派生。
- “另一个思路”成为真实新版本；血缘保存来源方案 id、冻结序号和候选语义。
- 首次规划失败冻结原请求；重试原样重发，规则兜底不重复生成，取消不清空失败卡。

### 2b：大字步骤

- `steps.js` 统一计算行动单、大字视图和救援使用的有效步骤。
- 大字视图使用 Portal 覆盖当前视口；背景锁定，手机主操作不依赖键盘。
- 翻页只是浏览；只有点“我现在做到这一步”才写入 `stepPositions[planId]`。

### 2c：做饭救援

- 行动单“开火之后”区进入真实救援；无方案版本不提供凭空救援。
- 真实救援冻结进入时查看版本的菜名和有效步骤，支持最多两轮。
- 第二轮必须重新拍现场、明确选择“有好转/还是没好”，不沿用第一轮照片。
- 独立示例使用两张明确标注的 AI 示例图，只演示第一轮，始终显示“与本次晚餐方案无关”。
- 结果优先展示“现在只做”，然后展示观察、最多三项动作、检查点和边界提醒。
- 刷新只恢复结构化草稿和轮次，不恢复媒体、不静默重发。

### 2d：生活记录

- 行动单“做完了，记录一下”进入真实成品图路径。
- 生成结果直接是可编辑草稿：标题、封面、旁白、补拍建议、标签和提醒。
- 草稿按 `planId` 自动保存在本次会话；内容不变时不刷新 `lastEditedAt`。
- “复制完整草稿”包含用户看到的所有草稿内容；界面始终明确尚未发布。
- 当前仓库没有能诚实充当本方案饭后成品的示例图，因此没有用户端示例入口。

## 3. 最终状态收口

1. 空库存不再使用 `emptyDeclared` 中间态。零识别横幅和底部空库存按钮互斥；存在任何有效食材时只能提交有效库存。
2. 行动单版本箭头、模拟补购、“本次已拿到”和库存纠正按钮达到 44px 手机触控目标。
3. `alternativeFrom.sourceSequence` 在新版本创建时冻结，源版本被最近三版裁掉后血缘仍成立。
4. 救援中断严格绑定 `kind + planId + scope(plan/demo)`；生活记录中断绑定 `kind + planId`；规划和识别中断维持全局语义。
5. 同方案空救援会刷新最新有效步骤。新草稿只有 `stepTouched === true` 才保留主动选择；旧草稿仅在缺字段时根据 `stepUnknown/stepIndex` 迁移。
6. 已有救援轮次后快照完全冻结；切到另一方案开始救援会替换当前单工作区。

## 5. API 与缓存真值边界

- 阶段 2 复用 `/api/eat-first`、规划接口和生活记录接口，并接入 `/api/rescue-dish`。
- 固定示例必须使用受控 `demoKey`；真实同名文件不能按文件名命中示例。
- 救援缓存同时绑定受控素材身份与语义请求签名；同一图的不同症状、步骤或 follow-up 不能复用错误结果。
- 生活记录真实上传不发送 `demoKey` 或 `sourceFileName`；未来新增示例时同样必须使用受控键和语义签名。
- `model`、`model-timeout-cache`、`model-error-cache`、`rules-fallback` 和固定示例在用户文案中保持诚实区分。
