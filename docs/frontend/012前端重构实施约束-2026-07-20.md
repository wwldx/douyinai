# 012 前端重构实施约束

日期：2026-07-20
状态：Verified（本地 V2；部署与 iPhone 真机待后续）
权威入口：`docs/roadmap/大区赛升级总计划-2026-07-13.md` 的 U34

## 1. 本次交付

在不改变 Vite + React、Node API、JSON 合约和既有功能链的前提下，把评委展示端从“工程能力面板”收敛成普通用户能在 30 秒内理解的移动端晚餐决策体验。

本次只改 `frontend/` 展示层；CloudBase 011 公网保持不动，012 完成本地定向验收后再决定是否发布。

验证等级为 V2：一次生产构建、桌面与 390px 主路径、必要的固定示例交互。不运行 30 例模型回归，不改模型，不部署。

## 2. 唯一体验原则

每屏只回答一个用户问题，并只突出一个主操作：

| 页面 | 用户问题 | 主操作 |
|---|---|---|
| 场景入口 | 你是刷到想吃的，还是打开冰箱没想法？ | 选一个入口 |
| 菜图确认 | 你想吃哪道菜？ | 确认菜名，继续看冰箱 |
| 冰箱上传 | 家里现在有哪些能用的食材？ | 拍冰箱并识别 |
| 库存确认 | 这些食材现在都能用吗？ | 用确认库存生成方案 |
| 结果 | 今晚最现实的一顿怎么做？ | 开始照着做；缺主料时先补齐并重算 |

做饭救援、冰箱整理、反馈、方案历史和饭后记录保留，但不得与核心做法同权竞争；默认以折叠入口或次级面板呈现。

## 3. 信息与文案规则

- 标题尽量不超过 16 个汉字，必要说明不超过 28 个汉字，按钮尽量不超过 10 个汉字。
- 不在用户界面使用 `Agent`、`Planner`、`Schema`、`模型`、`规则`、`粗分区`、`诊断编号` 等工程词。
- 副标题必须增加新信息，禁止换句话重复标题。
- 正常成功时不展示来源、模型名和耗时；网络慢或失败时保留明确降级说明，诊断编号放在可展开详情中。
- 用户关键判断不能只藏在 hover；手机端解释必须可点击展开。
- 商城按钮明确是演示，不真实下单；生活记录只生成可编辑草稿，不自动发布。
- 不夸大图片能力：不能判断过期、新鲜度、气味、熟度或是否安全食用。

## 4. 屏幕调整

### 4.1 场景入口

- 保留两张真实图片和 `data-testid="entry-feed"`、`data-testid="entry-fridge"`。
- 标题改为直接问题，删除 lead 与卡片内的重复流程复述。
- 两个入口允许视觉主次，但都必须清楚可点。
- 不再显示“Feed 路线”或“视觉搜索”等内部表达；改为“想吃这道菜”“看看冰箱”等用户语言。

### 4.2 菜图确认

- 主问题为“你想吃哪道菜？”。
- 图片、文字、语音是可组合输入，不让用户误以为三者都必填。
- 相机、相册保持独立；示例降为次级入口。
- ROI 默认折叠在“没识别准？只看这部分”，仍保留选整张、取消、恢复整图。
- 菜名文本框始终可编辑，手工修改后不得被 ROI 或恢复识别覆盖。

### 4.3 冰箱上传

- 冰箱照片是视觉主角；拍照为主，相册和示例为次。
- 餐次、时间、状态选择压缩为轻量控制，不再用多个同权卡片重复解释。
- 继续保留历史库存快照，但作为可展开次级入口，并明确不代表实时库存。

### 4.4 库存确认

- 标题直接问“这些食材现在都能用吗？”。
- 选中态明确表示“我确认可用”，控件最小高度 44px，并增加 `aria-pressed`。
- 局部补拍保留，但不要三按钮并排；390px 最多两个同排按钮。
- “优先处理”默认折叠，安全边界留在展开区。
- Feed 目标菜只作为一行上下文；冰箱路线的“帮我决定 / 我有想吃的”保持明确。

### 4.5 结果页

- 首屏顺序固定：结论、时间/难度/关键缺口、主行动、最多四步做法。
- 合并重复的 eyebrow、lead、成功生成说明与深色路线卡。
- “已有 / 还差 / 待确认 / 可选升级”合并为一张材料摘要，先突出关键缺口。
- 方案历史、先吃清单、冰箱整理放到做法之后并折叠。
- 做饭救援、反馈、饭后记录改为次级分组；其内部状态与 API 不得删除。
- 模拟补购仍要带材料重新规划并进入方案历史，按钮可缩短为“补齐后重算”。
- “调整条件”“再生成一个方案”“换一种开始方式”语义保持不变。

## 5. 视觉系统

- 画布暖白 `#F7F4EE`，表面 `#FFFCF7`，正文 `#1B1D1A`，弱文字 `#686E68`。
- 主品牌绿 `#176B55`，强调橙 `#E85D3F`，警告只保留一套暖黄色。
- 正文移动端 16px 左右，辅助文字不低于 13px；字重收敛到 500/600/700。
- 间距采用 4/8/12/16/24/32/48；减少每个区块各自的边框、底色和阴影。
- 圆角：控件 12px、普通内容 16px、主图 20-24px。
- 所有触控控件至少 44px，主操作 50px；390px 下一个区域最多两个并列按钮。
- 统一 `:focus-visible`，选择按钮使用 `aria-pressed` 或完整 tab 语义。
- 加入 `prefers-reduced-motion`；动画只用于 120-200ms 的状态反馈。
- 顶部和底部均考虑 iOS safe area；键盘弹起时不应被固定底栏遮住。

## 6. 冻结合约

不得整文件重写 `frontend/src/App.jsx`。不得修改：

- 状态、refs、请求函数、流程函数、回退逻辑、超时逻辑和本地缓存逻辑。
- `/api/*` 路径、请求体、响应字段和 `x-agent-session-id` / `x-agent-request-id` 请求头。
- `frontend/src/lib/agentSession.js`、`frontend/src/lib/targetCoverage.js`、`frontend/src/data/samples.js`。
- 相机 input 的 `capture="environment"`；相册 input 不得增加 `capture`。
- 图片压缩、ROI 裁剪、语音降级、失败不冒充缓存、人工确认库存、模拟补购重规划、最近 3 个方案、两轮救援和生活记录编辑行为。
- `demo/`、`data/`、Docker、部署配置和后端。

允许修改：

- `frontend/src/index.css`。
- `App.jsx` 中纯展示 JSX、文案、className 与可访问性属性。
- `SpeechInput.jsx`、`ImageFocusSelector.jsx`、`Toast.jsx` 的展示结构，但必须保留 props 和行为。
- 新增无业务状态的纯展示组件；不引入大型 UI 库，不换框架。

## 7. 最小验收

1. `npm run showcase:build` 通过。
2. Feed：菜图/菜名 -> 冰箱 -> 库存 -> 目标菜结果。
3. 冰箱：冰箱 -> 库存 -> 自由推荐结果。
4. 相机/相册、语音文本兜底、ROI、局部补拍、调整条件、负反馈重规划、最近 3 个方案、模拟补购、两轮救援和生活记录入口仍存在。
5. 桌面与 390px 无横向溢出，390px 不出现三个主要按钮挤在一行。
6. 所有关键触控不低于 44px，选择态不只依赖颜色。
7. 正常用户页不泄露模型/provider/Schema/内部 JSON；安全与演示边界仍可找到。

## 8. Kimi 实施边界

先阅读本文件和 `AGENTS.md`，再只检查 `frontend/src/App.jsx`、`frontend/src/index.css` 与三个现有组件。优先完整实现入口、库存确认、结果三屏，再统一菜图和冰箱上传屏。不要先讨论框架，不改后端，不提交、不推送、不运行模型请求；完成后只报告改动文件、关键设计选择、未触碰合约和建议由 Codex 验收的风险点。
