## 1. 第一检查点当前结论

用户已确认第三轮界面属于真正重构，整体方向明显优于前两轮旧结构换肤。

当前已形成一条高保真旗舰路径：

1. `刷到`：用短视频菜图建立“今晚想吃”的动机。
2. `确认`：确认菜名、可支配时间和补充要求。
3. `现实`：拍冰箱并对照目标菜所需食材，人工确认库存与不确定项。
4. `决定`：用纸质行动单表达“已有 / 还差 / 模拟补入 / 做法”，并可切换不补货方案。

桌面端使用固定故事轨，手机端收为顶部进度条。当前旗舰路径以黄焖鸡示例数据为稳定演示，不代表真实模型链路已经迁移。

## 2. 当前版本明确没有完成的内容

以下能力在第三轮第一检查点中被有意暂缓，并非已经否决：

- 冰箱起点的完整独立路径。
- 真实模型 API。
- 等待阶段与已用时间。
- 方案历史。
- 显式反馈约束后的重新规划。
- 用户确认状态后的先吃清单。
- 冰箱粗分区与整理建议。
- 做饭失败后的救援。
- 饭后生活记录草稿与抖音分享闭环。

此外，当前首页关于“从冰箱直接开始”只显示后续阶段提示，不提供假入口。

## 3. 用户本次浏览器批注

批注位置：冰箱确认页“不确定食材”区域。

用户反馈：

> 看不清的地方，目前假如想补充的话，只能手动输入添加吗？可以考虑增加语音输入或者直接允许用户补拍吗？是不是方便点。

该反馈先记录，不立即实施。需要与 Kimi 3 一起讨论：

- “说出是什么”和“补拍这一处”是否都应提供。
- 两个入口如何融入当前连续叙事，而不是重新堆成工具按钮集合。
- 补拍后的确认步骤如何表达，避免模型误识别直接污染库存。
- 手机和桌面是否采用不同入口优先级。

## 4. Codex 已核对的工程事实（不是产品决定）

- 仓库已有真实语音组件 `frontend/src/components/SpeechInput.jsx`，支持浏览器语音识别、录音转写和手动输入兜底；是否复用以及如何呈现仍待讨论。
- 现有 `/api/analyze-fridge` 可以识别补拍近照；如果后续采用补拍，必须展示识别候选并由用户明确确认后才加入库存，不能只增加一个没有真实处理能力的按钮。
- 当前新前端的冰箱页仍使用稳定示例库存，没有接入真实冰箱识别。补拍能力应与真实 API 迁移一起设计，避免一半真实、一半写死的混合状态。
- “食材新鲜度提醒”必须继续遵守安全边界：AI 不根据照片判断过期、变质或可安全食用。可以恢复的是用户主动确认“已开封 / 标签日期临近 / 状态不确定”后的先吃提醒。
