## 1. 第一检查点当前结论

用户已确认第三轮界面属于真正重构，整体方向明显优于前两轮旧结构换肤。

当前已形成一条高保真旗舰路径：

1. `刷到`：用短视频菜图建立“今晚想吃”的动机。
2. `确认`：确认菜名、可支配时间和补充要求。
3. `现实`：拍冰箱并对照目标菜所需食材，人工确认库存与不确定项。
4. `决定`：用纸质行动单表达“已有 / 还差 / 模拟补入 / 做法”，并可切换不补货方案。

桌面端使用固定故事轨，手机端收为顶部进度条。当前旗舰路径以黄焖鸡示例数据为稳定演示，不代表真实模型链路已经迁移。

## 2. 必须纠正的范围认识

产品始终有两类同等核心的任务：

1. 从想吃的菜出发：目标菜 → 现实冰箱 → 今晚决定。
2. 从冰箱出发：现实冰箱 → 确认库存 → 自由推荐，或再补充目标菜。

第一检查点只被要求实现第一条旗舰路径，以便先验证真正重构后的视觉与交互方向。第二条不是可选功能，也没有被产品否决；它被明确安排在方向确认后的双任务闭环阶段。后续讨论只决定它怎样进入、与第一条路径在哪里汇流以及如何保持新设计质量，不再讨论“要不要恢复”。

完整产品还必须恢复真实模型、等待与耗时、诚实失败降级、调整条件、重新规划和状态恢复。这些是两类任务成立的基础能力，不是次级装饰。

以下已验证能力按权威简报仍属于不可丢失的功能结果，但可以讨论阶段、入口、信息层级以及是否进入 30 秒主演示：

- 方案历史与显式反馈约束后的重新规划。
- 用户确认状态后的先吃清单。
- 冰箱粗分区与整理建议。
- 做饭失败后的两轮救援。
- 饭后生活记录草稿与抖音内容闭环。

若 Kimi 3 建议永久删除其中某项，必须明确说明这与当前权威简报冲突、删除能换来什么，以及需要用户修改哪条产品要求；不得在迁移中静默丢失。

当前首页关于“从冰箱直接开始”只显示后续阶段提示，不提供假入口。

## 3. 用户本次浏览器批注

批注位置：冰箱确认页“不确定食材”区域。

用户反馈：

> 看不清的地方，目前假如想补充的话，只能手动输入添加吗？可以考虑增加语音输入或者直接允许用户补拍吗？是不是方便点。

该反馈先记录，不立即实施。需要与 Kimi 3 一起讨论：

- “说出是什么”和“补拍这一处”是否都应提供。
- 两个入口如何融入新的整体体验，而不是重新堆成工具按钮集合。
- 补拍后的确认步骤如何表达，避免模型误识别直接污染库存。
- 手机和桌面是否采用不同入口优先级。

## 4. Codex 已核对的工程事实（不是产品决定）

- 仓库已有真实语音组件 `frontend/src/components/SpeechInput.jsx`，支持浏览器语音识别、录音转写和手动输入兜底；是否复用以及如何呈现仍待讨论。
- 现有 `/api/analyze-fridge` 可以识别补拍近照；如果后续采用补拍，必须展示识别候选并由用户明确确认后才加入库存，不能只增加一个没有真实处理能力的按钮。
- 当前新前端的冰箱页仍使用稳定示例库存，没有接入真实冰箱识别。补拍能力应与真实 API 迁移一起设计，避免一半真实、一半写死的混合状态。
- “食材新鲜度提醒”必须继续遵守安全边界：AI 不根据照片判断过期、变质或可安全食用。可以恢复的是用户主动确认“已开封 / 标签日期临近 / 状态不确定”后的先吃提醒。

## 5. 后续与 Kimi 3 的多轮讨论任务

Kimi 3 进入多轮产品评审模式。本阶段只讨论，不改代码、不创建文件、不提交；用户、Codex 与 Kimi 3 达成明确结论后，才会收到单独的实施授权。

### 第一轮：校正理解并提问

先确认以下事实：

- 冰箱起点是必须恢复的第二条核心任务，不是可选次级功能。
- “从刷到到出锅”是第一检查点形成的设计命题，不是预先冻结的产品总结构；当前实现实际只到行动单。
- Kimi 3 可以判断该命题在双入口和后续能力恢复后仍然成立、需要改写，或应被更好的整体命题替代。
- 现阶段不能为了保护四场景结构而强塞功能，也不能为了迁移旧功能退回旧卡片大厅。

第一轮不要直接给最终方案。请先：

1. 用简短文字诊断当前第一检查点在恢复双核心任务时面临的主要结构矛盾。
2. 区分哪些是产品硬事实、哪些只是当前设计假设。
3. 向用户和 Codex 提出最多 5 个真正会改变方案的关键问题；每个问题说明不同答案会怎样影响设计。
4. 提问后停止，等待回答。可以在后续轮次继续追问，不需要一次性定稿。

### 第二轮：提出推荐结构

收到回答后，再提出一个明确推荐方向，并说明：

1. Feed 起点与冰箱起点如何出现、分流、汇流和返回。
2. 当前“刷到 / 确认 / 现实 / 决定”哪些保留、哪些改写；是否继续使用“从刷到到出锅”作为总命题。
3. 真实模型、等待与耗时、失败降级、重新规划和状态恢复如何进入体验。
4. “说出是什么 / 补拍这一处 / 忽略”怎样处理，补拍失败、仍不确定或出现多个候选时如何收口。
5. 做饭救援与饭后生活记录如何成为晚餐决定后的自然延伸。
6. 方案历史、反馈重规划、先吃清单和冰箱整理分别位于主路径、次级入口还是后续阶段，以及理由。

先讨论产品取舍和信息架构，不画旧页面拼装图，不写实现代码。方案提出后再次停止，等待用户与 Codex 反馈。

### 第三轮：确认后的分阶段恢复计划

只有推荐结构经讨论确认后，才输出分阶段恢复计划。每阶段只写：目标、进入条件、增加的场景或状态、明确不做什么、验收标准。仍不实施，直至用户另行授权。
