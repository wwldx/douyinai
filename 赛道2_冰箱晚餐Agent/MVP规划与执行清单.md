# MVP 规划与执行清单

更新日期：2026-05-23  
项目：冰箱晚餐 Agent  
目标：做出一个现场可演示的视觉搜索 AI Agent 原型

## 1. 产品目标

让用户拍一张冰箱照片后，在 30 秒内得到一个现实可执行的晚餐方案。

系统需要回答三个问题：

1. 冰箱里大概有什么。
2. 这些东西能不能做出今晚满意的一顿饭。
3. 如果不能，应该补买什么，或是否应该直接外卖。

## 2. 用户画像与模拟上下文

Demo 阶段使用模拟用户上下文，不要求真实授权数据。

示例画像：

```json
{
  "user": {
    "name": "小林",
    "cookingLevel": "新手",
    "preferences": ["少油", "微辣", "不爱洗太多锅"],
    "avoid": ["香菜", "复杂刀工", "油炸"],
    "recentMeals": ["黄焖鸡外卖", "麻辣烫", "便利店饭团"],
    "goal": "今晚想吃热的，但不要太麻烦"
  },
  "context": {
    "time": "21:10",
    "availableCookingTime": "25 分钟",
    "energyLevel": "低",
    "nextSchedule": "22:00 需要继续改项目文档",
    "weather": "小雨"
  }
}
```

需要强调：

- 这些数据是“模拟已授权上下文”。
- 真实产品中可来自用户授权的历史饮食、日程、位置、购物记录和反馈。
- Demo 主流程不要让用户填写大量信息。

## 3. Demo 食材选择

为了降低识别风险，演示图片应使用容易识别的材料。

优先食材：

| 类别 | 推荐样例 | 原因 |
|---|---|---|
| 蔬菜 | 番茄、黄瓜、生菜、胡萝卜 | 颜色明显、形状稳定 |
| 蛋奶 | 鸡蛋、牛奶、酸奶 | 识别稳定，菜谱通用 |
| 主食 | 面条、面包、米饭、速冻饺子 | 容易生成晚餐方案 |
| 蛋白质 | 火腿肠、鸡胸肉包装、豆腐 | 可扩展菜谱 |
| 饮料 | 可乐、矿泉水、果汁 | 增加真实冰箱感 |
| 调味线索 | 酱油、辣酱、沙拉酱 | 只作为辅助，不强依赖 |

避免食材：

- 保鲜盒里的剩菜。
- 被袋子遮住的散装肉。
- 半透明包装里的模糊食材。
- 堆叠严重、光线太暗的冰箱。
- 需要专业判断新鲜度的食材。

## 4. 核心流程

```text
用户上传冰箱图片
  -> 视觉模型识别食材
  -> 生成可编辑库存卡
  -> 用户轻量确认
  -> 结合画像和时间约束
  -> 生成晚餐方案
  -> 输出保底菜 / 进阶菜 / 缺料清单 / 外卖兜底
```

## 5. 页面结构

建议单页应用：

| 区域 | 功能 | 优先级 |
|---|---|---|
| 顶部状态栏 | 产品名、赛道、当前模型状态 | 中 |
| 图片输入区 | 上传冰箱图、选择预置样例 | 高 |
| 食材库存卡 | 展示识别出的食材，可删除或标记错误 | 高 |
| 用户状态卡 | 展示模拟厨艺、偏好、时间、精力 | 高 |
| 晚餐推荐区 | 保底菜、进阶菜、外卖兜底 | 高 |
| 缺料购物区 | 推荐补买 1 到 3 个材料 | 中 |
| 安全提醒区 | 新手风险、刀工、油炸、食材新鲜度提醒 | 高 |
| 商业延展区 | 生鲜补货、外卖、厨具升级建议 | 低，作为展示增强 |

## 6. 模型调用策略

优先使用 GPT / Claude 高阶视觉模型。

建议拆成两个模型任务：

1. 视觉识别：从图片中识别食材和包装线索。
2. 晚餐规划：结合食材、用户画像和时间约束生成方案。

工程接口：

```text
FridgeVisionProvider
  - provider: "openai" | "anthropic" | "mock"
  - analyzeFridge(image)

DinnerPlannerProvider
  - provider: "openai" | "anthropic" | "mock"
  - planDinner(inventory, userContext)
```

可以先用同一个高阶模型完成两个任务，但代码层面建议拆开，方便后续替换。

## 9. Prompt 草案

### 视觉识别 Prompt

```text
你是一个冰箱食材视觉识别助手。请从用户上传的冰箱照片中识别可见食材、饮料、速食和包装线索。

要求：
1. 只识别图片中能看到的内容，不要编造。
2. 对被遮挡或不确定的物品，放入 uncertainItems。
3. 不要判断食材一定新鲜，只能说“看起来可用”或“需要用户确认”。
4. 输出固定 JSON，不要输出 Markdown。
```

### 晚餐规划 Prompt

```text
你是一个现实主义晚餐规划 Agent。你需要根据冰箱库存、用户厨艺、口味偏好、近期饮食和今晚可用时间，推荐一顿现实可执行的晚餐。

要求：
1. 不要只给菜谱，要先判断今晚适不适合自己做。
2. 新手用户不要推荐高风险动作，例如油炸、复杂刀工、处理整鱼整鸡。
3. 推荐必须考虑可用时间，时间很晚时优先简单菜、速食或外卖兜底。
4. 至少输出一个现有材料可做的保底方案。
5. 如果缺料，只推荐 1 到 3 个关键补买项。
6. 商业建议必须克制，不能硬推消费。
7. 输出固定 JSON，不要输出 Markdown。
```

## 10. 商业化表达

可以讲商业延展，但要注意表达方式。

不建议说：

> 勾引用户消费。

建议说：

> 在用户真实晚餐决策中，自然衔接生鲜补货、外卖兜底和厨具升级建议。

可展示的商业场景：

| 场景 | 表达方式 |
|---|---|
| 缺少青菜 | 推荐补买一把青菜，提升菜品完整度 |
| 时间太晚 | 推荐外卖或速食兜底 |
| 经常做低油炸物 | 温和建议空气炸锅 |
| 长期重复外卖 | 推荐简单自炊计划 |

关键原则：商业推荐必须服务于用户当下决策，不能喧宾夺主。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 冰箱识别不准 | 推荐材料错误 | Demo 使用清晰样例，加入用户确认 |
| 食材新鲜度误判 | 安全风险 | 明确模型不能判断过期，要求用户确认 |
| 菜谱难度过高 | 用户执行失败 | 根据厨艺约束推荐，新手默认保守 |
| 推荐不考虑时间 | 不现实 | 必须输入可用时间，并在 prompt 中硬约束 |
| 商业推荐太硬 | 价值观风险 | 用“补货/兜底/升级建议”表达 |
| 功能太多 | Demo 发散 | MVP 只围绕今晚一顿饭 |

## 12. 评分点对齐

| 评分关注 | 对齐方式 |
|---|---|
| 用户价值 | 解决“今晚吃什么”这个高频问题 |
| AI 能力结合 | 视觉识别、偏好理解、时间约束和安全规划共同决策 |
| 体验完整性 | 拍冰箱 -> 确认库存 -> 推荐晚餐 -> 缺料/外卖兜底 |
| 创新性 | 从看见食材到生成现实行动，而不是普通菜谱搜索 |
| 现场表现 | 食材图直观，演示结果容易理解和讨论 |

## 13. 开发阶段

第一阶段：静态闭环

- 准备 3 张清晰冰箱样例图。
- 手写对应识别 JSON。
- 手写晚餐规划 JSON。
- 完成前端 UI。
- 实现食材确认和推荐展示。

第二阶段：接入模型

- 实现图片上传。
- 调用 GPT / Claude 视觉模型识别食材。
- 调用 GPT / Claude 生成晚餐计划。
- 加 JSON schema 校验。
- 加失败兜底。

第三阶段：现场增强

- 增加“我只有 15 分钟”追问。
- 增加“我不想洗锅”追问。
- 增加缺料购物清单卡片。
- 增加轻商业建议卡。
- 准备录屏和离线缓存。

## 14. 60 秒讲解脚本

```text
我们做的是冰箱晚餐 Agent，选择视觉搜索赛道。

很多人晚上回家打开冰箱，其实不是想知道里面有什么，而是想知道今晚到底吃什么。我们让用户拍一张冰箱照片，AI 先识别可用食材，再结合用户的厨艺水平、口味偏好、最近吃饭记录和今晚可用时间，给出一个现实可执行的晚餐方案。

比如用户是新手，今晚只有 25 分钟，那系统不会推荐复杂硬菜，而是优先给出番茄鸡蛋面这种低失败率方案。如果材料不够，它会告诉你补买一两样关键食材；如果时间太晚，也会建议速食或外卖兜底。

所以它不是单纯识别食材，也不是普通菜谱搜索，而是从真实冰箱状态出发，帮用户完成今晚这一餐的决策。
```
