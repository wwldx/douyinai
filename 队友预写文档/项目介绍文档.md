# 项目介绍：冰箱晚餐 Agent

## 一、定位目标人群

本项目面向两类核心用户：

1. **厨艺有限、不知道晚餐怎么凑合的上班族**：下班晚、精力低，面对冰箱里的食材不知道能不能做成一餐。
2. **想省心快速解决晚餐 decision fatigue 的人群**：不想动脑子想今晚吃什么，但又不想顿顿外卖。

## 二、解决的痛点与用户价值

| 痛点 | 本项目提供的价值 |
|------|------------------|
| 看得见冰箱食材，但不知道能不能凑出一顿饭 | AI 拍照识别 + 判断"能不能做" |
| 已经很累，想吃简单的但菜谱推荐动不动就炒菜 30 分钟 | 结合精力/时间约束，输出"今晚现实方案" |
| 自己厨艺有限，复杂菜谱根本搞不定 | 根据厨艺水平推荐低失败率方案 |
| 缺一两个材料不知道该补买还是换菜 | 直接给出缺料补买清单和换菜替代路线 |
| 识别工具只告诉"这是什么"，不能继续给行动 | 视觉结果直接驱动晚餐决策，不只展示识别结果 |

**核心一句话**：把"打开冰箱、不知道吃什么"的日常困境，转化为"拍一下冰箱、AI 告诉你今晚最现实的一顿饭"。

## 三、实现方案简述

### 产品入口

- **主流程**：上传冰箱照片 → AI 识别食材 → 用户勾选确认 → 输出晚餐方案（保底菜 / 进阶菜 / 缺料补买 / 兜底外卖）
- **开发调试台**：展示每一步的原始输入输出，方便核查链路

### 技术架构

```
用户上传冰箱图
    ↓
/api/analyze-fridge（视觉识别 Agent）
    ↓ 返回：食材列表 + 不确定项 + 安全提醒
    ↓
用户确认库存（勾选/取消食材）
    ↓
/api/plan-dinner（晚餐规划 Agent）
    ↓ 输入：确认后库存 + 用户上下文（厨艺/时间/精力）
    ↓
输出：保底菜 + 进阶菜 + 缺料补买 + 兜底外卖 + 安全提醒
```

- **前端**：Vite + React，单页应用，两个入口（展示页 / 调试台）
- **后端**：Node.js 服务，两个轻量 Agent API，支持 OpenAI Responses API + Right Code 中转站
- **数据**：本地预置缓存兜底，保证现场演示稳定性

### 两段式 Agent 设计

1. **视觉识别 Agent**：`/api/analyze-fridge` — 拍照识别冰箱里的食材、不确定项、新鲜度风险
2. **晚餐规划 Agent**：`/api/plan-dinner` — 根据确认后库存 + 用户上下文输出行动方案

当前未引入 LangChain / LangGraph 等重框架，两个端点 + JSON Schema 合约已经能清楚表达分工，且稳定可解释。

## 四、核心创新点

1. **从"识别物品"升级为"完成一餐决策"**
   视觉识别不是最终目的，识别结果直接驱动晚餐决策。用户不止知道"冰箱里有什么"，更知道"今晚怎么吃"。

2. **正视多模态识别不确定性 — 用户确认机制**
   遮挡、保鲜盒、剩菜等视觉不确定场景，不会硬给结论，而是标注不确定项，要求用户主动确认后才进入推荐。

3. **结合个人上下文，不做通用推荐**
   晚餐规划 Agent 读取的不只是库存，还有用户厨艺水平、口味偏好、近期饮食、时间精力，输出因人而异的方案。

4. **面向新手 / 低精力 / 深夜场景的安全约束**
   深夜推荐热软少油好消化的方案；新手不推荐油炸、复杂刀工；时间不足时优先外卖兜底，不强行推荐烹饪路线。

5. **轻量架构，服务现场稳定性**
   两个端点 + JSON Schema 已足够表达业务逻辑，无需引入 LangChain 等框架。模型出错时有缓存兜底，页面不空白。

## 五、商业延展方向（克制、自然）

- **缺料补买**：发现缺少关键材料时自然出现补买建议，不硬推
- **外卖兜底**：时间不足或食材风险高时推荐清淡热食外卖
- **厨具建议**：长期低油烹饪需求下给出少数工具建议
- **习惯反馈**：长期记录近期饮食，减少连续外卖频率

商业建议服务于用户当下决策，不做无差别推送。

## 六、技术亮点

- **流式 SSE 解析**：Right Code 中转站 Responses API 流式返回，服务端解析 `response.output_text.delta` 再返回前端，避免超大 JSON 一次性传输
- **本地缓存兜底**：预置 3 个冰箱样例 + 视觉识别缓存，超过 4.5 秒未返回时自动切换缓存，保证现场演示链路不中断
- **双入口设计**：展示页面向评委游客保留顺滑主流程；调试台面向开发展示每一步原始输入输出，便于人工验收
- **JSON Schema 合约**：前后端通过固定 JSON Schema 通信，schema 改动时前端渲染和文档同步更新，保证接口稳定性
